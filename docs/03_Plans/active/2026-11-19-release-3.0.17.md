# Release 3.0.17

## Goal

Ship site mapping rules: an operator maps Forward devices to NetBox sites in the Forward
source settings, without writing anything in Forward. One ordered list of rules, each
`location <glob> -> <site>` or `tag <Forward tag> -> <site>`. By default a device's NetBox
site is its Forward location; a mapping is what changes that. The `NetBox_Site_<name>` tag
from 3.0.16 stays as an explicit per-device override and wins over a rule.

Also in this release: the source form reads Forward tags into a dropdown and suggests
Forward location names; a Site Mapping Rules card on the Scope page and the same counts in
the support bundle; Health warns when a map cannot take the rules; refusals name the map
and the fix; saving the source form no longer turns `enable_predict` off.

## Constraints

- No customer names, network ids, snapshot ids or hostnames in the repo.
- No migration: one new optional source parameter, `site_rules`.
- A source with no rules behaves exactly like 3.0.16 on every binding, including org-bound
  queries that were not republished, and its durable hashes do not change.
- Rules that are set are never silently ignored: a custom map, a query that predates the
  rules, or a sync set to `Require diff` stops the run and says which map and what to do.
- Shipped queries change (the four site-naming maps declare `site_rules`): customers
  republish once, then set rules.
- `development/constraints-upgrade-from.txt` keeps `forward-sdk==0.1.36`, 3.0.16's own
  pin; this release does not move the SDK.
- The release-time sensitive-pattern feed is a CI secret and cannot be read locally, so the
  cut runs with the unverified-parity flag; the publish workflow applies the superset feed
  and can still refuse the tag.

## Approach

1. The tranche (PR #641) went through a design review and four audits before the cut; the
   plan's Review Record lists each finding and its fix.
2. Full Django suite and the scripts tests on the final tree, then `scripts/release.py 3.0.17`
   through the usual lineage: production PR, evidence PR, tag.
3. After the tag: republish the four queries to a customer's Forward organization (diff the
   live copies against the shipped text first), then the customer sets rules.

## Validation

- Full Django suite on the tranche commit: 4,910 tests OK (33 skipped); 463 scripts tests;
  pre-commit, harness-check, strict docs build and the browser UI gate pass. New tests were
  red before their fix or fail when it is disabled.
- Live, read-only, on a production-shaped Forward network: with empty rules the four site
  queries return rows identical to the current ones; three location rules put devices, VLANs
  and locations at the three target sites; 100 rules over 10,788 devices run in 12 s; the
  generated inline queries compile and run; the locations query returns real names.
- Not verified: a real site move on a customer-shaped NetBox (the test host was down); the
  refusal paths and the validation-page advice are unit-tested only, not run in a live sync.

## Release Step

- The release gate (`invoke ci`, the artifact test, the upgrade test) runs inside
  `release.py --write`.
- Plan: this file records the cut; the tranche plan stays in `active/` like the others.

## Rollback

Remove the rules from the source (or revert the release): sites fall back to the tag
convention and then to Forward locations, as in 3.0.16. Devices a rule moved move back on
the next sync. The VLANs and empty sites a move left behind stay in NetBox until Prune
orphans removes them (dry run first). A source with no rules is unaffected by the release.

## Decision Log

- Rules live on the source, beside the device-tag scope: they describe how a network's
  locations map to sites, shared by every sync of that network.
- Location globs and exact tags only; rank is the list position, never stored.
- The parameter is sent only to queries that declare it, found from the declared signature,
  never by text, because the helper module is copied into about thirty queries.
- Rejected: remapping site names in Python after the fetch (it cannot see tags and would
  duplicate every site-naming model); relying on the legacy retry (it does not cover the
  common bindings).
- No SDK bump in this release: the upgrade-from pin stays at 3.0.16's.
