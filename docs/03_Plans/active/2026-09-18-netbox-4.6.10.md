# Bump tested NetBox runtime to 4.6.10

## Goal

Declare and pin NetBox `4.6.10` as the tested runtime for the `maint/2.9.x`
lane, so every gate (dev stack default, release artifact validation, SBOM
check, harness) builds and validates against it instead of `4.6.8`. Also
fix a real regression the upgrade surfaces: NetBox 4.6.9 (#22812) changed
`JobsMixin.delete()` in a way that silently disables this plugin's
running-job delete protection on `ForwardSync`/`ForwardIngestion` for the
single-instance delete path.

## Constraints

- `maint/2.9.x` lane stays `4.6.x`; `4.6.10` is within the declared
  `>= 4.6.5` supported range, so this is a tested-version bump, not a
  compatibility-range change.
- `scripts/tested_runtime.py` is the single declared source; every other
  pin site must agree, including the escaped-regex form
  `check_release_authorization.py` carries specifically because a plain-text
  grep for `4.6.8` does not find it (the exact gap the 4.6.8 uplift left
  behind, per that module's own docstring).
- No production behavior changes; this is a runtime-pin and test-fixture
  update only.

## Approach

Ran `invoke harness-check` after bumping `TESTED_NETBOX_VERSION` alone and
fixed exactly what it named, per `tested_runtime.py`'s own documented
workflow. Confirmed `netboxcommunity/netbox:v4.6.10` exists before pinning
it. Test fixtures asserting the old literal are data, not pins the harness
tracks, and were swept separately by grep.

**Regression found and fixed.** After the pin bump, `invoke ci` failed two
tests unrelated to any file this plan touches:
`test_scheduled_jobs.SyncDeleteScheduleCleanupTest.test_running_job_protects_sync_from_deletion`
and `test_jobs.JobTerminationConcurrencyTest.test_pending_immediate_runner_cannot_start_during_sync_deletion`
- both reproducible in isolation, and both passing clean against unmodified
`maint/2.9.x` (4.6.8) as a control, which ruled out flakiness and pointed at
the version bump itself. NetBox's own changelog between 4.6.8 and 4.6.10
named the cause directly: `netbox/models/features.py`'s `JobsMixin.delete()`
(fixing #22812, "Avoid loading all jobs into memory when deleting a
JobsMixin object") now does

```python
def delete(self, using=None, *args, **kwargs):
    using = using or router.db_for_write(self.__class__, instance=self)
    with transaction.atomic(using=using):
        batch_delete_jobs(self.jobs.using(using))
        return super().delete(using, *args, **kwargs)
```

- batch-deleting the instance's own `jobs` GenericRelation *before* calling
`super().delete()`, which is where Django's `pre_delete` signal fires. Both
`ForwardSync` and `ForwardIngestion` are `JobsMixin`, and each has a
`pre_delete` receiver (`cancel_enqueued_jobs_on_sync_delete`,
`refuse_ingestion_delete_with_live_baseline`) that raises `ProtectedError`
when a bound `Job` is still `RUNNING` - by the time either fired, on 4.6.10,
the running job's row was already gone, so a sync or ingestion could be
deleted right out from under an in-progress RQ worker, exactly the failure
mode the signal's own docstring exists to prevent.

Django's `QuerySet.delete()` (bulk delete) never calls an instance's
`delete()` method - only the Collector, which still dispatches `pre_delete`
- so the existing signals remain correct and sufficient for
`ForwardSync.objects.filter(...).delete()`. The gap is specifically the
single-instance `sync.delete()` / `ingestion.delete()` path, where
`JobsMixin.delete()` now runs its batch-clear before anything else.

**Fix**: extracted each signal's guard body into a plain function
(`protect_sync_from_deletion_while_jobs_active`,
`protect_ingestion_from_deletion_while_live_or_running`), called from both
the unchanged `pre_delete` receiver (bulk path) and a new `delete()`
override on each model that runs the guard *first*, then calls
`super().delete(*args, **kwargs)` - which is what reaches `JobsMixin.delete()`
and its batching, now safely after the running-job check has already had a
chance to see the jobs. Both overrides wrap the guard + `super().delete()`
call in `transaction.atomic()`, matching `JobsMixin.delete()`'s own pattern.

## Rollback

Revert the commit; no schema, no migration.

## Decision Log

- Bumped straight to `4.6.10` (latest `4.6.x` patch) rather than `4.6.9`,
  since both are available and `4.6.10` is the newer patch in the same
  supported line.
- Fixed the delete-protection regression in this same branch/PR rather than
  splitting it out: the chore alone is unsafe to ship (it silently reopens a
  data-loss hole), so the two are causally inseparable even though they
  touch different files.
- Kept both the `pre_delete` signal and the new `delete()` override rather
  than replacing the signal: `QuerySet.delete()` bypasses the override
  entirely, so removing the signal would reopen the bulk-delete path this
  plugin has protected since the signal was first added.
- Extracted the guard bodies into plain functions instead of duplicating
  them: this project's memory explicitly warns that this exact class of
  all-or-nothing guard has shipped broken-in-one-branch-only before
  ([[ambiguous-name-hold-not-refuse]]) - one function, two call sites, is
  the version that can't drift apart again.
