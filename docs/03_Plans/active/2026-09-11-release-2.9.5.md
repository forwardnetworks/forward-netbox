# 2.9.5: the numbers an operator reads are current, honest, and actionable

## Context

A customer upgraded to 2.9.4, ran a sync, and reported two things. Both show
2.9.4 working - cause badges, the quarantine split, the "why? / clean up"
links, the new Blocking column - and both show something wrong that 2.9.4 made
visible:

- The Ingestion Issues table labels an `ipam.ipaddress` row red **Blocking**
  while the row's own message says the baseline was promoted over it.
- The uncovered-device count read the same number for days across several
  syncs, which reads as "the sync is still creating uncovered devices".

These are two structural gaps and one policy inconsistency, and the two
recurring ingestion issues are **downstream of the uncovered-device backlog
itself**.

**Why the numbers never move.** The panel renders a cached job payload that
only the Refresh button produces (`views.py`, name filter
`"scope reconciliation"`). Nothing enqueues it after a sync. The job that
*does* run after every sync (`DeviceScopeTagReconciliationJob`) records
absence streaks but stores nothing the panel reads. "Identical for days" means
nobody clicked Refresh - not that the sync is creating anything. The prune
button would also delete 0 regardless: uncovered-device absence streaks only
started existing in 2.9.3, the default quarantine is 3 runs and 72 hours, and
the uncovered card never says so. The orphan card has that sentence; the
uncovered card does not.

**Why the label lies.** The message "Recorded and skipped ... the baseline was
promoted over this row" is written **per row, at record time**, from the
exception class alone (`merge.py`) - a promise about the future.
`baseline_ready` is set **per ingestion**, much later, only if the merge ends
with zero retryable failures (`ingestion_merge.py`). One skipped row plus one
retryable failure anywhere in the run means `ForwardPartialMergeError` raises
first, `baseline_ready` stays False, and every row in the run is labelled by
the worst row. The classifier that knows the row was skipped
(`_is_destination_rule_rejection`) is evaluated twice and thrown away both
times; `raw_data` carries no disposition. `health_checks.py` has the same
defect in miniature: `ingestion_check_status` and `ingestion_check_message`
order their checks differently.

**Why the two issues recur, and what they have in common.**

- `dcim.devicetype` "still-referenced-by-device": a *rename* in Forward. The
  superseded diff row emits a delete of the old type
  (`sync_runner_contracts.py`, exempt from the removal allowlist); devices
  still point at it; the delete is refused and - by design - **retried every
  run** (`record_refused_delete`, `_without_refused_deletes`). The
  schema-driven PROTECT hold-back (`workload_state.py
  _reference_protected_pks`) covers three models and not this one. The devices
  holding the old type are, almost certainly, devices Forward no longer
  reports - the uncovered/orphan set.
- `ipam.ipaddress` "primary-ip-reassignment-blocked": the holder device
  carries no identity from this sync, so the release is correctly refused
  (`sync_ipam.py`) - but the move is staged anyway, the merge rejects it, and
  the row recurs once per run, structurally. The remedy is logged as a staging
  warning with a *count* and never reaches the issue row; the holder is never
  identified. A device this sync does not own but whose address it manages is,
  again, almost certainly an uncovered/orphan device.

So the convergence story for both issues is the same: prune the uncovered set
and they clear. Which is blocked on the quarantine, which the panel does not
explain, on a number that never refreshes.

**One policy inconsistency.** `prune_orphan_devices` partitions *all*
out-of-scope pks by quarantine with no cause gate, so devices Forward still
reports are prune-eligible. The uncovered prune gates on `kind == "absent"`
only. Two destructive buttons, same cause, opposite rules. **Decided: align
the orphan prune to absent-only.**

**A latent hazard the census has.** `_absence_kinds` probes `network.devices`
only. An SNMP-endpoint device that drops out of endpoint scope is classified
`absent` - "gone from Forward" - though Forward still has it in
`network.endpoints`, and it would become a prune candidate after quarantine.
Reporting deployments have hundreds of endpoint devices.

## Goal

After 2.9.5, on the page the operator is already looking at:

1. The numbers are current after every sync, without a click.
2. The uncovered card says how many are eligible *now*, how many are held and
   why, and the button is disabled when it would delete nothing.
3. A trend badge answers "growing or static" from the page.
4. An uncovered device can be removed from its own page, through the same
   gates as the whole-set prune.
5. An issue row's label is derived from what that row did, and can never
   contradict its own message.
6. The two recurring issues either converge or say exactly what will make them.
7. No prune deletes a device Forward still reports, on either button.

## Constraints

- 2.9.x lane: NetBox 4.6.x, `netbox_branching` 1.1.3, no optional plugin
  installable on 4.7. Written here first, then forward-ported to `main`.
- No new model, no migration, no `urls.py` change: `@register_model_view` on
  `ForwardSync` is the whole routing surface for the new views.
- No new deletion path. Every prune goes through `enqueue_button_job` and the
  existing `PruneUncoveredDevicesJob` / `prune_orphan_devices` gates; a
  per-device remedy narrows an allowlist, it never widens one.
- No upstream plugin changes and no plugin version bumps: `netbox-routing`
  0.4.3 and `netbox-cisco-aci` 0.4.0 stay pinned exactly as they are.
- NQE call budget: no change to the per-sync census count; live validation is
  a bounded number of executions recorded in `forward_api_usage`.
- Live network and snapshot identifiers, customer names and device names
  appear in no committed file; captured config excerpts are sanitised syntax
  examples, never inventory.

## Approach

## Changes

### 1. The panel refreshes itself after every completed sync - zero NQE delta

`tag_backfilled_devices` calls `compute_scope_reconciliation` itself when
handed no report, and the post-sync `_reconcile_forward_device_scope_tags_work`
hands it none. So every completed sync **already runs both NQE queries and the
census** and stores only tag counts. This is a storage/lookup fix. Do **not**
chain `ScopeReconciliationJob` - that doubles the census.

- `jobs.py`: compute once, pass `report=` into `tag_backfilled_devices`, and
  persist `tag_result["scope_reconciliation"] = public_scope_report(report)`
  plus `total_owned_prune_candidates`. New `public_scope_report()` in
  `scope_reconciliation.py` (the non-`_` keys, `json_safe_value`'d); the
  Refresh job's `_scope_reconciliation_work` uses it too. The
  `StalePostSyncSnapshotError` exit stores nothing - a stale report must not
  become "current".
- Persist `unmanaged["owned_absent_device_ids"]` so item 3 can gate without a
  census.
- Accept both producers when finding the latest report - name contains
  `"scope reconciliation"`, or contains `"reconcile device scope tags"` and
  the data has the `scope_reconciliation` key - ordered by `-completed`, not
  `-created`. The lookup lives in `scope_reconciliation.py` as
  `latest_scope_report(sync)` so `template_content.py` never imports `views`.
  Render "Last updated by <job> at <completed>, snapshot <id>" on the card.
- Trend: `total_uncovered` and `total_out_of_scope` are **already** in the tag
  job's data; add `total_owned_prune_candidates`. `_job_data_count_trend(sync,
  key)` works unchanged and, because it filters `data__has_key`,
  Refresh-button jobs never pollute the pair.

### 2. The uncovered card is honest about the quarantine

- Add the orphan card's sentence to the uncovered card: an absence must persist
  for N consecutive syncs and H hours.
- The button counts `owned_quarantine.prune_eligible`, not
  `owned_prune_candidates`, and is `disabled` when eligible is 0. Text becomes
  "Delete N eligible now" with a muted "M held by the quarantine" beside it,
  so a large "Delete N" never appears when the answer is 0.
- Trend badge on the "created by this sync" summary row, and the same on the
  orphan row.
- Render the report's `generated_at` next to the card title, so "this is from
  three days ago" is on the page rather than inferred.

### 3. Per-device uncovered remedy on the device page

**Sync-scoped, same job, no new deletion path.** Every destructive button in
the repo is `ForwardSync`-scoped through `enqueue_button_job`; a view on
`dcim.Device` would be the first exception and would put a Forward URL under
`/dcim/devices/`. So:

- `views.py`: `@register_model_view(ForwardSync, "prune_uncovered_device",
  path="prune-uncovered/device")`, permission `dcim.delete_device`, POST with
  `device=<pk>` and optional `include_quarantined`; enqueues kind
  `"prune_uncovered"` with `job_kwargs={"restrict_to_device_pks": [pk], ...}`.
  Same overlap guard, same `JobBlockedBySyncRun`, same job name - a bulk prune
  in flight blocks the single one, correctly. GET redirects to the panel.
- `jobs.py`: `PruneUncoveredDevicesJob.run` forwards `restrict_to_device_pks`
  only when supplied; job.data gains `restricted_to_device_pks` and
  `refused_device_pks_by_reason`.
- `prune_uncovered_devices(..., restrict_to_device_pks=None)`: the allowlist is
  the **intersection** of the caller's set with what the bulk prune would
  already delete. Each requested pk lands in exactly one of
  `refused["not_owned"]`, `refused["not_absent"]`, `refused["held"]`, or the
  eligible set. Shrink guards are computed over the **full** absent set before
  the restriction - deleting one device can never trip them, and must still be
  refused if the full picture says the scope collapsed. `restricted_refusals`
  is added to `_prune_result` on every exit.
- `template_content.py` `ForwardDeviceOwnershipPanel`: offer the form only when
  the device has an identity from exactly **one** sync, is in that sync's
  latest report's `owned_absent_device_ids`, and has no foreign delete blocker.
  When held, render the checkbox and the quarantine sentence. When uncovered
  but Forward still reports it, render the explanation instead of a button.

Negative space pinned in `RestrictedPruneAllowlistTest`: not owned, `untagged`,
`vendor_excluded`, held-without-override each refused and named; override
deletes only the named device while a second held device survives; restriction
never widens; the shrink guard still applies to a single device. Plus the
view's 403 without permission and the running-sync block.

### 4. Row-level disposition that cannot contradict the message

- `merge.py`: persist `raw_data["disposition"]` as `"skipped"` or `"failed"`
  from the one `_is_destination_rule_rejection` result. The message states what
  happened, not what will: "Recorded and skipped: re-running cannot change a
  NetBox validation rejection." Drop "so the baseline was promoted over this
  row" - that is the ingestion's fact and the ingestion's status line already
  says it.
- `_MergeIssueRecorder.record` classifies **once**, returns the result, and
  `_record_failed` uses it, removing the duplicate call.
  `sync_reporting.record_issue` gains `disposition=None`, written into
  `raw_data` only when supplied (item 5 uses it).
- `ingestion_issues.py`: `row_disposition(issue)` reads
  `raw_data["disposition"]`. `issue_blocking_disposition` becomes four-valued:
  `none` | `blocking` | `skipped` | `promoted_over`. A `"skipped"` row is
  `promoted_over` when the ingestion promoted, else `skipped`; a `"failed"` or
  legacy row keeps today's `baseline_ready` behaviour. `tables.py` gets the
  `Skipped` branch.
- `filtersets.py`: `blocking_issue_q() & Q(ingestion__baseline_ready=False)`
  and a **NULL-safe** negation of the disposition -
  `~Q(raw_data__has_key="disposition") | ~Q(raw_data__disposition="skipped")`.
  A bare `~Q(raw_data__disposition="skipped")` drops every legacy row, because
  a missing JSONB key compares as NULL and `NOT NULL` is NULL, not true.
- `health_checks.py`: one `ingestion_check_verdict(ingestion)` in the order
  missing -> catch-up states -> failed -> skipped -> blocking -> ready ->
  non-blocking -> not ready; `ingestion_check_status` and
  `ingestion_check_message` both render from that verdict. `ready` sits above
  `nonblocking` deliberately: a promoted ingestion with non-blocking issues is
  a `pass` that still names its issues, which is existing pinned behaviour.
- Test: a real mixed merge - one destination-rule rejection plus one retryable
  failure - asserting the skipped row is never `blocking` and the failed row
  is. This is the case that is untested today.

### 5. The two recurring issues converge, or say what will make them

**devicetype / protected delete.** Extend `_reference_protected_pks` to cover
every superseded-rename delete, not just three named models, so a delete the
database will refuse is *held back* with a named reason instead of retried
every run. The held-back warning names the count of referencing devices and how
many of those are in the sync's uncovered/orphan set, with a link to the list,
so the operator sees "clears itself once those are pruned" rather than a
failure. Reuse the existing hold-back warning.

**primary-IP / unowned holder.** Split the classifier from the mutation in
`sync_ipam.py`: new `primary_ip_holder_release_plan(runner, ip, *,
destination_device_id) -> {"releases", "unowned_holder_ids", "evaluated"}`;
`release_owned_primary_ip_claims` becomes `plan["releases"]` so the bulk path
and its tests are untouched. At both call sites, and **only when the assignment
fields are among the changed fields** (a status-only update must not be
skipped): if `unowned_holder_ids` is non-empty, do not stage; call new
`record_unowned_primary_ip_holder_skip(runner, ip_pk=, holder_pks=,
destination_device_pk=)` which (a) records the aggregated skip warning under
new reason `primary-ip-held-by-unowned-device`, added to the rollup reasons
with a template so a fleet collapses to one line, and (b) records **one**
sync-phase issue per ip per run with `disposition="skipped"` and
`holder_device_pks` in context - pks, never names. Delete the count-only
warning.

**The regression trap, stated precisely:** the skip keys on
`unowned_holder_ids`, **never** on `releases == []` - empty releases also means
"no holders at all" and "scope context missing". The scope-missing exit returns
`evaluated=False` with an empty unowned list so it keeps today's behaviour
(stage, merge rejects) rather than silently skipping every reassignment.
`test_an_owned_holder_that_left_scope_is_still_released` must pass unchanged.

### 6. The orphan prune gates on cause, like the uncovered prune

`prune_orphan_devices`: require the census (else `ScopeCensusUnavailableError`,
mirroring the uncovered prune), then keep only pks whose kind is `absent`
before `partition_quarantined_orphans`, using the existing name-to-pk
resolution rather than re-matching names at delete time. The orphan button
counts `out_of_scope_absence.absent_from_snapshot`. Tests: `untagged` orphan
never pruned; `vendor_excluded` never pruned; missing census refuses the prune;
and the existing scope-UI prune test, which currently passes with a fixture
that omits the census.

### 7. The census sees endpoints

`_absence_kinds`: when `sync_endpoints` is on, also probe `network.endpoints`
for the names, so an endpoint device Forward still has is `untagged`, not
`absent`. This is what stops items 6 and 3 from deleting a live endpoint device
after quarantine. Same census call budget: one query per table, names batched
as today.

**Field report while building this (2026-09-11):** 189 of a deployment's
550 uncovered devices are console servers and SNMP endpoints. On that
org's live endpoint table, 658 endpoints all carry SNMP output: 435 are
console servers (432 tagged in Forward), 84 are CIMC controllers, 139 are
generic. So the badge "in Forward but untagged" was covering two opposite
situations: a console server whose *endpoint* tags were never added to the
include set (fix the scope), and a generic endpoint or CIMC controller the
endpoint scope excludes by design (nothing to fix). Built: the endpoint half
of the census now classifies each such device by the endpoint-scope rule
that excludes it - `endpoint_scope_off`, `endpoint_no_snmp`,
`endpoint_cimc`, `endpoint_generic`, `endpoint_untagged`,
`endpoint_in_scope` - the uncovered card breaks the untagged count down by
that reason, and the device page names the reason and its remedy. The
three-valued `kinds` the prunes gate on is unchanged. The endpoint half now
runs whether or not endpoint sync is on: turning it off is exactly the
moment every endpoint-derived device would otherwise become `absent` and
prunable, which is one more census query per report and the price of
`absent` meaning what the prune assumes.

Also fixed on the way: `prune_uncovered_devices` still had one exit - a
sync with no absent device at all - that returned before classifying a
restricted request, so a device Forward still reports was refused with no
reason recorded.

### 8. Support bundle

The stored report now carries the trend keys and `generated_at`, so
`scope_reconciliation` in the bundle gains them for free. Add `disposition`
and the row disposition to the exported issue rows.

### 9. Routing policy: route-maps, prefix-lists, community-lists

**Destination: not the blocker.** `netbox-routing` 0.4.3 is both our pin and
the latest release, and it already models everything asked for:
`RouteMap`/`RouteMapEntry`, `PrefixList`/`PrefixListEntry`,
`CommunityList`/`CommunityListEntry`/`Community`, `ASPath`/`ASPathEntry`. No
version bump, no upstream change.

**Source: confirmed by live probe against a validation org, not the local
schema dump.** Every candidate normalized path fails at NQE compile time with
`Record does not have field`: nothing on `Device` (its 23 fields include
`bgpRib`, `files`, `networkInstances`, `aclEntries`, `securityPolicy` - no
policy objects), nothing on `BgpNeighbor`, and on the RIB path
`bgpRib.afiSafis[].neighbors[].adjRibInPost.routes[].pathAttributes` only
`asPath` exists - no communities of any width. `device.files.config` is present
(control probe passed). **So this is a config-derived NQE layer with per-vendor
parse contracts over `device.files.config`** - a new capability class.

**Vendor scope, from the validation-org device census** (roughly 5,200 devices,
4,800 completed): Cisco IOS-XE and NX-OS dominate, then Arista EOS, then IOS,
with a handful of IOS-XR. PAN-OS, Fortinet and F5 are firewalls/ADCs and out of
scope for BGP policy. First pass: **IOS/IOS-XE, NX-OS, EOS** - IOS-like syntax
throughout, one parse contract with two dialect tables. IOS-XR deferred.

**Two destination facts found while building it, and what was decided.**

1. **netbox-routing names policy objects globally.** `PrefixList.name`,
   `CommunityList.name` and `RouteMap.name` are each unique
   (case-insensitively) and carry no device. A live census of the validation
   org (about 45,000 policy lines over four dialects) found roughly a third
   of names defined *differently* on different devices - 263 of 732
   prefix-lists, 258 of 876 route-maps, 165 of 359 community-lists - and the
   differences are mostly disjoint, not near-copies. Collapsing by name with
   a deterministic winner would silently drop 53% of route-map entries and
   86% of community-list entries. **Decided (revised on review, to stay
   closest to netbox-routing's global catalogue): the query itself builds a
   catalogue.** Per configured name, every device's definition is grouped by
   content (NQE `group ... by` on the entry list); the definition shared by
   the most devices owns the bare name, and each other definition is stored
   as `<name>@<lowest device holding it>`, with the device count and a
   representative device in the description. Shared policy appears once under
   its real name - the netbox-routing shape - and nothing is dropped. Live:
   798 route-map names become 1,439 objects (641 variants), community lists
   2,577 objects, prefix lists ~1,071. Rows are global, not device-owned
   (ownership mode `global`, sharded by `name`), so a diff run re-derives the
   catalogue from the query's own delta rather than from one device's rows.
2. **The plugin's own validation rejects common entries.**
   `PrefixListEntry.clean()` in 0.4.3 raises when `ge < le` - the normal
   `ge 24 le 32` form - and when any bound is not longer than the prefix.
   The merge runs `full_clean`, so those rows would be rejected on every
   run. **Decided:** the adapter predicts the rejection, stores the entry
   without bounds, keeps the verbatim modifiers in the entry's description,
   and rolls the count into one warning. `eq N` is stored as `ge N le N`,
   which the plugin accepts. Worth an upstream report, not an upstream
   dependency.

**Depth (decided, revised):** names, sequences, actions, prefixes (as
`CustomPrefix` rows), numeric communities (as `Community` rows, shared
fleet-wide by value), and the route-map `match` / `set` clauses as the
entry's JSON fields keyed by clause head (`ip_address_prefix_list`,
`community_exact_match`, `as_path_prepend`, ...), `continue` as
`flow_control`, `description` as the description. The many-to-many links
(`match_prefix_list`, `match_community_list`) are **not** written: the
staging engine stages concrete fields only, and the JSON carries the
referenced names verbatim. Expanded (regex) community lists and well-known
community names have no numeric destination and are recorded and skipped.

**Shape.** Three new bundled queries - `forward_routing_prefix_lists.nqe`,
`forward_routing_community_lists.nqe`, `forward_routing_route_maps.nqe` -
each walking `device.files.config` (a `ConfigLine` tree: `text`, `children`,
`lineNumber`), emitting one row per entry. All three were run against the
validation org before being committed: flat `seq` lines (IOS / IOS-XE /
NX-OS) and nested `seq` children (EOS) both resolve, `ge` / `le` / `eq`
modifiers parse, and route-map stanzas carry their child clauses. Parsing of
the header is in NQE (`regexMatches` with typed groups); clause-to-JSON is in
Python (`sync_routing_policy.py`) where it is unit-tested against captured
syntax examples. Each map carries `forward_netbox_shard_keys`, joins
`_TIER2_DEVICE_OWNED_QUERY_FILENAMES`, and needs no alias variant: the
alias rule keys on `device_type` / `platform` identities, which these rows
never carry. Seeded **disabled**.

The adapter is registered at every site the plan listed plus a lookup-cache
primer (`_prime_routing_policy_identity_cache`) so a converged fleet does not
pay one query per list on every run, a migration for the NQE-map model
choices, and fast-baseline allowlisting so enabling the maps does not turn
the fast baseline off. Delete ordering: entries, then their empty parent.

**Customer-side obligation, release note, not code:** every org-backed customer
must run *Publish Bundled Queries* once after upgrade, or the three new maps
resolve to nothing.

### 10. Git / config backup: an operator trigger, and the untested half

**What exists.** `run_config_backup` fetches a git `core.DataSource`, pages
`forward_config_backup.nqe`, writes `configs/<netbox-name>.cfg` (opt-in
`unmanaged/<forward-name>.cfg`), commits once, pushes, then best-effort
`data_source.sync()`. It runs **only** as a post-sync overlay, with no button
and no `BUTTON_JOB_SPECS` entry. The git layer is **not** mocked:
`test_config_backup.py` pushes to a real local bare repo via dulwich, and the
Validity test is a genuine cross-plugin round-trip.

**Four gaps:**

- **No operator trigger.** An operator cannot run a backup on demand, cannot
  verify the feature without a whole sync, and the health check only says
  "last_synced is set". Add `config_backup` to `BUTTON_JOB_SPECS` (permission
  `forward_netbox.run_forwardsync`), a POST view and a button on the sync page
  gated on the data source being configured, through the standard
  `enqueue_button_job` pipeline. This is the no-CLI rule applied to a feature
  that shipped without a surface, and it is what makes the rest testable.
- **The credentialed path is untested.** `_authenticated_url` embeds
  `DataSource` username/password into HTTP(S) URLs; nothing tests URL-encoding
  of special characters, the existing-`@` strip, ssh passthrough, or - the one
  that matters - that the assembled URL never leaks into a `ForwardSyncError`
  message or `job.data`. Unit-test it with no server first. Then add a
  git-over-HTTP remote with auth to `development/docker-compose.yml` (fixture
  credentials in `development/secrets/`) and one test each for a successful
  authenticated push, a 401, and a non-fast-forward push - pinning the error
  wording and the no-secret property.
- **Job and health layers have zero tests.** The enqueue gating (status,
  snapshot, parameter, duplicate-name guard), the work function (job-data
  overlay, stale-snapshot exit, redaction - config text never reaches
  `job.data` or logs), and all five warn branches of the delivery check
  including the JSON int-vs-str tenant binding quirk.
- **The Validity round-trip can vanish silently.** It `skipTest`s when
  `validity` is absent and nothing asserts it ran. Add a guard that fails if
  the integration is registered but the e2e test skipped, and widen the
  scenario: tenant `data_source` binding, a non-default `device_config_path`
  template, and the `unmanaged/` prefix.

**Built (2.9.5):** the git-over-HTTP remote is an in-process dulwich smart-HTTP
server with basic auth (`_GitHttpRemote` in `test_config_backup.py`) rather than

### 11. ACI validated against a real fabric

**What exists.** Eight models (`acifabric, acipod, acinode, acitenant, acivrf,
acibridgedomain, acifilter, acil3out`) plus a native `dcim.inventoryitem` for
APIC CIMC, fed by ten queries, all seeded disabled. **Every ACI query is regex
over raw command text** - there is no structured ACI model in NQE. No variant
gap: the only ACI-relevant opt-in is platform derivation, and both
`forward_devices` variants use the same `normalizeDevicePlatformName`.

**Why a live run is the test.** `test_sync_aci.py` proves the adapter given
well-formed rows; `test_query_registry.py` proves the `.nqe` files contain
certain strings. **No test executes any ACI regex against any command text, and
no captured command output exists in the repo** - the two fixtures are
synthetic contract manifests. A field-order change or an APIC version whose
output differs yields zero rows and a green CI.

**Probe results against a real fabric (2026-09-11).** Read-only, bounded: five
NQE executions, no sync. 56 APIC-platform devices, 55 completed, 36 command

- **Confirmed working.** All four `moquery` matchers hit verbatim as the
  queries write them, non-empty on all 55 completed APICs: tenants/VRFs

  inventory (`eqptch*`).
- **Finding 1 - `eqptCh` is present on COMPLETED APICs here.** The 2026-06-17
  plan recorded it as appearing only on backfilled snapshots, which is why
  `forward_apic_cimc_readiness_audit` exists. On this fabric it is collected on
  all 55 completed devices with non-empty output, so CIMC inventory should
  populate and that historical caveat does not apply here. The audit stays - it
  is still the right check for a fabric that lacks it - but its docs should stop
  implying the backfilled case is the norm.
- **Finding 2 (corrected) - every ACI map has source data, on two sides
  of the fabric.** A first probe scoped to APIC-platform devices found no

  APIC-side set. And a readiness diagnostic: when an enabled ACI map returns
  zero rows, one bounded NQE run reports whether its source command is

### 12. The drift comparison's query explosion

A reported comparison: 766,460 ms for 663,696 rows in 261,148 queries (449,355
ms of it in SQL), and `ipam.vlan` alone 239,755 ms across 102,334 queries -
while the per-model table reports `ipam.vlan` as 7,902 Forward rows, 0
candidates, **In sync: Yes**. A fully converged model is costing about 13
queries per row. 2.8.7 fixed this class for the dependency preview by priming
caches (15 queries to 3, flat); the drift comparison path does not prime for
`ipam.vlan`.

**Cause found (by tracing the query, not by reading the code):** the
simple-model bulk path fetches existing rows per lookup field (`site__in`,
`vid__in`) without joining the FK, and the lookup key then reads `vlan.site`
on each object - one `dcim_site WHERE id = N` per existing row per lookup
field. Priming was never the issue on this path; 2.8.7's fix covered the
adapter models. Both bulk fetches now `select_related` the FK fields their
keys read, the VLAN pair primer joins the site for the adapter path, and
`ipam.prefix` (which has no primer of its own) primes its sites.
`SiteBearingModelsArePrimedTest` pins that a converged comparison issues no
per-row site reload and that five times the rows cost the same query count. A
first version of this fix asserted the wrong cause and its own tests failed in
CI; recorded so the next reader traces before fixing.

### 13. Models reporting "Not measured"

`dcim.platform`, `dcim.devicerole` and three `dcim.inventoryitem` map variants.
Two of the inventoryitem ones are `unsafe_contributor_reduction` / full-only
**by design**, so "Not measured" is correct for them - but it reads identically
to a defect, which is the same complaint 2.8.3 fixed for the estate-wide
verdict. Make the badge distinguish "excluded by design, here is why" from
"could not be compared", via `_unavailable_reason(result)` and a
`comparison_unavailable_reason` row key fed by
`query_diff_ownership_mode_for_name`.

`dcim.platform` and `dcim.devicerole` were unmeasured for a third reason,
found in `bulk_orm_apply_simple_models`: these low-volume models keep the
adapter-equivalent tree save path, which has no preview mode, so a preview
returned no comparison for them. **Fixed in this release:** both are now
measured through the adapter loop. `_ensure_platform` called the module
upsert directly - the one write on that path the preview runner could not
intercept - and now goes through the runner method; its lookup/values plan is
factored out so the preview classifies platforms read-only. Pinned by
`PlatformAndRoleAreMeasuredTest`, including that measuring writes nothing.

## Rollback

Every change is additive at the data layer: `raw_data["disposition"]` and the
stored `scope_reconciliation` job payload are new JSON keys that older code
ignores, and there is no migration. Reverting the release restores the
previous behaviour without data repair. The three new routing maps are seeded
disabled; a customer who published them and reverts sees the org queries
orphaned by the registry audit, which is the existing behaviour for any retired
bundled query.

## Decision Log

- **Convergence over suppression.** Both recurring issues trace to devices the
  sync no longer covers; the fix is to make that visible and let the prune
  clear them, not to hide the rows.
- **Per-device remedy reuses the whole-set job.** A second deletion path is how
  a delete acquires a guard the other lacks. `restrict_to_device_pks` narrows
  the existing job; it cannot widen it.
- **A fourth disposition state exists.** "Skipped, run not yet promoted" is
  real and distinct from both "blocking" and "promoted over"; collapsing it
  into either is the current bug.
- **Endpoint census is a prerequisite for aligning the orphan gate**, not a
  separate nicety: gating on `absent` makes the definition of `absent`
  load-bearing, and today it is wrong for hundreds of endpoint devices.
