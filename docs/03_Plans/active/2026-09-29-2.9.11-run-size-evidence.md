# Say when a run is far larger than normal, and put the evidence in the bundle

## Goal

A customer's first full run after an upgrade staged 147,015 changes, most of
them BGP peers, and merged them because Auto merge was on. NetBox held 16,605
peers and Forward reported about 138k, so the load was correct - but nothing
said so until a person ran a script in a NetBox shell to count rows, list what
recent ingestions had done and check for duplicates. Make the same evidence
part of Health and the support bundle, say plainly when a run is out of
proportion, and let Auto merge stop for review when it is.

This plan covers the evidence and the flags. The merge hold and the
configurable config-backup folder are separate commits under the same tranche.

## Constraints

- Counts, ids, timestamps and statuses only. No names, no configuration text.
- Nothing may make the sync page slower. The sync page builds the health
  summary on every load for its attention banner, so the aggregate queries run
  only for the Health tab and the bundle (`include_evidence=True`).
- Every aggregate runs under a statement timeout in its own savepoint and is
  reported as skipped with the reason when it trips - never silently omitted.
- The learned change density cannot be the norm: it is changes per *written*
  row, so it says how many changes one written row produces and never how many
  rows a run writes. The run this exists for wrote 127k rows at a normal
  density. The norms are the table's own size and what earlier runs applied.
- No migration and no `@query` change. Everything is GUI and bundle; nothing
  asks an operator to run a command.

## Touched Surfaces

- `utilities/run_size_anomaly.py` (new): the rule, pure and stdlib-only.
- `utilities/health_evidence.py` (new): row counts beside Forward's,
  before/after the latest run, duplicate groups, recent ingestions with merge
  facts and merged changes by model and action.
- `utilities/health.py`: `sync_health_summary(include_evidence=)`, and the
  checks `Unusually large run`, `Run held for review`, `Baseline never
  completed` and `NetBox holds far fewer rows than Forward`.
- `utilities/change_explainability.py`: counts by action, model and
  model-by-action over every change instead of the first 5,000.
- `views.py`: the bundle and the Health tab ask for the evidence.
- `templates/forward_netbox/forwardsync_health.html`: two cards.
- Tests for each, using real syncs, ingestions, jobs and rows.

## Approach

1. **Full counts.** `change_explainability` aggregates `ChangeDiff` by object
   type and action over the whole branch. The field detail stays sampled.
2. **The rule.** A model is flagged when its staged changes reach 10,000 and
   are at least 3x the rows NetBox already holds for it (table of at least
   1,000 rows), or at least 10x the median of three or more earlier runs. An
   empty or small table and a model with too little history are never flagged.
3. **Evidence.** Row counts (Forward's from the latest validation run, NetBox's
   from the table, split at the latest ingestion's start by each row's own
   `created`), a duplicate-group count for BGP peers (scope + peer), and for
   the last three ingestions the job and merge status, the job statistics and
   the merged changes over every `ObjectChange` for the ingestion's request id.
4. **The empty `merge_job`.** An Auto merge runs inside the sync job, so
   `merge_job` stays empty for it and a bundle read that as "never merged".
   The payload now carries `merge.mode` (`automatic_inside_sync_job`,
   `queued_merge_job` or `not_merged`) and the merge time and counts.
5. **Flags.** `Unusually large run` (history norm, cheap, shows on the sync
   page), `Baseline never completed` (two finished runs, none promoted), and
   `NetBox holds far fewer rows than Forward` (evidence only, no link).

## Validation

- Targeted Django tests: `test_run_size_anomaly` (the rule's positive and
  negative space), `test_change_explainability_full_counts`,
  `test_health_evidence`.
- The existing Health, log-export and config-backup health tests.
- Full `invoke ci` before merge.

## Rollback

Revert the commit. No migration, no persisted state beyond the job data the
merge hold writes in its own commit.

## Decision Log

- **Not learned density.** See Constraints; the run that motivated this had a
  normal density and an abnormal number of written rows.
- **Evidence only on the Health tab and the bundle.** Live counts on a 144k-row
  table on every sync-page load would be the cost of a banner nobody asked for.
- **The table's own size as a norm.** It needs no history, so it works on the
  first upgrade, and a first load into an empty table is by definition not
  flagged.
