# Record v2.7.10 as unpublished and bump to 2.7.11

## Goal

Move the release forward after `v2.7.10` was tagged and refused, and record that
refusal where the harness and the provenance verifier both read it.

## Constraints

- A tag is immutable under the `version-tag-integrity` ruleset, so `v2.7.10`
  cannot be reclaimed and the version number is spent.
- The four version surfaces move together in one commit; splitting them reverts
  the fast baseline from ~6 min to ~15 h.
- This commit must land as its own reviewed pull request, ahead of the release
  commit. That is the whole reason `v2.7.10` failed.

## Touched Surfaces

- `scripts/check_release_lineage.py` (new), `scripts/tests/test_release_lineage.py`
  (new)
- `scripts/verify_release_provenance.py` - `UNPUBLISHED_RELEASE_TAGS`
- `pyproject.toml`, `forward_netbox/__init__.py`,
  `forward_netbox/utilities/fast_baseline.py`,
  `forward_netbox/tests/test_runtime_dependency_check.py`
- `README.md`, `docs/README.md`, `docs/01_User_Guide/README.md`, `CHANGELOG.md`

## Approach

`v2.7.10` was refused by `_require_prior_release_bridge`, which walks first-parent
from `PRIOR_POST_RELEASE_DOC_COMMIT` to the release commit and requires at least
four commits: the bridge, then a bootstrap/control commit, then the production
and evidence pair. The lineage offered three - bridge, anchor, release - because
the entire tranche was squashed into a single commit, which removed the very
commit the rule requires.

Nothing about the tree was wrong; `691f67a` is on `main` and gated clean. So this
change carries only the version move and the record of the burn, and it lands as
its own pull request. That restores the missing lineage position: the next
release sees bridge, anchor, `691f67a`, this commit, then the release commit.

`UNPUBLISHED_RELEASE_TAGS` gains `v2.7.10` so the harness accepts an anchor on a
tag that published nothing, the same treatment `v2.7.3`, `v2.7.7` and `v2.7.8`
already carry.

`check_release_lineage.py` is the part that matters beyond this release. Every
rule the publish workflow enforces is a rule that costs a version number to
discover, because it only runs once a tag exists and a tag is immutable. The
lineage walk, the bridge's parent and documentation-only shape, the length
floor, the production/release pairing and the release plan are all decidable
from the local clone, so they now run before the tag. Pointed at the commit that
burned `v2.7.10` it prints the same refusal in under a second.

It deliberately does NOT reimplement the two rules that need GitHub - that each
commit arrived through a merged pull request, and that its workflows succeeded.
A second implementation of a security check is a second thing to get wrong, so
the report names them as unverified rather than implying coverage.

## Validation

`scripts/check_harness.py` and `python3 -m unittest discover -s scripts/tests`,
which together cover the anchor rule, the unpublished-tag list, and the
README/CHANGELOG consistency check. The full gate runs against the release tree,
not this one.

## Rollback

Revert. The version returns to 2.7.10, which is unusable, so this would only be
correct as part of abandoning the release.

## Decision Log

- **Bump rather than retry 2.7.10.** The tag cannot be deleted and a tag that
  published nothing must never be promoted, so the number is spent.
- **Land separately rather than fold into the release commit.** Folding is
  precisely what burned `v2.7.10`. The lineage requirement is not incidental -
  it is what makes the production content reviewable independently of the
  evidence that authorizes it.

## Open

- Nothing. The release plan for 2.7.11 carries the gate evidence.
