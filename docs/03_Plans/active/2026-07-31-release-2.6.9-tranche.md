# Release 2.6.9 Tranche

## Goal

Publish. `2.6.7` and `2.6.8` are tagged with no artifact, so PyPI has served
`2.6.6` since this line of work began — every fix in three tranches is reachable
only from GitHub.

## Contract

- `2.6.9` carries the whole of `2.6.7` and `2.6.8`. Neither exists on PyPI, so
  neither appears in the compatibility tables, exactly as `2.6.2` does not.
- No validation gate runs in the tag-triggered publish workflow.
- Upgrade and re-run the sync. No migration, no operator step.

## Constraints

- Do not weaken any fail-closed gate; move it earlier instead.
- Keep diagnostics free of customer data.
- Do not claim `2.6.7` or `2.6.8` shipped.

## Touched Surfaces

Two commits:

- `088641d` — upgrade gate moved to PR CI, PyPI-sourced version resolution,
  merge-message diagnosis, baseline delete confirmation. Plan:
  `2026-07-31-merge-diagnosis-and-release-path.md`.
- `26999a7` — the upgrade gate made runnable: each side of the upgrade builds on
  its own supported runtime. Same plan.
- This release commit — version surfaces and the three compatibility tables.

## Approach

**Why two tags were burned.** `artifact-upgrade-test` was added to `release.yml`
in 2.6.7, where the earliest it can run is after the tag is pushed. It failed on
a tagless checkout, and then — with that fixed — on resolving `2.6.7`, a version
that was tagged but never published, so `pip install forward-netbox==2.6.7` had
nothing to install. `v*` tags cannot be deleted or moved, so each failure
permanently consumed a version.

Both defects were one line long. The placement is what made them cost releases,
and that is what 2.6.9 changes: the gate runs in PR CI, and a harness check
fails closed if it returns to the publish workflow or vanishes from CI.

Moving it then showed the gate was unrunnable in a third way — it built both
sides of the upgrade on the target runtime under one constraints file, which no
available from-version satisfies. Both failures that burned tags were therefore
downstream of a gate that could never have gone green. It now seeds on the
runtime the previous release supported and migrates onto the current one, which
is what an operator actually does, and it has passed.

**The compatibility tables omit both burned versions.** They list what an
operator can install; showing a version with no artifact would misstate that.
The `2.6.9` summary states the gap and carries both tranches' notes.

**One regression caught while staging.** `insert_release_row` copies the support
cell from the current release, so inserting `2.6.9` beneath `2.6.6` silently
reverted the runtime requirement to `4.6.5 required; needs netbox-branching
1.1.1` — dropping the `4.6.x` / `1.1.x` tolerance that 2.6.7 introduced and this
release still provides. Corrected in all three tables. Worth knowing for the
next release inserted after a gap.

reverts independently; no migration or persisted state is involved.

## Decision Log

- 2026-07-31: Released with the `ipam.ipaddress` merge `ValidationError` still
  open. It is not diagnosable without the field names, and those are already
  recorded in the customer's issue record — but only in `raw_data`. Shipping the
  merge-message fix is what makes the *next* occurrence legible in the list, so
  waiting for the diagnosis before shipping the thing that produces it is the
  wrong order.
- 2026-07-31: `2.6.9` rather than `2.7.0`. Nothing here changes the supported
  runtime tuple or adds an on-by-default capability.

- Both failed publishes skipped the publish and GitHub-release jobs, so no
