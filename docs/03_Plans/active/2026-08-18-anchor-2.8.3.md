# Advance the release provenance anchor to 2.8.3

## Goal

Point the provenance anchor at `v2.8.3`, promote it in the compatibility
tables, and make the release after it verifiable despite a bridge commit that
should not have been usable.

## Why

`PRIOR_RELEASE_TAG` and `PRIOR_POST_RELEASE_DOC_COMMIT` define where the
reviewed lineage starts. A stale anchor grows that range on every release until
GitHub expires the oldest checks in it, and the harness fails while the anchor
disagrees with the release the table calls current - which is what forces this
to happen now rather than eventually.

## Constraints

- The anchor tag and the README "Current release" row must name the same
  version, or the harness refuses.
- The bridge commit must be the first commit after the tag, must have the tag
  as its parent, and must be documentation-only.

## Touched Surfaces

- `scripts/verify_release_provenance.py` - anchor pair, and the exception below
- `.github/workflows/release.yml`, `scripts/check_harness.py`,
  `scripts/tests/test_tasks.py` - the tag each pins
- `README.md`, `docs/README.md`, `docs/01_User_Guide/README.md`, `CHANGELOG.md`
- `scripts/tests/test_verify_release_provenance.py` - four new tests

## Approach

### The bridge is not documentation-only, and cannot be fixed

`scripts/release.py` left an unreleased `2.8.4.dev0` bump in the working tree
after `stage_post_release` failed partway, and a `git add -A` swept the four
version surfaces into the bridge commit. The bump was reverted on `main` in the
next commit, so the released version is what `main` carries.

The bridge itself cannot be repaired. The verifier diffs the release tag
against the bridge commit, that diff is immutable, and the bridge is pinned to
the first commit after the tag - so no later commit can reclaim the slot. This
is the same unsatisfiable pairing that made every release after `v2.7.0`
unverifiable and that cost `v2.6.10` and `v2.6.11` before that.

Left alone it blocks `v2.8.4` at publish time, which is the worst moment to
find it: the tag would already exist.

### The exception is declared, keyed by hash, and pinned by tests

`BRIDGE_CONTENT_EXCEPTIONS` maps that one commit hash to those four exact
paths. It excuses nothing else and no other commit, it cannot be inherited by a
future bridge because the key is a hash, and four tests assert its exact
contents, reject globs and directories, and confirm an unlisted commit gets
nothing.

This follows the pattern already in the file: `UNPUBLISHED_RELEASE_TAGS`
excuses an anchor that disagrees with the table, by naming the specific tags and
requiring a reviewed edit to add one. The exception is declared, not inferred.

### A wrong compatibility claim, fixed while promoting

All three tables described `v2.8.3` as tested on NetBox `4.6.6` while the same
row's body said it was tested and validated on `4.6.8`. The 4.6.8 uplift moved
the summary sentence and the thirteen pins but not the table cell, so the row
contradicted itself in the release that shipped it. `4.6.8` is what every gate
ran on.

## Validation

`check_harness.py`, the harness suite including the four new tests, and
`_require_prior_release_bridge` exercised directly against the real commit
rather than trusted to be right by reading.

## Rollback

Revert. The anchor returns to `v2.8.2`, the harness fails on the promoted
table, and `v2.8.4` cannot be verified.

## Decision Log

- **Fix it now, not at the next tag.** The failure is deterministic and already
  determined. Discovering it during a release means discovering it after the
  tag exists, which is how versions get burned.
- **Excuse by hash, not by widening the rule.** Widening
  `_is_documentation_path` would let every future bridge carry plugin code,
  which is the thing the rule exists to prevent. A hash key expires naturally:
  the next bridge is a different commit and gets no exception.
- **Do not rewrite history to clean the bridge.** Force-pushing `main` strips
  pull-request association by SHA and the verifier then refuses those commits
  permanently. That was done for `v2.7.7` and cost `v2.7.8`.

## Open

- The `.dev0` contradiction that produced this. `--open-next` exists to put
  `.dev0` on `main` and the operating rule says it must never be there; until
  one of them goes, the next release can repeat this.
- `stage_post_release` leaves edits in the working tree when it fails partway.
  A failed stage should leave nothing behind, or the next `git add` inherits it.
