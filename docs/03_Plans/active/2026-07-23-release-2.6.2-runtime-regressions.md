# 2.6.2 Runtime Regression Correction

## Goal

Ship a corrective release whose installed wheel renders every plugin menu/list
route under the supported NetBox 4.6.5 and Branching 1.1.1 runtime, and resolve
the reported post-upgrade sync failure from exported job evidence rather than
from the outer `ForwardSyncError`.

## Constraints

- Preserve ingestion records as durable, non-deletable operational evidence.
- Keep NetBox 4.6.5 and `netbox-branching` 1.1.1 as the exact release runtime.
- Do not infer the ingestion root cause from a screenshot that contains only
  the outer exception type.
- Do not publish a replacement release until the full repository gate and
  installed-wheel runtime checks pass.
- Do not include customer identifiers, URLs, credentials, or screenshots in
  committed tests or documentation.

## Sync Failure Findings

- The query-path exceptions do not propagate out of workload planning.
  `_resolve_specs_for_models()` catches every non-`JobTimeoutException` and
  stores it in `spec_errors`; `_build_workload_jobs()` converts each entry into
  one `ForwardModelResult` with `failure_count=1`, `row_count=0`, and
  `sync_mode="planning"`. `fetch_workloads()` retains those failure results
  while returning any workloads that did resolve.
- The observed outer failure is the validation boundary. After
  `fetch_workloads()`, `ForwardSingleBranchExecutor.run()` records
  `last_model_results` and calls `record_plan_validation()`. That method saves a
  blocked validation run and raises `ForwardSyncError` when `_blocking_reasons()`
  returns any reason. This matches the last exported log line and proves the
  run stopped before ingestion branch provisioning.
- Policy detail for the reported post-upgrade sync failure is unavailable.
  Without a matching force override, required dependency coverage blocks even
  when the policy is absent or disabled: a failed `dcim.device` blocks enabled
  child models, and failed `dcim.platform`/`dcim.devicetype` blocks an enabled
  `dcim.device`. An enabled policy can additionally block any failure through
  `block_on_query_errors` or all zero-result enabled models through
  `block_on_zero_rows`. The exported evidence proves one of these validation
  branches fired, but does not identify which blocking reason because the
  validation policy/run details were absent.
- A legacy built-in map becomes a `QuerySpec` with `query_repository`,
  `query_path`, and optional `commit_id`. For an unpinned/head path,
  `resolve_query_specs_for_client()` performs a read-only root repository index
  lookup, then tries exact path and unique unchanged filename. Before this fix,
  a query whose org path and filename both changed fell through to
  `get_committed_nqe_query()` using the obsolete stored path.
- A missing obsolete path normally raises `ForwardClientError`: non-transient
  HTTP failures are translated at the Forward client request boundary, and a
  repository response whose `queries` list omits the requested path raises the
  same type. Transport/timeouts and exhausted transient HTTP responses can
  instead raise `ForwardConnectivityError`, a `ForwardClientError` subclass.
  The exact type for the 11 query-spec failures associated with the reported
  post-upgrade sync failure cannot be recovered from the old bundle because it
  was swallowed before type-only logging; map construction and
  duplicate-contract errors are also possible at that catch boundary.

## Sync Fix Decision

- Preserve validation behavior. Do not allow an unresolved required map to
  continue merely because it is legacy; that would weaken dependency coverage
  and could stage a partial branch.
- For built-in legacy path specs, carry the bundled NQE `@intent` into the
  runtime spec. Use one read-only root repository index per repository to try
  exact path, then the existing unique unchanged-filename match, then exactly
  one query with that intent. Filename evidence must retain precedence over
  intent so the correction does not replace a previously resolvable binding
  with a different stale-intent query. When duplicate intent or filename
  candidates exist, accept exactly one candidate only when it preserves the
  complete stored path as a suffix under a relocated parent. Execute the
  resolved query ID and preserve an explicit commit pin; otherwise use the
  indexed current commit. Retain the obsolete-path API fallback. Ambiguous
  matches are not guessed and still become real query failures subject to
  normal validation.
- A relocated legacy query may predate a new plugin-supplied parameter. If the
  first read-only execution rejects parameters, retry once without parameters
  only when the spec was resolved from `query_path` and every supplied value is
  an unchanged, known-safe default. Operator-selected or scoped nondefault
  values never take this fallback.
- This performs no Forward repository write and does not persistently rebind
  the map. It changes only runtime resolution, so branch-native planning,
  validation evidence, ingestion evidence, and merge behavior remain intact.
- Record every collected spec-resolution exception using
  `safe_operation_failure()` at info level so the support-bundle sanitizer
  retains the model contract and exception class but never the exception
  message. Export a strict type-only summary of `Job.error`; unsafe or
  non-canonical historical job errors remain redacted.

## NQE Call-Efficiency Decision

- The previous `1.0`-second async poll default was a ceiling, not a fixed
  interval. Polling started at `0.1`, `0.2`, `0.4`, and `0.8` seconds, then
  plateaued at one request per second for every slow query.
- Raise the default ceiling to `5.0` seconds. Fast queries retain the same
  initial checks; slow queries continue through `1.6` and `3.2` seconds before
  plateauing at five seconds. The setting remains source-overridable.
- At `1200` polls, the default poll-count envelope is approximately `99.6`
  minutes. The independent per-workload deadline is still checked on every
  polling loop and remains the authoritative optional wall-clock guard.
- Reuse one repository query index per repository and operation. At `32` maps,
  read-only resolution falls from `32` index method calls to `1` for one
  repository, removing `31`; live direct-ID drift falls from `64` calls to `2`
  because it checks the org and system repositories, removing `62`. Bulk
  unpinned-path drift reuses the same operation index when resolving committed
  metadata.
- This changes metadata/status request cadence only. The resolver and drift
  tests assert that they execute `0` NQE queries and `0` NQE diffs.

The adjacent call-path audit found no unintended duplicate normal-ingestion
execution. The single-branch executor calls `fetch_workloads()` once with
diagnostics disabled. Finalized query specifications are uniqueness-checked
before futures are scheduled. Diff-to-full fallback, transient workload retry,
the legacy safe-default parameter retry, explicit validation diagnostics, and
live health probes are distinct recovery or operator-requested operations and
remain separately observable. Query-spec resolution, read-only rebinding,
live drift, and validation repository checks now use one operation index per
repository; the post-publish refresh is intentionally a second lookup only
after a repository write.

## Diff Program Work Packages 1-3

### Resolved execution contract

- `ForwardNQEMap` now persists a separate, read-only `diff_commit_id` plus the
  verified full and diff source SHA-256 values. Migration `0043` leaves all
  three fields blank on upgrade so no legacy map becomes diff-eligible by
  accident.
- `ResolvedExecutionContract` is the canonical full/diff decision. Its full
  revision contains the resolved query ID, repository/path, full commit,
  verified declarations, and the effective supplied parameters computed once
  during planning. Its diff revision uses the separate commit and must have a
  verified-empty declaration set.
- Planning, full execution, diff execution, and the legacy direct runner
  consume that contract. Query-path resolution records the actual resolved
  repository path. The old `diff_query_id == run_query_id` alias is gone.
- Raw queries, custom/unknown sources, unresolved IDs or commits, unverified
  sources/declarations, identical full/diff commits, unsupported full
  parameters, parameterized diff sources, and alias/rules variants without
  required data-file hashes are full-only. `Require diff` converts those
  reasons into an explicit planning error instead of bypassing the contract.

### Run-scoped diff artifact

- `DiffArtifactStore` uses one per-key `Future` to build a single immutable
  artifact for `(model, before snapshot, after snapshot, resolved map set,
  scope fingerprint)`. Concurrent consumers wait on the same future.
- A model artifact executes each unique resolved map once and is cached before
  `build_branch_plan()` creates local branch shards. Repeated consumers and
  more than 50 one-row local shards did not increase Forward diff calls: two
  unique maps produced exactly two diff calls, one per map.
- The artifact is run-scoped memory containing processed workload results.
  Raw Forward diff envelopes are split immediately and are not written to the
  ingestion model results, support bundle, or durable workload ledger.

### Fingerprints and baseline invalidation

- Layered canonical SHA-256 fingerprints cover snapshot IDs; model and sorted
  enabled map set; map weight and contract key; resolved query ID, repository
  path, full/diff commits, verified source hashes, declared/effective
  parameters; base/aliases/rules selection and data-file hashes; coalescing
  identity; reducer, normalization, identity, and query-contract versions.
- Scope fingerprints cover network, sorted include/exclude tags, match mode,
  prune behavior, selected Forward device tags, the apply-scope-tags toggle,
  endpoint/generic-endpoint/endpoint-scope toggles, and both snapshot-side
  device/site/matched-tag membership.
- Successful per-map model results retain only aggregate contract/map/scope
  fingerprints. Baseline selection requires complete, single-valued matching
  evidence for the model; old or incomplete records, including missing
  before-side scope provenance, force a full run that can establish a new
  baseline.

## Diff Program Work Package 6a

### Stalled-diff boundary and fallback decision

The pre-WP6 path was not reliably bounded. The fetcher created one optional
per-workload deadline and passed it through diff polling and pagination, but
the first synchronous `POST /nqe-diffs/...` still inherited the source's
normal `1200`-second HTTP timeout. The `360`-second workload deadline could be
checked only after that request returned. In addition,
`ForwardFetchBudgetExceededError` was re-raised by `_fetch_spec_rows()` rather
than entering its existing full-query fallback. A non-terminal first diff
request could therefore stall the sync for up to the transport timeout and
then fail the model instead of completing through the full contract.

WP6a adds:

- a `60`-second default `diff_fetch_timeout_seconds`, capped by the remaining
  parent workload deadline;
- deadline plumbing into the first diff request, every diff page, async query
  trigger, status poll, and result page;
- an HTTP client timeout derived from the remaining deadline, including a
  deadline-specific conversion of `httpx.TimeoutException` to
  `ForwardFetchBudgetExceededError`;
- transparent full execution for an `Allow` contract after a diff budget
  timeout, with the type-only diagnostic
  `diff_budget_exceeded:ForwardFetchBudgetExceededError`;
- bounded failure rather than an implicit full fallback for a `Require`
  contract;
- a lock-protected per-run circuit keyed by resolved contract fingerprint.
  The default threshold is one timeout; a later consumer of the same contract
  skips diff and records
  `diff_circuit_open:ForwardFetchBudgetExceededError`. Both timeout and
  threshold are validated source settings.

Support bundles expose only aggregated model/reason/count fallback evidence.
Exception messages, query rows, snapshot identifiers, device names, and scope
values are not exported.

## Diff Program Work Package 6b

### Merge-gated contributor baseline

Migration `0044` adds one immutable baseline generation per ingestion, one
relation metadata row per resolved query contract, and independently
decompressible zlib chunks targeted at approximately `4 MiB` compressed.
Payload entries are exact
`[canonical_row_sha256, semantic_target_key, canonical_row]` records with
versioned headers, row/count/byte metadata, relation checksums, per-chunk
checksums, and a separately compressed scope envelope.

Pending generations are staged atomically but are not readable as current.
Promotion requires durable `merge_applied_at` evidence and runs from the same
post-merge bookkeeping boundary as durable workload-state promotion. Explicit
no-op finalization records the same merge evidence before promotion. Promotion
locks the sync, validates every scope and relation byte, and compare-and-swaps
the pending generation's recorded parent against the current generation.
Failed/partial ingestions, interrupted merge bookkeeping, stale concurrent
generations, duplicate pending generations, corrupt bytes, missing chunks,
database failures, and compare-and-swap races leave the old current generation
unchanged.

Contributor promotion itself runs in a nested savepoint. A stale/corrupt
pending generation or cache-specific database error records only the exception
type, skips contributor advancement, and does not strand an already merged or
successful no-op ingestion. The normal workload baseline can finalize; a
future Tier 3 lookup sees the old snapshot or a cache miss and executes full
provenance. Job timeouts still interrupt bookkeeping for the existing safe
resume path.

Compatibility rejects query commit/source changes, contract or codec
fingerprint changes, network/snapshot changes, map-set changes, scope-config
changes, and scope-membership changes. Cache miss or any read/validation error
returns a type-only full-provenance reason. The disk work relation uses a
private mode-`0600` SQLite file in a mode-`0700` directory, applies strict
add/delete/modify identity changes in one transaction, and removes the
workspace in `finally`.

Default generation guards are `1,500,000` rows and `300 MiB` compressed across
the generation. Exceeding either guard aborts the atomic stage; it never
truncates. No Tier 3 map is marked diff-eligible by WP6b.

workloads only, no deletes, no primary-IP overlay, exact pinned
NetBox/Branching/Forward NetBox/optional-plugin/configured-app tuple, versioned

tables, no prior ingestion/workload/contributor baseline/device identity, no
competing nonterminal branch, and no unproved admitted-model custom field,
enabled event rule, validator, or protection rule. All mutable facts are
rechecked under the transaction advisory lock plus target, side, Branch, and

and a branch rollback point. Recovery after a successful load is database
restore/reseed. That loss of review, per-row audit, conflict, and rollback
lineage is the explicit price of the one-time direct baseline.
