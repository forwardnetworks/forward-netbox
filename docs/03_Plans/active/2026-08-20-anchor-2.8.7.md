# Advance the release provenance anchor to 2.8.7

## Goal

Move the provenance anchor onto the shipped 2.8.7 release and promote it to
current in the compatibility tables, so the harness agrees with reality again.

## Why

The anchor names the previous release and the documentation-only bridge commit
that must directly follow its tag. Until it advances, `check_harness.py` fails
by construction: the tables would name a current release the anchor does not,
which is the check working rather than a nuisance. That failure is the reason
this cannot be quietly forgotten - only deferred.

v2.8.7 published: the tag peels to `879da87c9ba83968bd5607656ec78d37889f4263`,
the release workflow succeeded on all four jobs, and PyPI and GitHub carry
byte-identical artifacts - wheel
`97cdbcaface4a1cd359776dac83de68fd7b84005484c7f36380e3d92738c4ec4` and sdist
`20908fadff670ce98fa9dd06b914d37f95eeaf959d9f7bf40565c9d1fbfc5d90`, each
verified by downloading the GitHub asset and hashing it rather than by reading
the workflow's own report.

## Constraints

- The bridge must be the first commit after the tag on main's first-parent
  lineage, and documentation-only. `2811eba` is one file, 46 lines, no code.
- The table promotion belongs HERE and not in the release branch. `--finish`
  promotes on the production branch, which flips the tables to "current
  release" before a tag exists and makes the harness unsatisfiable; that commit
  was dropped during this release for exactly that reason.

## Touched Surfaces

- `scripts/verify_release_provenance.py` - `PRIOR_RELEASE_TAG`,
  `PRIOR_POST_RELEASE_DOC_COMMIT`
- `scripts/check_harness.py`, `scripts/tests/test_tasks.py` - the tag the
  release workflow is pinned to
- `README.md`, `docs/README.md`, `docs/01_User_Guide/README.md`, `CHANGELOG.md`

## Approach

Anchor to `v2.8.7` and to bridge commit
`2811eba4286d34b195b5f820de47b6612276f2af`, promote 2.8.7 to current release,
and demote 2.8.6 to superseded.

## Validation

`check_harness.py` passes with the anchor advanced, and
`verify_release_provenance.py --controls-only` passes against live GitHub.

## Rollback

Revert this commit. The anchor returns to v2.8.6 and the harness fails again,
which is the safe direction: it blocks the next release rather than permitting
an unverified one.

## Decision Log

- **Promotion folded into the anchor commit**, as in 2.8.6's `55bb0bc`. One
  commit moves the anchor and the tables together, so the two can never
  disagree in a pushed state.
- **No `.dev0` opened.** `main` carries the RELEASED version; a `.dev0` belongs
  with the first substantive change after a release, not as an automatic step.

## Open

- A local-only `release: promote v2.8.7` commit was created on `main` by
  `--finish` before tagging. It was never pushed, and the tag peels to a commit
  that IS on `origin/main`, so the release is unaffected - but a stray commit
  on local `main` outside any pull request is how provenance gets broken, and
  it was discarded rather than merged. `--finish` making that commit at all is
  worth fixing.
- This host still stalls close-mode HTTP for callers other than the release
  verifier, which was made immune in this release. The machine needs attention
  outside a release window.
