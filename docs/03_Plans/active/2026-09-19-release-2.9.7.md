# Release 2.9.7

## Goal

Cut `2.9.7` on the `maint/2.9.x` lane: bump every version surface and the
tested-runtime pin together, and record the release note for the twelve
commits already merged to `maint/2.9.x` since `v2.9.6` - the 2.9.7
customer-followup tranche (live-validated but never tagged), plus a
five-item maintenance sweep and two fixes from this session.

## Constraints

- Version surfaces (`pyproject.toml`, `forward_netbox/__init__.py`,
  `forward_netbox/utilities/fast_baseline.py`,
  `forward_netbox/tests/test_runtime_dependency_check.py`, the README
  compatibility tables) must all read `2.9.7` together, or
  `check_harness.py` refuses the release - see
  [[fast-baseline-version-pin-trap]].
- `scripts/tested_runtime.py`'s `TESTED_NETBOX_VERSION` is now `4.6.10`
  (bumped in this window, PR #447) - the compatibility table entry for
  2.9.7 must say `4.6.10`, not repeat `4.6.8` like every prior row.
- No code change in this commit: every functional change already landed
  as its own reviewed, `invoke ci`-green PR.
- No customer names, identifiers, or scan-matching hostnames in this
  plan, the changelog entry, or the release commit message.

## Touched Surfaces

- `pyproject.toml`, `forward_netbox/__init__.py`,

## Approach

`scripts/release.py 2.9.7 --write` bumps every version surface and the
fast-baseline pin in the same commit, and regenerates `CHANGELOG.md` from
the README compatibility table. The twelve commits it covers (oldest to
newest):

1. **2.9.6 post-release bridge + provenance anchor** (`6e8664e`,
   `f58f2a4`) - documentation/tooling only, no user-facing behavior.
2. **2.9.7 customer-followup tranche** (`8a08d60`) - three things a
   customer reported within hours of 2.9.6: a per-model progress bar that
   ran backwards (80%→50%→90%), SNMP endpoints reading manufacturer
   "Unknown", and a blocking sync failure that didn't say why. Also: the
   sync form now refuses to save an enabled model with no enabled NQE map
   instead of letting it fail silently at run time, and a manual
   device/interface delete can release the plugin's own `netbox_routing`
   delete-blockers instead of only explaining them.
3. **SNMP endpoints get interfaces and IP addresses** (`ed188c9`) -
   endpoints imported as devices now also get their SNMP-derived
   interfaces (name, enabled state) and IPv4 addresses, matching what a
   modeled device gets.
4. **Live-validation pass on the whole 2.9.7 tranche** (`942da99`) -
   found and fixed one real live-only bug the linter missed:
   `regexMatches` used as a bare boolean in a dotted-quad guard lints
   clean but throws `NQE_RUNTIME_ERROR` at runtime; fixed with
   `!isEmpty(...)`. Confirmed the SNMP-vendor fix (Unknown count
   84→34), the new interfaces/IPs query (1297-1903 sane rows, no
   orphaned pairs), and the routing delete-blocker release all work
   against real Forward data and a real `netbox_routing` schema.
5. **NQE lint-blind-spot regression guard** (`e714e30`) - a static test
   over every builtin `.nqe` file for the two known lint-clean/
   runtime-broken patterns (bare `foreach`-as-value, `regexMatches` used
   as a boolean), so the class of bug item 4 found by hand gets caught
   automatically from here on.
6. **Cross-invariant test for `workload_state` sweep models**
   (`e7e54e9`) - pins that every model with a bespoke delete-sweep gate is
   also refused by all three generic delete producers, so a future sweep
   addition can't silently create a second, competing delete authority
   for the same model.
7. **Drift-report multi-map consolidation fix** (`5288302`) - a model
   with more than one enabled map (e.g. `dcim.inventoryitem`'s
   CIMC/APIC-CIMC maps) could have a stale-baseline delete go through
   unconsolidated when the maps disagreed on `sync_mode`; the
   consolidation guard now only requires more than one enabled map.
8. **Pre-push hook GIT_DIR isolation fix** (`ef588d6`) - root-caused and
   fixed the branch-corruption bug that had cost 5+ recovered pushes: a
   test fixture's bare `subprocess.run(cwd=...)` inherited the ambient
   `GIT_DIR`/`GIT_WORK_TREE` a git hook sets for its child processes, so
   the fixture operated on the real repo instead of its own temp dir.
9. **HSRP linter false-positive docs** (`582df0f`) - documentation only;
   `forward_hsrp_groups.nqe`'s `foreach group in ...` is correct
   (live-confirmed 1892 rows), the linter's `group`-as-reserved-word
   misparse is a known limitation, not a bug to "fix" by renaming.
10. **Say when an uncovered device is still tagged in Forward's
    configuration** (`ae68ae9`) - a customer reported 461 uncovered
    devices, 321 "tagged in Forward" per Forward's own UI. Root cause:
    Forward's Device Tags page reads the network *configuration*; every
    NQE query, and so the sync, reads the *snapshot*. The scope census
    now says which configuration fact keeps an already-tagged device out
    of the snapshot - disabled, not yet collected, or a tag entry that
    outlived the device (a vsys/vdom child, most commonly) - on the scope
    panel and the device page, instead of just "gone from Forward".
11. **NetBox runtime bumped to 4.6.10, plus a delete-protection
    regression it surfaces** (`730b154`) - NetBox 4.6.9
    ([#22812](https://github.com/netbox-community/netbox/issues/22812))
    made `JobsMixin.delete()` batch-delete an instance's own jobs before
    `pre_delete` fires, which silently broke this plugin's protection
    against deleting a `ForwardSync`/`ForwardIngestion` while one of its
    jobs is actively running. Fixed: both models now check for a running
    job before NetBox's own cleanup gets a chance to clear the evidence.

Full design detail lives in its own plan doc under `docs/03_Plans/active/`
for items 2, 3, 4, 10 and 11: `2026-09-15-2.9.7-customer-followups.md`,
`2026-09-16-snmp-endpoint-interfaces-and-ips.md`,
`2026-09-17-live-validate-2.9.7-tranche.md`,
`2026-09-18-uncovered-configured-in-forward.md`,
`2026-09-18-netbox-4.6.10.md`. Items 5-9 (the five-item maintenance
tranche, PRs #413-#417) were low-risk enough that `check_harness.py`'s
plan-file gate did not require one; their own PR descriptions and commit
messages carry the design detail summarized above.

## Validation

- `invoke ci` passed on every one of the individual PRs before merge
  (#410/#411/#412, #413-#417, #446, #447).
- A final combined-tree gate ran after all 12 commits landed on
  `maint/2.9.x` together (not just each PR individually against its own
  base): `invoke harness-check`, `invoke harness-test` (414 tests), and
  full `invoke ci` (414 + 71 + 2914 tests, 9 skipped, plus the
  2.9.5→2.9.6 artifact-upgrade leg) - all green.
- `scripts/release.py 2.9.7 --write` verify step: version-surface
  consistency, UI harness dependencies, no unaccepted advisories, no open
  high/critical Dependabot alerts, `poetry.lock` parity, and
  `check_harness.py` on this diff.
- The sensitive-pattern parity check runs UNVERIFIED in this checkout
  (`FORWARD_SENSITIVE_PATTERNS` is a CI-only secret not available
  locally); the release gate applies the superset feed and can still
  refuse the tag - recorded per [[sensitive-pattern-feeds-differ]].
- Item 10's root cause was confirmed by a live NQE/REST probe against the
  validation org before any code moved (see that item's own plan doc);
  item 11's regression was confirmed reproducible on 4.6.10 and absent on
  a 4.6.8 control before being called a real bug.

## Rollback

This commit is a version bump and changelog entry only - no functional
code changes ship in it (those already merged as separate PRs). Reverting
it restores the previous version surfaces; the functional PRs would need
their own separate reverts if any of them needed to be undone.

## Decision Log

- **One release-cut plan file for the version bump, not a rewrite of the
  item-level plans.** Those already carry full design and decision-log
  detail; duplicating them here would drift out of sync with the merged
  code.
- **Batched twelve items into one release rather than cutting 2.9.7 right
  after the customer-followup tranche merged.** Standing call from
  2.9.7's own backlog memory: a release costs a full gate run and a
  manual multi-PR flow, so minor items wait for a batch; this batch grew
  to include the maintenance-tranche PRs and this session's two fixes
  because none of them had a reason to cut alone either, until now.
