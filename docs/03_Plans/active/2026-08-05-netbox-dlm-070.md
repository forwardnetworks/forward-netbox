# Accept netbox-dlm 0.7.0

## Goal

The customer released netbox-dlm `0.7.0` and runs DLM on the NetBox that hosts
the sync. `pyproject.toml` capped the dependency at `<0.7.0`, so it was excluded
at install, and every version gate listed `0.6.0` as the newest validated
release. Validate against `0.7.0` and accept it.

## Contract

- The version is added because it was tested, not because it looked additive.
  The engine gates fail closed by design and widening them is a claim.
- Every pin moves together. A version accepted by one gate and refused by
  another is the failure this set of gates was rewritten to prevent.
- The upgrade-from constraints move too. They were initially left at `0.6.0`
  on the reasoning that they pin what the previous release shipped against —
  wrong, and `scripts/tests` caught it: `UpgradeFromConstraintsTests` asserts
  the two files differ ONLY in the branching pin, because anything else drifting
  between them silently changes what the upgrade gate compares. The file's own
  rationale is specific to branching and the NetBox cap, not to optional plugins.

## Constraints

- Eleven pin sites, two of which a first grep for `netbox-dlm` missed:
  `registry.py` carries BOTH `required_package_version` and
  `supported_package_versions`, and only the tests caught the second.
- `poetry lock` alone does not move the lockfile: `0.6.0` still satisfies the
  widened range, so it is kept. `poetry update --lock netbox-dlm` is required.
- No customer identifiers.

## Touched Surfaces

- `pyproject.toml`, `constraints.txt`, `poetry.lock`
- `scripts/validate_sbom.py`, `tasks.py` (SBOM runtime snippet)
- `forward_netbox/utilities/apply_engine_decision.py`,
  `forward_netbox/utilities/fast_baseline.py`,
  `forward_netbox/utilities/merge_set_based.py` (engine gates)
- `forward_netbox/utilities/plugin_integrations/registry.py`
- `forward_netbox/tests/test_plugin_integrations.py`,
  `forward_netbox/tests/test_optional_plugin_versions.py`

## Approach

Read the upstream diff before touching anything. `v0.6.0..v0.7.0` changes one
model: `Contract.platforms`, an additive `ManyToManyField` to `dcim.Platform`,
with migration `0005_contract_platforms`, plus `covers_device()` and
`covered_devices`. The rest is presentation — serializers, tables, forms,
filtersets, the contract template.

`SoftwareVersion` and `InventoryItemSoftware` are untouched, and those are the
models this plugin syncs. `Contract` is not written by the sync at all, so the
new field is out of the integration's path entirely.

That is the reason to expect it to pass, not a substitute for running it.

## Validation

`netbox-dlm==0.7.0` installed in the test image (confirmed in the build log),
then the DLM integration, DLM catalogue-conflict, plugin-integration and
optional-version suites: 61 tests. Two failures on the first run were stale
expectations in this repo, including the missed `supported_package_versions`.
Full plugin suite after that, because the engine gates are read by the fast
baseline and the merge.

## Rollback

Revert. `0.6.0` returns to being the newest accepted version; anything running
`0.7.0` then reports `unsupported_version` and drops the DLM models with a
warning, which is the documented behaviour rather than a broken state.

## Decision Log

- **Not pinned pre-emptively.** The version was left unaccepted until `0.7.0`
  was actually published and could be installed and run. Adding it on the
  strength of a changelog would have asserted a validation that had not happened.
- **`<0.8.0` rather than `<0.7.1`.** The cap exists to keep a major-shaped change
  from installing silently; the per-version gates are what actually enforce
  validation, and they still list versions explicitly.
- **The upgrade-from side installs `0.7.0` too.** Checked rather than assumed:
  `development/Dockerfile:20` installs the optional plugins under
  `${CONSTRAINTS}`, so the from-side image really does get whatever that file
  says; `PACKAGE=forward-netbox==<prev>` requests no extras, so the previous
  release's own `<0.7.0` cap never enters resolution; and
  `scripts/validate_upgrade_state.py` seeds and verifies nothing DLM-related, so
  what the gate actually compares is unchanged either way.

## Open

- The claim that an unsupported optional-plugin version fails silently is only
  half true, and the half that is true is the more damaging one. Dropping the
  models is announced — `query_fetch_execution.py:875` logs a warning per model
  naming the integration, the status and the supported set, and the health page
  renders `availability_reason`. The fast baseline, set-based merge and COPY/SQL
  gates are the ones that switch off without an operator-facing signal, turning
  a first sync from minutes into hours. Making that one loud is worth its own
  change.
