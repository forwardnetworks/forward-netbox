# Let Auto merge stop for review when a run is far larger than normal

## Goal

Auto merge means a healthy sync needs nobody, and also that a run that is wrong
- or merely enormous - reaches NetBox unreviewed. A customer's first full run
after an upgrade staged 147,015 changes and merged them before anyone could ask
whether that was right. Between staging and merging, decide whether the run is
out of proportion and, if it is, leave it staged for a person.

## Constraints

- **Narrow on purpose.** A guard that holds healthy runs gets switched off.
  It applies only when the sync has Auto merge on; only when the sync has
  finished a run before (the first load a sync ever does is never held); and
  only for a model the size rule flags - at least 10,000 staged changes and
  3x the table's established size (a table of at least 1,000 rows) or 10x the
  median of three or more earlier runs. An empty or small table, a small
  model and a model without history are never held.
- **Fails open.** An error in the guard is logged and the run merges as it
  always did. A guard that raised would stop every sync over a bug in its own
  arithmetic.
- **No new destructive path.** A held run is the existing review lane: the sync
  is `ready_to_merge`, the branch stays staged, the ingestion page keeps its
  Merge button, and deleting the ingestion discards it. Nothing is deleted or
  merged by the guard itself.
- No migration; the hold is recorded on the job's data through the run's own
  logger.

## Touched Surfaces

- `utilities/run_size_guard.py` (new): `decide_run_size_hold`, `record_hold`.
- `utilities/single_branch_executor.py`: `_hold_for_run_size`, called after
  staging and before the automatic merge.
- `utilities/change_explainability.py`, `utilities/health_evidence.py`: a public
  per-model change count and row count for the guard to reuse.
- `tests/test_run_size_guard.py`, `tests/test_bulk_merge.py`.

## Approach

After every workload and the primary-IP step have staged, and only when Auto
merge is on, aggregate the branch's `ChangeDiff` by model and pass models at or
above the floor to the rule, with each model's current NetBox row count and the
change counts earlier runs applied. If anything is flagged, record the findings
on the job, set the sync `ready_to_merge`, log a warning naming each model and
its multiple, and return the ingestion staged. The `Run held for review` check
(previous commit) reads the record, shows it on the sync page with a link to
the ingestion, and says how to merge or discard.

## Validation

- `test_run_size_guard`: the customer's shape is held; a first-ever run, an
  earlier run that never finished, Auto merge off, below the floor, a small
  table, growth within the multiple, too little history and no staged changes
  are never held; the hold is written through the logger.
- `SingleBranchExecutorTest`: a flagged run is left staged and unmerged with the
  sync `ready_to_merge`; the operator can still merge it; Auto merge off never
  asks the guard; an error in the guard fails open and the run merges.
- Full `invoke ci` before merge.

## Rollback

Revert the commit. Nothing persisted outside the job's data needs undoing.

## Decision Log

- **The table's size as the norm, not the learned density.** Density is changes
  per written row and cannot say how many rows a run writes.
- **"Merge anyway" and "Discard" are the existing Merge button and ingestion
  delete, reached from the banner.** New POST endpoints on a merge path add
  surface without adding capability; the banner links to where both already
  live and says which is which.
- **The density profile still learns from a held run.** Skipping it would need
  the guard to run before the observations fold, ahead of the primary-IP step
  whose changes the guard must count. One extra sample costs less than
  reordering staging.
- **Not applied to the fast-baseline path.** That path is a first baseline by
  definition and never merges through this branch.
