# Advance the release provenance anchor to 2.8.2

## Goal

Move the prior-release anchor from `v2.8.1` to `v2.8.2` and promote the shipped
release in the compatibility tables, so the next release verifies its lineage
against the release that actually precedes it.

## Constraints

- The anchor pair must move together and must be consistent across all of its
  sites. A stale anchor is not inert: it is what burned `v2.6.10`, and after
  `v2.7.0` the bridge slot was taken by another commit and could never be
  reclaimed.
- `PRIOR_POST_RELEASE_DOC_COMMIT` must name the documentation-only bridge that
  sits directly on the tag - here `63b80be`, whose parent is `424c66b`, which
  is what `v2.8.2` peels to. Both were checked rather than assumed.
- Re-anchoring is not self-validating. The verifier has to be re-run afterwards;
  it cannot notice an anchor that points somewhere plausible but wrong.

## Touched Surfaces

- `scripts/verify_release_provenance.py` - the anchor pair
- `scripts/check_harness.py` and `scripts/tests/test_tasks.py` - the expected
  tag fetch in the release workflow
- `.github/workflows/release.yml` - that fetch itself
- `README.md`, `docs/README.md`, `docs/01_User_Guide/README.md` - promote
  `v2.8.2` from release candidate to current release and supersede `v2.8.1`
- `CHANGELOG.md` - regenerated from the tables

## Approach

The table promotion is deliberately here rather than in the release commit. At
every shipped tag the README has read "Release candidate" for the version being
tagged; `release.py --finish` tries to promote before the tag and
`check_harness.py` refuses it, which is the guard working. Promotion belongs
with the anchor because both describe a release that has now actually shipped.

The anchor sites were found by diffing the previous advance rather than from
memory, and each replacement asserts its old value is present before writing.

## Validation

- `scripts/check_harness.py`, which cross-checks the anchor against the current
  release in the README table - the check that refused the early promotion.
- `invoke harness-test`.
- `pre-commit run --all-files`.

## Rollback

Revert. The anchor returns to `v2.8.1` and the tables to a candidate row, which
would block the next release rather than break this one.

## Decision Log

- **Bridge identity verified by parent, not by position.** `63b80be`'s parent is
  `424c66b` and `v2.8.2` peels to `424c66b`. Recording a bridge that merely
  looks right is the failure mode the anchor exists to prevent.
- **Promotion and anchor in one commit.** They are the same statement - "2.8.2
  is now the released version" - and splitting them leaves a window where the
  harness check contradicts itself.

## Open

- `2.8.3` is not opened on `main`; `main` stays at the released version.
