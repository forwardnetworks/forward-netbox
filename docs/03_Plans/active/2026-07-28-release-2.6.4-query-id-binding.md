# 2.6.4 Query-ID Binding Correction

## Goal

Restore full syncs for maps bound to a query ID, and make a run that fetched
nothing impossible to mistake for a converged one.

## Field report

A customer upgraded 2.6.1 to 2.6.3, ran **Resolve to Query ID** as the release
notes direct, and got a sync reporting Completed and Validation Passed with zero
changes, no branch, and a Drift report stuck at "not measured". The support
bundle and job log establish the chain:

1. **Resolve to Query ID** stores a `query_id` and moves the repository path
   into `resolved_query_path`, clearing `query_path`. All 34 maps reported
   `commit_binding: latest_commit`, `has_commit_id: false`.
2. `QuerySpec.resolve` only read `query_path`, so an ID-bound map never received
   a commit.
3. The execution contract rejects an empty or `"head"` commit as
   `unresolved_full_commit`, and any map that is not `full_eligible` raises
   `ForwardQueryError` and skips its model. `query_contract_preflight` reported
   `consistent: false` with 34 issues; **2 NQE query calls ran for 29 enabled
   models**, against 3,176 correctly-scoped devices.
4. The executor treated the resulting empty workload as "no changes" and
   recorded a completed, branchless, zero-change ingestion.
5. Drift stayed "not measured" because no ingestion applied anything.

The documented remediation was therefore what disabled the sync, and the result
was invisible.

## Constraints

- No migration and no operator step: resolution must use data the maps already
  store, so an upgrade plus a re-run is the whole procedure.
- Keep the parameter-compatibility guard. The contract must still refuse a
  revision whose declared parameters do not match the map.
- Do not loosen diagnostic redaction. Customer data must not enter logs or
  bundles to make this diagnosable.

## Touched Surfaces

- `forward_netbox/utilities/query_registry.py`
- `forward_netbox/utilities/forward_api_impl.py`
- `forward_netbox/utilities/single_branch_executor.py`
- `forward_netbox/utilities/query_fetch_execution.py`

## Approach

**Head resolution works for either binding.** A map that keeps its path resolves
through it. A map bound only by a query ID resolves head from the repository
query index via `resolve_nqe_query_head_commit`. Two guards: a commit is adopted
only when the path still resolves to the bound query ID, so a moved path cannot
graft another query's revision; and an ambiguous or unresolvable ID leaves the
spec untouched so the existing contract reporting explains the refusal rather
than failing the whole fetch. An explicit pin is never overwritten.

**An empty workload caused by failures fails closed.** `failed_model_strings`
decides whether an empty workload means convergence or wholesale failure, and
the run raises naming the failing models. Extracted as a helper so the decision
is unit tested rather than buried in `run()`.

**A worker timeout escapes resolution** instead of degrading into an unresolved
commit. The harness boundary check caught this in the first cut of the fix.

**Preflight reporting separates blocking from inert findings.** Both were
reported in one undifferentiated warning, so 30-odd routine
`diff:missing_diff_commit` lines buried the two rejections that actually
emptied the sync. They are now two messages, each naming its consequence: a
full-contract rejection says the model will be skipped and its data will not
sync; a diff finding says the model still syncs in full.

Both stay at warning level. An earlier cut dropped the diff message to info in
a full-only run, which the existing preflight tests correctly rejected: a map
that cannot diff silently falls back to a full fetch, and the operator should
know that even when the run was never going to diff. The fix here is
distinguishing consequences, not hiding one of them.

## Rejected alternatives

- **Have the customer pin every map to a commit.** A workaround, not a fix, and
  it freezes maps against a revision they did not choose to pin.
- **Treat an unresolved commit as eligible.** Removes the guard that stops a
  full contract executing against a parameter-incompatible revision, which is
  the reason the check exists.
- **Preserve raw warning text in support bundles.** It would have made this
  directly diagnosable, but the blanket redaction protects customer data in
  exception-derived messages. Structured, enum-like classifiers are the safe
  way to close the same gap.

## Validation

- Full Django suite: 1,642 tests, `OK (skipped=3)`.
- Harness suite: 219 tests, OK, including the worker-timeout boundary rule.
- 14 new tests covering both binding modes, the moved-path guard, pin
  precedence, unresolvable and ambiguous IDs, a failing repository lookup, and a
  client without the resolver.

## Rollback

Revert the commits. No schema change and no persisted state, so a downgrade
needs no data repair.

## Decision Log

- 2026-07-28: shipped as a corrective release ahead of the remaining 2.6.4
  backlog, because the defect leaves affected customers silently syncing
  nothing in production. Protected-delete ordering, diff enablement and the
  performance engines move to 2.6.5.
