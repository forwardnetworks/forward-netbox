# Release 2.7.2

## Goal

Ship the field-reported fix that `2.7.1` did not resolve: a sync that plans
nothing and ends having fetched nothing, on an installation whose maps are
bound to Forward queries by ID.

## Contract

- The four version surfaces move together in one commit, or the fast baseline
  silently reverts from minutes to hours.
- The by-ID fix and the row-shrink guard ship together. The first removes the
  comparison that used to notice a query changing underneath a map; the second
  replaces it. Shipping the first alone trades a loud failure for a silent one.
- Provenance verifies locally before the tag is pushed. A tag-time failure
  spends the version permanently.
- The post-release close-out archives the plan FIRST, then promotes and
  advances the anchor. The bridge commit must carry no executable content, and
  as of `#137` the harness enforces it.

## Constraints

- One migration, for the two drift-policy fields; it applies itself and needs
  no operator step.
- `netbox_branching` stays in the ingestion path.
- No new bundled query, so no organisation-library publish is owed.
- The release row carries no customer identifiers.

## Touched Surfaces

- `pyproject.toml`, `forward_netbox/__init__.py`
- `forward_netbox/utilities/fast_baseline.py` (runtime pin)
- `forward_netbox/tests/test_runtime_dependency_check.py`
- `README.md`, `docs/README.md`, `docs/01_User_Guide/README.md`
- `CHANGELOG.md` (generated)

## Approach

The tranche is already on `main` and each part was validated before it landed.
`scripts/release.py` owns the version and table edits. What remains is the
gate, the authorization record, the tag, and the close-out.

Merged since `v2.7.1`:

- Fail when the post-release bridge is not documentation-only (#137)
- Run a query ID at Forward's latest, and refuse a run that came back far
  smaller than its baseline (#140)
- Expose why a sync failed, per model (#139)

## Validation

The full local release gate and the exact-runtime artifact test, run in an
isolated Docker project against NetBox 4.6.6 with Branching 1.1.2, recorded
under Release Authorization below with their real outcomes.

Beyond the gate, the by-ID change was validated against a live Forward
instance before it merged: an ID-bound, commit-less map planned and fetched
rows, the captured execution payload carried no commit, no call was made to
the query-history endpoint, an explicitly pinned commit still sent that
commit, and the same tree's predecessor failed on the identical setup.

## Rollback

Nothing to roll back before the tag exists. Afterwards the recovery is a
forward release: the tranche is on `main`, so a defect found in `2.7.2` is
fixed in `2.7.3` rather than by retracting an artifact already installed.

The row-shrink guard is the one change that can refuse a run an operator wants.
It is overridable per baseline through the existing force-allow, so a false
positive does not require a release to clear.

## Decision Log

- The by-ID fix and the guard were kept in one pull request rather than
  sequenced, because the window between them is exactly the window in which a
  narrowing query deletes objects silently.
- The guard defaults on and is checked before the drift-policy enablement
  gate, so an installation with no policy is still covered. The existing
  delete limits are optional and unset by default, which is why they protect
  nobody, and that shape was deliberately not repeated.
- `2.7.1` shipped clean by every process measure while a customer stayed
  broken, because the reason was destroyed before anything recorded it. That
  is the argument for treating `#139` as release content rather than cleanup.

## Open

- The reported failure could not be reproduced from its own evidence; it
  required injecting a permissions failure at the history endpoint. The
  installation's root cause is still unconfirmed, and this release removes the
  dependency rather than explaining it.
- A query whose organisation copy has drifted still fails, now per model. This
  release makes that visible; it does not make the query run.
- `_forced_validation_override_applies` cannot fire on the sync path, which
  affects force-allow carry-forward for every blocking reason. Tracked
  separately; the row-shrink guard does its own lookup rather than depend on
  it.
