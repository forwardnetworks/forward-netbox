# 2.9.12: close out stuck merges, repair duplicates, harden deletes

## Goal

Fix the faults a customer's 2.9.11 estate exposed. A sync whose branch merge
was applied stayed "Ready to merge" and could not be recovered. The site-relabel
duplicate repair merged nothing, because routing rows block deleting the newer
device. Deletes wait silently on the ownership lock, and a large delete has no
chunking or resume. This plan grows one item per commit.

## Constraints

- Recovery never acts on a sync whose merge is unproven: it needs
  `merge_applied_at`, a branch that is merged or gone, no live job and an
  elapsed grace window.
- GUI only; no operator CLI is added.
- Any code that deletes names an explicit allowlist and a gate, and its tests
  pin the negative space.
- No customer names, hostnames or counts in committed content.

## Touched Surfaces

- `forward_netbox/utilities/stuck_recovery.py`
- `forward_netbox/tests/test_stuck_recovery.py`
- `forward_netbox/utilities/scope_reconciliation.py`
- `forward_netbox/tests/test_site_relabel_pairs_merge.py`
- this plan

## Approach

`classify_stuck_sync` treated `READY_TO_MERGE` as never recoverable, because a
staged run waiting for approval looks identical to a stuck one. It now returns a
`finalize_merged_bookkeeping` verdict for `READY_TO_MERGE` only when the latest
ingestion has `merge_applied_at` set, its branch is merged or absent, and no
sync job is live after the grace window. The existing recovery path then runs
`resume_post_merge_bookkeeping` and the post-sync overlays.

### Site-relabel duplicate repair

On one estate the repair merged none of 150 pairs: every delete of the newer
device was refused, because the sync's own routing rows (BGP peers, OSPF
interfaces) protect it. `merge_site_relabel_duplicates` now reads Django's
deletion plan for the newer device and deletes the blocking routing rows only
when every blocker is either on a fixed list of sync-built routing models or is
one of this plugin's own ownership records, which the following delete
releases. The next sync rebuilds those rows against the surviving device. Any
other blocker refuses the pair and nothing is deleted for it. Each pair stays
in its own transaction, so a refusal rolls back any release. The result lists
the rows released per model.

## Validation

- `test_stuck_recovery`: 28 tests pass in an isolated stack. New cases: applied
  with no branch and applied with a merged branch yield the verdict; the
  close-out completes the sync and makes the baseline ready; a staged run, an
  unproven merge, an applied merge with a ready branch, a live job and an
  unexpired grace window all yield no verdict.

- `test_site_relabel_pairs_merge`: 26 tests pass in an isolated stack. New: OSPF
  rows and a BGP peer addressed on the newer device are released and the merge
  completes; a non-routing protector refuses the pair with the other rows left
  in place; the releasable list is pinned exactly.

## Rollback

Revert the commit. A sync left in "Ready to merge" returns to needing manual
completion; no data or migration is involved.

## Decision Log

- Release routing rows on proof of the duplicate pair rather than per-row
  ownership: routing rows carry no ownership record, and the pair proof
  (same name, one at Forward's site) already establishes the newer device is the
  sync's own copy. The fixed model list and the refusal on any other blocker are
  the safeguard.

- Reused the existing recovery action rather than adding one, so the close-out
  runs the same bookkeeping path a normal merge does.
- Kept `test_ready_to_merge_is_never_recovered` for the staged case, which stays
  true.
