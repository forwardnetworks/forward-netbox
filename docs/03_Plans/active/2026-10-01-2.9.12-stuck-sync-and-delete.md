# 2.9.12: close out stuck merges, repair duplicates, widen primary IP and routing

## Goal

Fix the faults a customer's 2.9.11 estate exposed, and close the routing and
primary-IP gaps they raised. A sync whose branch merge applied stayed "Ready to
merge" and could not be recovered. The site-relabel duplicate repair merged none
of its pairs. A sync delete waited silently on the ownership lock and stripped
every device tag. SNMP endpoints and same-name duplicates never got a primary IP,
and most devices without a `Mgmt_` tag had no path to one. BGP peer address
families never linked their route maps or prefix lists, and static routes were
not modelled at all.

## Constraints

- Recovery never acts on a sync whose merge is unproven: it needs
  `merge_applied_at`, a branch that is merged or gone, no live job and an
  elapsed grace window.
- Every diagnostic and remediation is in the GUI; no operator CLI is added.
- Any code that deletes names an explicit allowlist and a gate, and its tests pin
  the negative space.
- A query's parameters do not change, so an org that published an older copy
  keeps working; it must republish the two changed queries to gain the links.
- New model maps are opt-in and off by default.
- No customer names, hostnames or identifying counts in committed content.

## Approach

**Stuck merge close-out.** `classify_stuck_sync` returns a
`finalize_merged_bookkeeping` verdict for `READY_TO_MERGE` only when the latest
ingestion has `merge_applied_at`, its branch is merged or gone, no job is live and
the grace window has passed; the existing recovery path finishes the sync. An
empty verdict now carries a reason, and the bundle exports the merge evidence.

**Duplicate repair.** The newer copy's delete was refused because the sync's own
routing rows protect it. The repair reads Django's deletion plan for the newer
device and removes those rows only when every blocker is on a fixed list of
sync-built routing models or is one of this plugin's ownership records; any other
blocker refuses the pair and deletes nothing. The last run's outcome shows on the
Scope Reconciliation page.

**Delete behaviour.** Operator deletes of a sync wait two minutes for the
ownership lock, then stop with a message naming the holding database session. The
delete confirmation states that the sync's settings are lost, lists each tag and
how many devices would lose it (a read-only mirror of the strip), and offers to
leave the tags on the devices. Module Readiness runs as a background job and the
page renders the stored report.

**Primary IP.** The `Mgmt_` tag read now covers SNMP endpoints. The device lookup
no longer collapses same-name devices onto one arbitrary copy: it takes the copy
holding interface addresses, or leaves the name unresolved. An opt-in fallback
uses Forward's single management address for a device with no `Mgmt_` tag, only
when that exact address is on exactly one of its interfaces. The bundle reports
coverage.

**BGP policy links.** The peer address-family query reads route-map and
prefix-list attachments from configuration (NX-OS direct and through peer
templates, Arista, IOS-XE) and emits four columns, null when none. The route-map
query reports the holders of each non-owner variant so a device links to its own
variant. A name that is not imported leaves the field empty and is counted; a row
without a policy never clears an existing link.

**Static routes.** The map reads configured `ip route` / `ipv6 route` lines. One
`StaticRoute` is kept per VRF, prefix and next hop with every configuring device
attached; the device sorting first owns the attributes. Removal detaches only the
device, and deletes the route only when its last device leaves and it carries the
sync's marker.

## Validation

- Full Django suite on the 2.9.12 branch: 3,321 tests; the only two failures were
  in the new static-route tests and are fixed (a converged-row rewrite bug found
  by the repeat-apply test, and a query-text assertion). Re-run of those: pass.
- Scripts suite: 422 tests pass.
- The peer address-family and route-map queries were run against a real network:
  the same rows come back as before plus the policy columns (about 44% of address
  families carry a policy); the static-route query returns every configured line
  the earlier counts found.
- Not exercised on real data: the static-route apply, the delete confirmation in a
  browser, and the endpoint primary-IP step; these have unit and integration
  tests only.

## Rollback

Revert the release. Migration `0058` only widens the NQE map model choices, so
reverting leaves no orphaned data; any `StaticRoute` rows the opt-in map created
stay in NetBox and carry the sync's marker in their comments. Policy links set on
peer address families remain until an operator clears them.

## Decision Log

- Static routes ship opt-in in a maintenance release because the user asked for
  them and the map is off by default; the apply path has no live acceptance run.
- The primary-IP fallback is a separate setting from the tag source so enabling
  one never changes the other's behaviour; tags always win.
- Policy links are never cleared by a row without a policy: a platform whose
  configuration the query cannot read must not erase links an operator set.
- Peer-group inheritance on Arista and IOS-XE, IOS-XR, and chunked resumable
  deletes are deferred: the delete that hung completed on its own and the bounded
  lock wait covers its cause.
- Django in the lock stays on 6.0.8 rather than moving to 6.1, matching the line
  NetBox 4.6 ships.
