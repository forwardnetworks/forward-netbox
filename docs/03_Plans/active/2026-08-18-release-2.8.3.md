# Release 2.8.3

## Goal

Ship the three correctness fixes a deployment's 2.8.2 sync produced, the
NetBox 4.6.8 uplift, and two tooling fixes that make this release's own
machinery trustworthy.

## Constraints

- The four version surfaces move together with the fast-baseline runtime pin,
  through `scripts/release.py` rather than by hand. A stale pin there reverts
  the first baseline from about six minutes to about fifteen hours, silently.
- The lineage from the recorded bridge to the release commit must hold at least
  four commits, with the production and release commits last.
- The prior-release anchor stays at `v2.8.2` until the post-release change; the
  bridge commit after the tag must be documentation-only.
- `FORWARD_SENSITIVE_PATTERNS` is not on this host. The release-time feed is a
  SUPERSET and runs only after the tag, so the gap is recorded and the added
  content reviewed rather than assumed - see Approach.
- A patch, not a minor. One entry changes what a sync deletes unattended, and
  it only ever removes capability from a destructive path.

## Touched Surfaces

Landed across four pull requests:

- `#223` the protected-delete skip on the device path, the prune removal
  allowlist, and drift-report coverage reporting
- `#224` tested and validated on NetBox 4.6.8
- `#225` the merge's tree-model detection and its canary
- `#226` the release command's exit status and the scale gate's load guard

This commit adds the version surfaces, the compatibility tables, and this plan.

## Approach

### What a deployment reported

Its first 2.8.2 sync confirmed both 2.8.2 fixes in the field - every skip named
its NetBox row, and the sites, device types and VRFs the diff path used to
delete were gone - and surfaced three more.

A `dcim.device` delete refused by the database was recorded as a FAILED row,
because devices delete through the branch collector and never reached the
conversion every other path gets. One failed row blocks baseline promotion
permanently, which puts every drift figure back to "Not measured" for the whole
deployment. That is the entry that matters: declining to delete a device is
minor, wedging convergence over it is not.

The tag-scope prune turned out to be a third delete producer with no allowlist,
which is why software-version catalogue rows kept being attempted after the
other two paths were gated.

And the drift report used one string, "Not measured", for three unrelated
situations, only one of which is fixed by re-running the preview.

### The sensitive-pattern gap

Same position as 2.8.1 and 2.8.2, and handled the same way rather than waved
through. Every string literal added since `v2.8.2` was enumerated - 99 of them,
84 not schema identifiers - and reviewed: payload keys, version strings, CSS
classes, our own message prose, and synthetic fixtures. The prose added to
documentation was scanned for person tags, hostname-shaped tokens, long digit
runs and addresses; none present. `check_sensitive_content.py --git-files`
passes over all tracked content.

## Validation

Recorded in the Release Authorization section below, bound to the evidence base
commit: the full isolated gate and the exact-runtime artifact test, both on the
final tree, both on NetBox 4.6.8 - the first release gated there.

## Rollback

No migration, so a downgrade is an install of the prior wheel. The prune
allowlist restores by reverting `#223`.

## Decision Log

- **Land the tooling fixes before cutting the release, not after.** Both are
  false negatives in the machinery this release runs: a command that reports
  failure after publishing, and a gate that reports a regression on a busy
  host. Fixing them afterwards would mean running the release through the
  known-broken versions first.
- **Lead the notes with convergence, not with `ProtectedError`.** What an
  operator experienced was every drift figure reading "Not measured"; the
  exception is the mechanism, not the symptom.
- **Patch, not minor.** Nothing gains an operator control and nothing changes
  shape.

## Publish Refusal and Recovery

The first v2.8.3 tag was refused by the publish workflow and this section
exists so the recovery is not mistaken for a clean first attempt.

The sensitive-content gate applies the release-only superset pattern feed,
which no developer checkout has. It reported two findings against
`path:sha256:e478676137834484` - a redacted PATH rather than file content. The
hash resolves to `docs/03_Plans/active/2026-08-17-blake-2.8.2-followups.md`, a
filename this repository created, identified by hashing all 1009 tracked paths
and matching the digest without ever seeing the feed.

Nothing was published. `Validate tagged release` failed and the build, PyPI and
GitHub-release jobs were all skipped, so no 2.8.3 artifact ever existed.

The pre-tag review that missed it enumerated 99 added string literals and
scanned added prose for person tags and hostnames. It never scanned the
filenames being added. The scanner checks paths in the working tree, in
history, in ref names and in tag names; the review covered contents only. A
review that reports "clean" while a whole category was never looked at is the
same defect this release fixes in the product.

Recovery, in order:

- `#228` renamed the file. Its content was already clean.
- `#229` advanced the reviewed history baseline to the rename commit, because
  history scanning covers paths too and the old path is in `526eda3`.
  Rewriting public history was rejected: that was done for `v2.7.7` and cost
  `v2.7.8`, because force-pushing `main` strips pull-request association by SHA
  and the verifier then refuses those commits permanently.
- The full gate and the artifact test were re-run on the fixed tree. Reusing
  the earlier evidence would have attested to a tree that no longer exists.
- The `v2.8.3` tag was deleted and recreated at the fixed commit. That required
  briefly disabling `version-tag-integrity`, which blocks tag deletion with no
  bypass actors; the ruleset was captured to JSON first, restored immediately
  afterwards, and confirmed `active` before the new tag was created.
