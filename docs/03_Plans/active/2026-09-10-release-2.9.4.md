# Release 2.9.4 - no operator CLI troubleshooting

## Goal

Ship the 2.9 lane's GUI tranche to the customer who reported the problem it
fixes and has not taken 2.9.3. After this release an operator is never told to
run a management command to understand or fix something: every count on the
scope panel is explicable and actionable from the page it appears on, the full
set behind every count is listable, each remediation is a gated button, and a
support bundle carries all of it so a problem we have to look at arrives with
its evidence instead of a screenshot.

## Constraints

- NetBox 4.6.x (tested 4.6.8), `netbox_branching` 1.1.3. This is the 4.6 lane;
  `main` is 4.7 only from 3.0.0, so a 4.6 fix has nowhere else to land.
- No new model, so no migration and no `urls.py` change. `urls.py` includes
  `get_model_urls` wholesale and `@register_model_view` is enough for a view
  hung off an existing model.
- Persisted diagnostics and the support bundle carry schema identifiers,
  primary keys and counts - never device names or collected values. Two report
  keys and five bundle sections were added under that rule.
- Destructive safety is unchanged. The absence quarantine, the survivable-shrink
  refusal, the empty-scope refusal, the cause gating and the active-sync block
  all stay as they are.
- `ForwardDeviceIdentity.device` and `ForwardDeviceTagClaim.device` stay
  `PROTECT`; see the Decision Log.
- The release lane declares itself in `scripts/release_lane.py`, and this
  lane's sensitive-history baseline is now a lane-specific repository variable
  rather than the shared one - see the Decision Log.

## Approach

Three commits, in the order the work has to be trusted in.

`4ff8e66` fixes the release tooling this lane could not release without. The
2.9.3 anchor advance left the provenance fixture verifying the same tag it had
just made the anchor, collapsing two dict keys and pointing every test at the
prior release; thirteen failed on a missing `merge-base` response and
`invoke ci` has been red on this lane since. The tag under test is now the next
release, and a new test asserts it differs from the anchor. The same commit
points this lane's release workflow at its own sensitive-history baseline
variable.

`4321bd5` is the product tranche. The guard lands first, because a rule with no
failing test is a preference: `scripts/check_operator_text.py` refuses
operator-facing text that names a command, with a three-entry allowlist of
deploy-time actions and no grandfather list. Then the four surfaces that fire
during an incident - the uncovered-device prune button, the wedged-sync
recovery control, the blocking/non-blocking split on ingestion issues, and the
two device sets the panel counted but would not list - plus the device-page
panel that explains a refused manual delete, the permission gates the panel
footer was missing, and the summary counts linking to the cards that explain
them.

`52d2dba` makes the support bundle sufficient on its own: `environment`,
`scope_reconciliation`, `delete_blockers`, `operator_action_jobs`,
`ownership_records`, and a blocking-first ordering on the issue rows.

## Rollback

Every product item is additive: two report keys, four views, two job runners,
one device panel, one table column, one filter, one menu item, five bundle
sections, one guard script and its `ci` step. No migration and no data change,
so reverting the three commits is sufficient and leaves no state to clean up.
A deployment that has already used the prune-uncovered button has deleted
devices the previous release could delete too, by command.

The release-tooling half is not rolled back with the product: the lane variable
`FORWARD_SENSITIVE_HISTORY_BASELINE_MAINT_2_9_X` is additive and the shared
variable is untouched, so reverting `release.yml` restores the previous
behaviour exactly.

## Decision Log

- **The 2.9.3 CLI-only decision is reversed deliberately.** Its decision log
  argued that reading dry-run JSON is safer than clicking red. That put the fix
  out of reach of the person who reported the problem, who was looking at a
  panel showing a count and offering nothing to do about it. Danger is managed
  by gates, not by hiding the control.
- **The device FKs stay `PROTECT`.** Cascading them would let a manual or
  merge-time delete drop ownership evidence without the audited release path,
  and that path is the only thing enforcing "another sync claims this device".
  The apply engine also relies on the resulting `ProtectedError` to record a
  skip rather than a failure. The refusal stays and is explained on the device
  page instead.
- **The operator prune does not sweep another plugin's dependent rows.** The
  sync-time prune sweeps what a `ProtectedError` reports and retries;
  `_delete_prunable_devices` releases this plugin's ownership and asks the
  database to delete the device. So a device held by ten `netbox_routing` BGP
  peers refuses the button too. Sweeping here would mean this button deletes
  other plugins' rows - a widening of a destructive path that needs its own
  allowlist and its own decision. Instead the refusal names the model and the
  device panel gives the two-step remedy.
- **The uncovered prune was discarding its protected tally.**
  `_delete_prunable_devices` computes it and the orphan half has reported it as
  `protected_by_model` since 2.5.5; this half dropped it, so a device refused by
  another plugin's rows reported a bare count and named nothing.
- **The sensitive-history baseline is per-lane.** One repository variable
  cannot serve two lanes with disjoint histories, and the refusal lands after
  the tag is pushed. Swapping the shared variable and swapping it back is what
  left this lane broken twice.
- **The delete-blocker survey is bounded in time as well as count.** The cost
  per device is the size of its cascade and the bundle is a synchronous GET; the
  scope panel learned that by returning 504 with its queries still running. A
  partial survey that reports `stopped_on_time_budget` beats a bundle that never
  downloads.
