# NetBox 4.7 compatibility, part one: make the tree detector prove itself

## Goal

Stop `_is_bulk_safe` from silently answering "safe to bulk insert" for models
whose hierarchy it can no longer recognise.

## Why

NetBox `4.7.0-beta1` replaces the deprecated `NestedGroupModel` (django-mptt)
with an ltree implementation. `max_version = "4.6.99"` means the plugin refuses
to load on 4.7 rather than half-working, so nothing is broken today and this is
scheduled work rather than an incident.

The compatibility scan came back clean everywhere except two places, and one of
them is one line:

    return not issubclass(model_class, MPTTModel)

`_is_bulk_safe` decides whether a model may be `bulk_create`d during a merge.
Tree models may not: they recompute hierarchy state on save, and a bulk insert
skips it. Two futures:

  - django-mptt leaves the dependency tree with `NestedGroupModel`. The import
    at the top of `bulk_merge.py` fails, loudly, and someone fixes it. Safe.
  - mptt stays installed as somebody's transitive dependency while NetBox
    models stop inheriting from it. `issubclass` answers False for every former
    tree model, all of them become "bulk safe", and merges corrupt hierarchies
    with no error anywhere.

The second is the one worth engineering against, and it is the same defect
shape this codebase keeps finding: a check reporting a confident answer about
something it is no longer measuring.

## Constraints

- Do not guess 4.7's replacement base class or field names. Nothing here should
  encode a symbol nobody has verified against a real 4.7 runtime.
- Do not fail closed for every model when detection is uncertain. Treating
  everything as a tree disables `bulk_create` on the merge path, which is a
  large regression to buy a hypothetical.
- The plugin must keep working on 4.6.x exactly as it does now.

## Touched Surfaces

- `forward_netbox/utilities/bulk_merge.py` - `_is_tree_model`, `_is_bulk_safe`
- `forward_netbox/tests/test_tree_model_detection.py` (new)

## Approach

Detection becomes two independent positive tests, either sufficient: the
`MPTTModel` base class, and the `{lft, rght, tree_id, level}` column signature
django-mptt adds. The base class is the part upstream can change without
telling us; the columns are likelier to survive a refactor. Neither invents a
4.7 symbol.

That narrows the gap but cannot close it, because an ltree implementation has
neither. So the residual risk is handled by a canary rather than by cleverness:
a test asserts the detector still recognises `Region`, `SiteGroup` and
`Location` as trees in the INSTALLED NetBox, and separately that it does not
just answer "tree" for everything - which would be a safe-looking way to pass
the first assertion. When 4.7 support is attempted, a detector that has stopped
detecting fails the suite instead of shipping.

## Validation

`forward_netbox/tests/test_tree_model_detection.py`: the canary against real
NetBox models, a flat-model control, a synthetic class carrying the mptt
columns without inheriting from `MPTTModel`, and a partial signature that must
NOT count (`level` alone appears on plenty of flat models).

## Rollback

Revert. `_is_bulk_safe` returns to the single `issubclass` test.

## Decision Log

- **A canary, not a prediction.** Encoding a guess at 4.7's ltree base class
  would be untested code that looks like coverage. A test that fails when
  detection breaks is honest about what is known today.
- **Field signature as the second test, not the only one.** The base class is
  exact while it holds; dropping it in favour of columns would trade a precise
  check for a heuristic with nothing gained.
- **Not fail-closed on uncertainty.** Considered and rejected: with mptt absent
  every model would read as a tree, disabling bulk_create on the merge path.
  The canary catches the same condition without the regression.

## Open

- The rest of 4.7: `NestedGroupModelSerializer` on all 8 API serializers, which
  none of our models need - they are flat `ChangeLoggedModel`s, `_depth` is in
  no `fields` tuple, so switching base classes is API-invisible and can be done
  independently of 4.7.
- PostgreSQL 15+ and Redis 6+ minimums for the docs.
- `querystring` -> `querystring_replace`: our templates use neither, but NetBox
  4.6.6 already emits a `FutureWarning` for the tag, so re-grep at port time.
- None of this is reachable by a customer while `max_version` is `4.6.99`.
