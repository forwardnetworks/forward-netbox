# Release 2.6.7 Tranche

## Goal

Ship the convergence, diagnosability and apply-performance work staged after
2.6.6 as a single minor release.

Next release in the 2.6 line. It adds an opt-in apply engine, a release-time
upgrade gate and a new error classification, but every addition is off by
default or invisible until a failure occurs, and nothing requires a migration or
an operator step — so it stays on 2.6 rather than opening 2.7.

## Contract

- Upgrade and re-run the sync. No migration, no configuration change.
- The COPY/SQL apply engine stays **off** unless a sync opts in, and only for
  `dcim.macaddress` on the exact supported runtime.
- Persisted diagnostics still carry schema identifiers only, never key values.
- Every existing apply engine, disposition and count keeps its meaning.

## Constraints

- Keep `netbox_branching` in the ingestion path.
- Do not weaken the tag-only publish trigger or Trusted Publishing scoping.
- Do not enable diff for any model that was NO-GO before this tranche.
- Do not release without the owner's explicit authorization.

## Approach

Three of the seven fixes are the same defect wearing different clothes: a
function written, tested, and never called.

- `protecting_reference_blocked_deletes` had **zero** production call sites, so
  a delete the database would certainly refuse was still attempted and still
  failed the row — and a failed row blocks baseline promotion permanently.
- `structured_failure_diagnosis` was wired into the merge path only, leaving
  every sync-phase failure — the common case — with an exception class name and
  nothing else.
- 2.6.6's density learning shipped the same way and was caught then.

A tested-but-unwired function passes every gate this repository has. That is
worth a standing check before the next release, not a note in one plan.

The remaining work splits into convergence (`8e84efa`, `217cc3a`),
diagnosability (`1b3ba41`, `3210294`) and apply performance (`cbe606d`).

- `invoke artifact-upgrade-test` ran end to end: 2.6.5 installed from PyPI,

Each behavioural change carries a **negative control** — the fix is disabled and
the test is confirmed to fail — because three of these defects were functions
that existed and did nothing, and a test that never fails would not have caught
them.

## Rollback

Every commit reverts independently; none introduces a migration or persisted
state. The COPY/SQL engine additionally has two runtime kill switches
(`enable_copy_sql` off, or `dcim.macaddress` in `copy_sql_kill_switches`), so it
can be disabled without a code change.

## Decision Log

- 2026-07-30: 2.6.7, not 2.7.0. The tranche adds capability, but all of it is
  opt-in or diagnostic, and the supported runtime tuple is unchanged, so it
  belongs in the 2.6 line. (First staged as 2.7.0 and corrected by the owner.)
- 2026-07-30: Promoted the `v2.6.6` row from "Release candidate" to "Current
  release" across all three compatibility tables first. 2.6.6 shipped to PyPI
  and GitHub on 2026-07-30, but `--finish` was killed at a foreground time limit
  *after* pushing the tag, so the promotion step never ran and the docs claimed
  a shipped release was still a candidate.
- 2026-07-30: Two items are deliberately **not** in this release —
  IPAddress Fix B (a 19.3x measured ceiling, but it replaces `full_clean()` with
  a hand-rolled subset, breaks the row-for-row adapter-parity contract that
  function documents, and couples the plugin to NetBox's `get_duplicates()`),
  and diff enablement for Interfaces/BGP/IPv4/Device (needs a live proof run
  against Forward, which requires a full baseline re-ingest first). Both await
  owner sign-off.
