# Release 2.7.3

## Goal

Ship the tranche that came out of one day of customer reports: a sync that died
on a single interface, six issue rows that named nothing, and three ingestions
that would not delete. Plus netbox-dlm `0.7.0`, which the customer released and
runs on the same NetBox.

## Contract

- The four version surfaces move in ONE commit. Splitting them reverts the fast
  baseline from minutes to hours with no error.
- The tag is created locally, provenance verified, and only then pushed.
- The first first-parent commit after the tag is documentation-only. That slot
  cannot be reclaimed.
- No `.devN` is opened on `main` afterwards.

## Constraints

- The prior-release tag is hardcoded in SIX coupled places: `PRIOR_RELEASE_TAG`
  and `PRIOR_POST_RELEASE_DOC_COMMIT` in `verify_release_provenance.py`, the tag
  fetch in `release.yml`, two assertions in `check_harness.py`, a workflow
  fixture in `scripts/tests/test_check_harness.py`, and one in
  `scripts/tests/test_tasks.py`.
- `check_harness.py` reads the real workflow, so it passes while the two
  fixture-based tests fail. Only `python3 -m unittest discover -s scripts/tests`
  catches that pair.
- The plan-file gate is per COMMIT, not per PR.
- `release.py <version> --write` inserts the candidate row itself, and
  `stage_prepare` then refuses with "a release candidate already exists". Reset
  the eight staged files and run the prepare that carries the summary instead of
  trying to patch the empty row.
- No customer identifiers in the release notes: the interface failure is
  described by rule, never by device.

## Touched Surfaces

- `pyproject.toml`, `forward_netbox/__init__.py`,
  `forward_netbox/utilities/fast_baseline.py`,
  `forward_netbox/tests/test_runtime_dependency_check.py`
- `README.md`, `docs/README.md`, `docs/01_User_Guide/README.md`, `CHANGELOG.md`

## Approach

Everything in this release is already on `main` and already ran the full plugin
suite: #144, #145, #146, #147, #148, #149, #150. This change is the version bump
and the release notes; the gate then re-runs the lot against the built artifact.

## Validation

`invoke ci` and `invoke artifact-test` on the pinned environment, then the tag,
then `verify_release_provenance.py` against the local tag before pushing it.

## Rollback

Before the tag is pushed, revert the branch. After it is pushed, the tag is
immutable and the ruleset forbids moving or deleting it — a defect found then
costs a version number, which is why the upgrade gate runs in PR CI rather than
at tag time.

## Decision Log

- **Cut now rather than accumulate.** The customer installs from `main` between
  releases, and `main` declares the released version, so his NetBox reported
  `2.7.2` while running four commits past it. Which commits he had was
  determinable only by correlating his ingestion timestamps against merge times.
- **`#46` and `#54` deliberately excluded.** Device-identity pruning touches
  ownership release, where pruning wrongly drops a claim on a live device;
  scoping the CI trigger changes CI behaviour for the very PR that carries it.
  Neither belongs in a release cut under time pressure.

## Open

- `main` will declare `2.7.3` while accumulating post-release commits again.
  That is the accepted cost of not opening a `.devN`; the next release must bump
  the surfaces as its first post-tag act.
- Two of the three ingestions the customer cannot delete are fixed here. Any
  held by device identities for departed devices are not (#46).
