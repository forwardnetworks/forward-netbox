# Release 3.0.15

## Goal

Make the Scope page say what it counts, close two gaps in the 3.0.14 cleanup, and bring the dependencies current:

- The Scope page no longer shows one "No include tag" figure that mixes two things. "Uncovered: created by this sync" (rows this sync created that no include tag covers) and "Not managed by this sync" (devices in NetBox that belong to no sync) are separate rows; the total is a sentence, not a headline. The support bundle carries both figures under the same labels.
- Two new checklist items explain what operators were reading as defects: devices Forward lists only as generic endpoints that are not imported, and devices that have no primary IP because Forward records none.
- The stale-row removal needs the right to delete every model it deletes, in the UI and the REST API. Before, the change permission on the sync was enough.
- A sync created through the REST API starts with the same primary-IP defaults as one created in the web form.
- The platform restore (3.0.14) also puts back the platform a deleted platform cleared on virtual machines and on config contexts, proved by the same change log. NetBox's `handle_deleted_object` logs each config context whose platform link a deletion removes, so the link is provable. Restoring needs `virtualization.change_virtualmachine` and `extras.change_configcontext` as well as `dcim.change_device`.
- Dependencies: paramiko 5.1.0 (through netmiko 4.8.0; the PYSEC waiver is removed), forward-sdk 0.1.36, cryptography 50.0.2, python-dotenv 1.2.4, build 1.6.1, pymdown-extensions 12.3, and the pinned GitHub Actions.

## Constraints

- No customer names, network ids, snapshot ids, hostnames or addresses in the repo, plans, tests or docs.
- No shipped NQE query change, nothing to republish. No migration.
- No change to what the sync deletes or when: the permission check only narrows who may start the removal.
- `development/constraints-upgrade-from.txt` forward-sdk pin moves 0.1.35 -> 0.1.36 only in the release step.
- The plugin never imports paramiko; it reaches it through netmiko and Validity.

## Touched Surfaces

- Scope page: template, `reconciliation_strip.py`, `bundle_label_index.py`, `bundle_ui_figures.py`, `cleanup_checklist.py`. Plan: `2026-11-09-scope-page-clarity.md`.
- Removal permission: `sync_facade.py` (`button_job_extra_permissions`, `missing_button_job_permissions`), `views.py`, `api/views.py`; tests `test_button_job_permissions.py`.
- API defaults: `api/serializers.py` (`apply_new_sync_primary_ip_defaults` before `super().validate`).
- Platform restore: `utilities/platform_restore.py` (devices and virtual machines); tests `test_platform_restore.py`.
- Dependencies: `pyproject.toml`, `poetry.lock`, CI workflows. Plan: `2026-11-09-dependency-audit.md`.

## Approach

1. Each change landed with tests derived from the symptom and a code-reviewer audit.
2. Full Django suite on the final tree, then `scripts/release.py 3.0.15` through the usual lineage.
3. After the tag nothing needs republishing. The customer upgrades and reads the new Scope rows.

## Validation

- Full Django suite on the merged branch on the test host: 4625 tests OK (33 skipped).
- Live, customer-shaped estate (about 3,900 devices), read-only Forward: a clean-database baseline sync on 3.0.14 merged with 0 failures (3,858 devices, none without a primary IP, none uncovered, stale-row preview 0 removable / 198 held). The Scope page on the 3.0.15 build was checked through the UI with agent-browser, with two temporary test devices that were removed afterwards.
- Dependencies on the rebuilt dev image: paramiko 5.1.0, netmiko 4.8.0, cryptography 50.0.2, forward-sdk 0.1.36, netbox-validity 3.6.1, scrapli 2026.2.20 and dulwich 1.2.14 import cleanly; Paramiko 5.1.0 completed an SSH key exchange against a real sshd from inside the NetBox container; `mkdocs build --strict` passes with pymdown-extensions 12.3.
- Not exercised live: Validity's own SSH device polling and a full sync under the new forward-sdk on a second run (the baseline ran on 3.0.14). Say so in the release notes.

## Release Step

- `development/constraints-upgrade-from.txt` forward-sdk pin stays at 0.1.35: it is 3.0.14's own pin, the release the upgrade gate installs from. It moves to 0.1.36 at the next cut (3.0.16), as the constraint's comment requires. The version bump is written by `invoke release --write`.
- The release-only sensitive-pattern feed cannot be read locally, so the cut runs with `FORWARD_NETBOX_PATTERN_PARITY_UNVERIFIED=1`.

## Rollback

Revert the release. Nothing is migrated; stored states are unchanged.

## Decision Log

- The Scope total stays as a sentence only: a customer read the 128 total (124 not managed + 4 uncovered) as 128 uncovered devices.
- The removal permission check lives in one helper used by both the view and the API, so the two cannot drift.
- Platform restore covers virtual machines and config contexts. NetBox logs both: the platform it clears on a VM, and the config-context update that removes the link when a platform is deleted (verified in `core/signals.py`, `handle_deleted_object`).
- Checked and left as is: the OSPF interface cleanup row carries no `process_id` because the sync keys an OSPF interface on its interface alone and the delete adapter needs only device and interface (an OSPF instance row does carry it). A parent held because its child model was refused or stays is the designed fail-closed answer, not a bug.
