# Release 3.0.13

## Goal

Fix what the first customer bundle from 3.0.12 showed: a device that was another device's BGP neighbour could not be deleted, a long config backup blocked every sync and sync-form save, changing a primary-IP setting did nothing when Forward had no new data, merged routing deletes never reached the change log, and the bundle's issue and primary-IP guidance still left the operator guessing. Collect NetBox's per-row search-index jobs into a few batches. Move the tested runtime to NetBox 4.7.4 and netbox-branching 1.2.3, and forward-sdk to 0.1.35.

## Constraints

- No customer names, network ids, snapshot ids, hostnames or addresses in the repo, plans, tests or docs. Tests use synthetic names.
- No shipped NQE query change, so nothing to republish. No migration.
- The one new stored parameter is a plugin-owned marker, `overlay_rerun_pending`, set when a primary-IP setting changes and cleared once the step has run.
- The delete fix keeps every address and BGP peer: it only takes the address off the deleted device's interface. Nothing outside the selected devices' own addresses is touched.
- The support bundle stays name-free.
- `development/constraints-upgrade-from.txt` forward-sdk pin moves to 0.1.31 only in the release step, after the version bumps (the pre-push upgrade gate reads it).

- Change log: `merge.py`, `sync_events.py` (reset NetBox's per-thread delete memory before a merge).
- Search jobs: `search_batching.py`, wired into `jobs.py` (`sync_forwardsync`, `merge_forwardingestion`, `ForwardJobRunner.handle`).
- Guidance: `cleanup_checklist.py`, `primary_ip_reasons.py`, `skip_reason_catalogue.py`, `sync_routing_static.py`, `sync_reporting.py`, `views.py` issue summary.

- Runtime: `scripts/tested_runtime.py`, `development/`, `tasks.py`, release and artifact validators, `constraints.txt`, `poetry.lock` (NetBox 4.7.4, netbox-branching 1.2.3).

## Approach

1. Land each fix with tests derived from the customer's symptom, reproduce the missing change-log rows with a real-branch test first, and run a code-reviewer audit on the delete and lock changes.
2. Run the full Django suite on the final tree, then `scripts/release.py 3.0.13` through the usual lineage.
3. After the tag nothing needs republishing; the customer upgrades, saves the setting and re-runs.

## Validation

- Real-branch test: a staged routing delete is in the main change log by request id (failed before the fix, 29 tests pass after).
- Real-branch test: a no-change run with a pending primary-IP setting provisions a branch, runs the step, merges and clears the marker; without the marker it stays branchless.
- `invoke ci` on NetBox 4.7.4 with netbox-branching 1.2.3 via `scripts/release.py`, including the artifact and upgrade legs.
- Real-savepoint test: 30 saves each in their own savepoint queue one search-index batch, not 30.
- Not verified: the search batching against a real worker and Redis under production load, the new pages in a browser, and the delete with a netbox-branching branch active in production.

## Rollback

Revert the release. Nothing is migrated. The marker is ignored by older plugins' validation only if they predate it, so roll back before changing a primary-IP setting.

## Decision Log

- Profiled the merge of a customer-shaped sync (about 900,000 changes): the database was nearly idle and one worker core was saturated. 84% of the samples sat on one bookkeeping line in `bulk_merge._record_result`, `required.issubset(component_results)`. Given a dict that grows by one entry per merged change, it cost time proportional to everything merged so far, so the merge slowed as it went (83 then 66 changes a second) and was quadratic overall: in the same shape, 129 seconds per 50,000 calls at 300,000 entries against 0.02 seconds for direct membership. Replaced with a per-key membership test (one or two keys).

- Profiled during the customer-shaped sync: about 60% of the database's busy time while staging was two lookups repeated for every saved row, the object type and the custom fields of the row's model. NetBox caches both in `netbox.context.query_cache`, which it sets for a request and for its own script and job runs; the sync's staging ran outside it. Plugin jobs now set the same per-run cache. Both are definitions the sync does not change; NetBox accepts the same staleness for its own jobs.

- Found by running 3.0.13 against a real customer-shaped database: NetBox 4.7.4's `extras.0145_taggeditem_object_id_bigint` failed on an existing install because the plugin's device guard trigger was declared `UPDATE OF content_type_id, object_id`, which pins those columns. Fresh test databases never hit it. The guard is rebuilt without a column list (the function returns early when an update leaves both columns unchanged), by migration 0068 and by a `pre_migrate` hook that runs before any app's migrations, so an upgrade works whatever order Django picks. Ordering 0068 before NetBox's migration with `run_before` was rejected: it would make an install already on 4.7.4 refuse to migrate.

- The release-only sensitive-pattern feed is a GitHub secret and cannot be read locally, so the cut runs with the parity bypass.
- NetBox 4.7 defers search indexing per savepoint scope, so the plugin's per-row savepoints queued thousands of "Search cache update" jobs. The plugin's jobs now replace `netbox.search.deferred._flush`, which NetBox calls only for COMMITTED work, merge those batches per database alias and hand them to the real flush in 5000-entry chunks. A first version collected at `mark_for_deferred_indexing`, before the transaction outcome was known; a reviewer showed a rolled-back delete would still have removed the object from search, so it was rebuilt on the commit side, with a test for exactly that. A branch schema dropped by an auto-merge before the job ends is skipped rather than enqueued against nothing.
- A device that is another device's BGP neighbour is kept consistent by detaching the address, not deleting the peer, matching how the plugin already models a neighbour address it cannot place on an interface.
- A full sync of a customer-shaped estate left 274 devices without a primary IP after context copies. Read-only Forward checks split them four ways, none a sync failure: SNMP endpoints (console servers) were never read by the step, which queried only modeled devices; FortiGates with two management addresses (mgmt1, mgmt2) were refused as ambiguous although Forward's collection IP is always one of them; devices whose management address Forward records on no interface (a Palo Alto's management port, FortiGates Forward models with no interfaces); and vdoms whose chassis holds the address on `mgmt`, which the vdom lacks. The first two now use Forward's own collection IP. The last two have nothing in Forward to attach the address to, so an opt-in `add_management_interface` adds a tagged, virtual, management-only interface carrying it. An interface the sync did not add is never taken over, and an address NetBox already holds elsewhere is never moved or duplicated. No sync deletes these interfaces, because every staged delete comes from a Forward row.
- The same run showed a pending primary-IP setting still skipped as "snapshot unchanged" before reaching the branch stage. That is the earlier no-op check in `should_skip_unchanged_snapshot`, not the one the marker already covered. It now runs when the marker is pending, which is what the customer saw as "it doesn't appear to have done anything".
