# 2.6.5 Full Tranche

## Goal

Clear the deferred backlog in one release: protected-delete ordering, diff
enablement for the models it blocks, the three proven performance engines, and
the remaining smaller items.

2.6.4 shipped the query-ID binding correction and is treated as burned; 2.6.5
is the substantive release.

## Sequencing

Dependency-first, because correctness work must land before the large
performance diffs destabilise it:

1. **Protected-delete convergence** (gating). Unblocks item 2.
2. **Delete-correctness comparator** from the diffproof tree. Needed to trust
   item 1 and to validate item 3.
3. **Diff enablement** for the models item 1 blocks.
4. **Performance engines** - set-based merge, then COPY/SQL staging. Largest
   and most conflict-prone; land last.
5. **Smaller items** and release.

## Scope and current state

### 1. Protected-delete convergence (gating)

Canonical delete intent is exact: 1,434 expected, 1,434 matched, 0 spurious, 0
missing. Physical convergence still fails: Device 6 to 5, Interface 561 to 559,
IPAddress 54 to 63 (of which +9 is a legitimate HSRP VIP cascade).

**This is not purely an ordering problem.** The Device failure is a
`ProtectedError` with *two surviving BGP peers* - children that were never
scheduled for deletion, so no reordering can succeed. The fix must decide, per
protecting relation, whether the child is in scope and should be deleted, or
the parent delete is genuinely not permitted and must be reported rather than
attempted.

The proven ordering pattern for the simpler case is
`_add_destination_fk_release_dependencies` in `bulk_merge.py`: batch-read
destination FK values, restore only the missing release edges, and let an
UPDATE that retains its reference still fail strictly. Generalising it needs
the same discipline. A partial, unverified generalisation was reverted before
the 2.6.2 gate; redo it against the validation harness with real data, not by
inspection.

#### Root cause found: the missing edge is an ordering gap, not a policy gap

`SquashMergeStrategy._build_fk_dependency_graph` step 3 builds its
child-before-parent DELETE edges out of each child's `prechange_data`:

```
# 3. Check DELETEs for dependencies on other DELETEs
for delete in deletes:
    if delete.prechange_data:
```

Branch-native bulk DELETE ObjectChanges can carry an **empty `prechange_data`**
when the row came from the direct first-baseline path - the identical gap
`_add_destination_fk_release_dependencies` already exists to close for UPDATEs.
The edge is therefore never created, the parent DELETE is attempted while a
child row still references it, and the database refuses it with `ProtectedError`.
The parent survives, and every later sync repeats the failure. That is how a
device kept two BGP peers and never converged.

`_add_protected_child_delete_dependencies` closes it the same way the UPDATE
case was closed: read the protecting references from the **destination**, which
needs no branch preimage, and restore the missing child-before-parent edges.

This is a genuine convergence fix rather than the suppression previously
contemplated. Suppression would have changed nothing - the existing fallback
already records a refused delete as a failure with accounting intact - whereas
the edge makes the delete actually succeed. It also needs no accounting change
at all, which removes requirement 2 below.

A reference whose row *survives* the run deliberately gets no edge, so a delete
the database genuinely must refuse still fails strictly instead of being
reordered into a false success.

**Cycle safety.** `_order_collapsed_changes_fast` raises on a cycle and aborts
the entire merge, and an edge added here once caused exactly that in the LAG
case. `_acyclic_delete_edges` therefore Kahn-sorts the candidate set first and
drops any edges touching a cycle, logging what it dropped. Mutually protecting
rows are undeletable by the database anyway, so dropping the edge only returns
that pair to the failure it would have had regardless - never to a lost merge.

Verified: removing the wiring makes
`test_child_delete_is_ordered_before_the_parent_it_protects` fail with
`AssertionError: 1 not less than 0`.

#### Earlier progress: detector landed, wiring deferred

`protecting_reference_blocked_deletes` in `bulk_merge.py` identifies deletes the
database will refuse: it walks each delete target's reverse PROTECT/RESTRICT
relations, batch-reads referencing rows, and reports only those whose
referencing row is *not* itself being deleted in the run. Seven tests, including
a real parent/child pair that asserts the relation is PROTECT before asserting
the block, and the converse case where deleting the child unblocks the parent.

Wiring it into the merge was attempted and **backed out**, because a full-suite
run surfaced two requirements the detector alone does not satisfy:

1. **In-run FK release must count as non-blocking.** The detector reads current
   destination state, so it flagged the case
   `test_dlm_protected_version_delete_follows_destination_fk_reassignment`
   covers: an UPDATE in the same run moves the reference away and the protected
   delete then succeeds. Suppressing it is a false positive. The check must
   consult `postchange_data` for the referencing field the way
   `_add_destination_fk_release_dependencies` already does, and treat a
   retained reference as blocking but a released one as clear.
2. **Suppressed deletes must be accounted.** Dropping entries from
   `to_process` broke the merge accounting invariant
   (`Bulk merge returned without accounting components`). A suppressed delete
   has to be recorded as a reported non-application, not silently removed.

Landing the detector without the wiring is deliberate: an unverified
generalisation of this exact behaviour was reverted before the 2.6.2 gate, and
repeating that is worse than an extra increment.

Interfaces - the 535,777-row win - entered Tier 2 with the ownership sets added
in #94, alongside the BGP trio and the Tier 3 IP-address reducer. Nothing to do.

The two that remain are **not blocked on item 1**. Each carries its own
correctness gate, recorded in `_query_diff_ownership_mode`:

- `forward_devices*.nqe`: device revisions combine modeled devices with endpoint
  candidates; exact collision and endpoint feature parity are not live-proven.
- `forward_aci_apic_cimc_inventory.nqe`: the parameterless draft exposes
  contributor selectors before a select-distinct reduction, so a changed
  contributor delta cannot prove an unchanged alternate controller preserves the
  final row.

Both gates need live proof, not a flag flip. Enabling either without that proof
would silently corrupt device or inventory data for every customer, so they stay
blocked and move to the 2.6.6 backlog.

  also merge profiling and observability work. 50 files, +4,910/-637, 35

- `~/forward-netbox-copysql-backup-20260727` - COPY/SQL staging engine, 8.98x
  on MAC. 41 files, +3,986/-534, 14 untracked.
- `~/forward-netbox-diffproof-backup-20260727` - item 2 above. 55 files,
  +6,110/-405, 24 untracked.

The raw diff stats above are inflated: the backups sit four releases behind, so
main's later work counts as difference. Measured per line with `diff -u`, the
genuinely outstanding work is **about 1,411 lines for set-based merge and 719
for COPY/SQL**, not 15,000.

Both still touch the merge and apply-engine paths rewritten for 2.6.4, so each
engine is ported and validated independently. A bulk port risks silently
reverting the query-ID binding fix.

## Constraints

- Keep `netbox_branching` in the ingestion path.
- Audit NQE call volume on every sync-path change; Forward engineering has
  raised unnecessary query execution.
- No silent scope reduction: an engine that cannot be validated is not landed.

## Coverage lesson carried in

The 2.6.3 and 2.6.4 failures shipped because every test fixture fabricated a
repository listing row *containing* `lastCommitId`, which the live org listing
never returns. Mocks were more permissive than the API. Fixtures added here
must mirror observed live responses, and any new client interaction needs at
least one test whose fixture is copied from a real payload.

## Validation

Each item lands with its own gate run and its own tests. The release is
authorized only on the final tree.
