# 2.6.5 Full Tranche

## Goal

Clear the deferred backlog in one release: protected-delete ordering, diff
enablement for the models it blocks, the three proven performance engines, and
the remaining smaller items.

2.6.4 shipped the query-ID binding correction and is treated as burned; 2.6.5
is the substantive release.

## Sequencing

Dependency-first, because correctness work must land before the large
performance diffs destabilise it:

1. **Protected-delete convergence** (gating). Unblocks item 2.
2. **Delete-correctness comparator** from the diffproof tree. Needed to trust
   item 1 and to validate item 3.
3. **Diff enablement** for the models item 1 blocks.
4. **Performance engines** - set-based merge, then COPY/SQL staging. Largest
   and most conflict-prone; land last.
5. **Smaller items** and release.

## Scope and current state

### 1. Protected-delete convergence (gating)

Canonical delete intent is exact: 1,434 expected, 1,434 matched, 0 spurious, 0
missing. Physical convergence still fails: Device 6 to 5, Interface 561 to 559,
IPAddress 54 to 63 (of which +9 is a legitimate HSRP VIP cascade).

**This is not purely an ordering problem.** The Device failure is a
`ProtectedError` with *two surviving BGP peers* - children that were never
scheduled for deletion, so no reordering can succeed. The fix must decide, per
protecting relation, whether the child is in scope and should be deleted, or
the parent delete is genuinely not permitted and must be reported rather than
attempted.

The proven ordering pattern for the simpler case is
`_add_destination_fk_release_dependencies` in `bulk_merge.py`: batch-read
destination FK values, restore only the missing release edges, and let an
UPDATE that retains its reference still fail strictly. Generalising it needs
the same discipline. A partial, unverified generalisation was reverted before
the 2.6.2 gate; redo it against the validation harness with real data, not by
inspection.

### 2. Delete-correctness comparator

Held in `~/forward-netbox-diffproof-backup-20260727`: a single canonical
namespace `SHA256(canonical_row_identity(...))` plus 27 tests. The current
comparator mixes canonical and legacy hashes and returns invalid verdicts, so
this must land before item 1's results can be trusted.

### 3. Diff enablement

Already cleared: 12 Tier 1 contracts, Modules, OSPF Instances, OSPF Interfaces,
MAC. Blocked on item 1: **Interfaces (535,777 rows, the largest win)**, BGP
Peers, BGP AF, BGP Peer AF, IPv4 addresses, Device.

### 4. Performance engines

Both proven and both held outside the repository, based on 2.6.1-era main
(`8707c27`) as uncommitted working trees:

- `~/forward-netbox-merge-backup-20260727` - set-based merge, 14.17x on MAC
  with full paired-branch equivalence including conflicts and concurrent main;
  also merge profiling and observability work. 50 files, +4,910/-637, 35
  untracked.
- `~/forward-netbox-copysql-backup-20260727` - COPY/SQL staging engine, 8.98x
  on MAC. 41 files, +3,986/-534, 14 untracked.
- `~/forward-netbox-diffproof-backup-20260727` - item 2 above. 55 files,
  +6,110/-405, 24 untracked.

Roughly 15,000 insertions across about 150 files, on a base four releases
behind, with overlapping touch surfaces in the merge and apply-engine paths.
Porting is real conflict work and must be validated per engine, not in bulk.

## Constraints

- Keep `netbox_branching` in the ingestion path.
- Audit NQE call volume on every sync-path change; Forward engineering has
  raised unnecessary query execution.
- No silent scope reduction: an engine that cannot be validated is not landed.

## Coverage lesson carried in

The 2.6.3 and 2.6.4 failures shipped because every test fixture fabricated a
repository listing row *containing* `lastCommitId`, which the live org listing
never returns. Mocks were more permissive than the API. Fixtures added here
must mirror observed live responses, and any new client interaction needs at
least one test whose fixture is copied from a real payload.

## Validation

Each item lands with its own gate run and its own tests. The release is
authorized only on the final tree.
