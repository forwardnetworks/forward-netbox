# Say why there are fewer config files than devices

## Goal

A customer asked why the repository held 2,744 configuration files for 4,286
devices. The support bundle's config backup section carried only the last run's
status and failure stage, so it could not explain a shortfall, and Health said
only that the data source had synced. Record what each backup run found - how
many managed devices Forward returned a configuration for and how many it did
not - and show it in Health and the bundle in plain words, next to the exact
Validity path for the folder in use.

## Constraints

- Counts, ids, timestamps and short reason tokens only. No configuration text,
  no device names, no warnings text (they can name devices).
- The backup job already stores `ConfigBackupResult.as_dict()` in its job data
  on success; Health simply never read it. This reads it rather than adding a
  second store, so there is no migration and no new source or sync parameter.
- A run that found the snapshot already backed up records zeros, and reporting
  those as "the last backup wrote nothing" would hide the run that did the work.
  The newest run that actually fetched is the one reported; the newest run's
  own skip reason is shown beside it.
- "No result" must not read as "nothing was produced". A sync with no config
  backup job row (never run, or removed by NetBox's job retention) says so and
  says how to record one from the sync page.

## Touched Surfaces

- `utilities/config_backup.py`: `scoped_devices`, `scoped_without_config` and
  `files_in_folder` on the result, counted during the fetch.
- `utilities/health.py`: `_last_config_backup_run` reads the recent jobs and
  returns the last fetching run's whitelisted counts; the plain-words sentence;
  the Health card data (`config_backup`); the delivery bundle payload; the
  delivery check message.
- `templates/forward_netbox/forwardsync_health.html`: a Config Backup card.
- `tests/test_config_backup_result_evidence.py`.

## Approach

During the fetch, count the distinct managed devices (the sync's identities the
fetch was scoped to) for which a configuration came back. Managed devices minus
that is the number Forward has no collected configuration for. Record it with
the number of files in the backup folder of the repository head after the run.

Health turns the last fetching run into one sentence: "Forward returned a
configuration for 2,744 of 4,286 managed devices in the last backup; 1,542 have
no collected configuration in that snapshot (their collection failed or is not
supported), so no file exists for them." A run recorded before the scope was
kept falls back on written plus unchanged against the managed devices there are
now. The card also shows the counts, the snapshot and commit, and whether
Validity's `device_config_path` matches the folder, with the exact value to set.

The customer bundle's empty `last_run_status` means the job lookup found no
backup job for the sync: the lookup matches by sync and the job name, and a
successful run stores its result there, so an empty status is a missing job row
(never run, or removed by job retention), not a run that produced nothing. The
payload now carries `config_backup_jobs_found` so the two cases read differently.

## Validation

- `test_config_backup_result_evidence`: the run records devices with no
  configuration, an unmapped row does not count as a managed device with one,
  files from earlier runs count toward the folder, the sentence and the
  fallback, a skipped later run does not hide the working one, only counts reach
  the payload, the card and the rendered Health tab, and the bundle.
- The existing config backup and Health tests.
- Full `invoke ci` before merge.

## Rollback

Revert the commit. Nothing is persisted outside the job data the backup already
wrote.

## Decision Log

- **Read the job data, do not add a second record.** A separate store would need
  a migration or a sync parameter and would drift from the job it copies.
- **The sentence goes on the delivery check without changing its status.** A
  device Forward never collected a configuration for is not a delivery fault,
  and turning the check to a warning for every such estate would be noise.
- **The bundle keeps the delivery payload value-free.** The folder is a boolean
  there; the exact path appears on the Health card, as the operator's own
  device_config_path does in the check messages.
