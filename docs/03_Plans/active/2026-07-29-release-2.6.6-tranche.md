# 2.6.6 Tranche

## Goal

Close the customer-visible failures found while supporting a 2.6.5 upgrade, and
remove the structural reasons they were hard to diagnose. Most of this release
is diagnostics: the recurring defect was not that the system behaved wrongly but
that it knew things and refused to say them.

## Scope

### 1. A shared DLM catalogue row could be created twice in one branch

Four `netbox_dlm.cve` `IntegrityError` rows failed at merge on a customer
instance, blocking the baseline. Because a partial merge is retryable but the
failure is deterministic, every retry failed identically.

Three defects had to line up:

1. `netbox_dlm.cve` was absent from `MODEL_CONFLICT_POLICIES`, while every
   comparable natural-key catalogue (`dcim.site`, `manufacturer`, `platform`,
   `devicetype`) carried `reuse_on_unique_conflict`.
2. `reuse_on_unique_conflict` only caught `IntegrityError`. `full_clean()`
   checks uniqueness in Python *first* and raises `ValidationError`, so the
   policy had never worked on the common path — for any model using it.
3. `_coalesce_update_or_create` hard-coded `conflict_policy="strict"`, so every
   direct caller bypassed the policy table. That included `ensure_dlm_cve`, the
   create-if-missing safety net invoked from the vulnerability path, while the
   CVE map's own apply went through `coalesce_upsert` and did honour the policy.
   The same model therefore behaved differently depending on which path reached
   it — exactly how a branch ends up with two rows for one `cve_id`.

**The fix must be at staging, not merge.** `Vulnerability.cve` is an inbound FK,
so converging a duplicate by natural key at merge would strand every branch-side
vulnerability pointing at the discarded pk. That is why
`_resume_existing_create` resolves by pk only; it is a deliberate safety
property. Preventing the duplicate is the only safe place.

Each defect is independently guarded: reintroducing (2) or (3) fails the suite.

**Caveat carried deliberately:** this is consistent with all available evidence
but has not been reproduced against the reporting instance. It is a real defect
with real guards regardless of whether it is *their* defect.

### 2. Head resolution failed for a query that had been moved

Moving a query to another folder does not rewrite its history: commits made
before the move still record the old path. Head resolution asked for the
query's *current* path at each historical commit, which the API answers with
404, so no revision produced verifiable source and the contract refused the map
as `unresolved_full_commit`.

Candidates are now `(commit, path)` pairs, trying the path recorded on the
commit first and the current bound path second, so an unmoved query is
unaffected. Verified against a live repository before changing anything.

### 3. Ingestion delete was missing (regression since 2.6.3)

The 2.6.3 fix for a `NoReverseMatch` crash removed the delete *action* rather
than registering the view it pointed at, leaving ingestions undeletable.
`delete` and `bulk_delete` are registered, the table offers the action again,
and `ForwardContributorBaseline`'s PROTECT relation is reported by name and
count instead of surfacing as a 500. Bulk delete skips protected rows and
reports them rather than abandoning the selection.

### 4. Merge failures discarded their own diagnosis

Merge issues persisted only the exception class and an empty `raw_data`. The
four CVE failures above could therefore not be diagnosed from the GUI, the API,
the CLI, or a support bundle. `structured_failure_diagnosis` now records schema
identifiers — constraint, table, column, invalid field names.

The redaction line is drawn deliberately and tested: those identifiers are
defined by the plugin, whereas the key *values* a Postgres DETAIL line embeds
are not captured, and anything failing the safe-token pattern is dropped rather
than assumed safe.

Ingestion issues are also reachable now — the list truncated the message and
offered no way to open a row.

### 5. The contract preflight reported a healthy binding as a failure

`unresolved_full_commit` was raised as a hard failure whenever a map had no
stored commit. That is the normal resting state for a query-ID or path binding,
because head resolves at sync time and is never written back.

Two support bundles from the same instance proved it: 32 of 32 maps reported
this both while the sync applied nothing AND after the same sync applied 24,748
changes. A signal identical when broken and when healthy cannot gate a sync.

It is now informational, and the message explains why rather than prescribing a
remedy. Genuinely blocking issues still fail, and one blocking issue among any
number of benign ones still fails the check.

An earlier attempt in this same tranche made the message *more* confident before
establishing it meant anything; that is recorded here because the correction is
part of the change.

### 6. Scope reconciliation ran two live NQE queries during page load

The view called `compute_scope_reconciliation` inline on GET, which issues two
`fetch_all` queries — every device and every endpoint. A customer hit a 504
after about 30 seconds with the queries still running, and every page load
reached Forward, which is the call volume Forward engineering has asked us to
reduce. It now runs as a background job with the page rendering the stored
result, mirroring `DependencyPreviewJob`.

### 7. Model change density was never learned

`set_model_change_density` had zero production call sites. The learning
machinery — Welford variance, confidence scoring, safety factors, budget
widening — was fully built and permanently handed an empty map, so every
deployment sized row budgets from the hardcoded `DEFAULT_MODEL_CHANGE_DENSITY`
table forever. Three independent bundles confirm it: `model_count=0`, all 29
models on `default_density`.

Density is now measured per plan item. Two properties had to be right, because a
wrong value is worse than an admitted guess:

- **Attribution**: changes per row *of that workload*. Grouping by the changed
  object's content type credits a cable's terminations to
  `dcim.cabletermination`, measuring ~1.0 for a model whose real density is 3.0.
- **Denominator**: rows actually *written*. On a steady-state sync most
  submitted rows are unchanged, so dividing by all of them yields a density near
  zero, which *widens* the row budget and lets a shard exceed the change budget
  it exists to enforce.

An observation that cannot be trusted is rejected, not learned: zero rows, zero
changes, or a ratio outside the clamp range leave the learned density untouched.

### 8. Release flow

- `stage_prepare` bumped only two of the four version surfaces, leaving the
  fast-baseline runtime pin and the runtime version test behind. That drift cost
  the 2.6.3 release six full gate runs, and the fast-baseline pin is
  load-bearing. All four now move together and a missing surface is an error.
- `--open-next` marks `main` as `X.Y.Z.dev0` after a release ships, so an
  install from `main` is self-describing rather than indistinguishable from the
  published release. A customer installed from `main` inside that window and
  reported running a version PyPI did not yet have.
- The preflight now checks the plan's evidence base commit against
  `origin/main`. Authorization binds the tagged commit to its parent, and a
  squash merge means a branch-side value can never match once merged; 2.6.5 lost
  an extra PR and a full CI cycle to a one-line correction.

**Explicitly rejected:** moving the tag push after artifact upload.
`release.yml` triggers on `push: tags: v*` and states the intent directly —
*"Only a version tag can publish; there is no manual gate-bypass route."*
Reordering requires `workflow_dispatch`, creating exactly the bypass the control
exists to prevent, and would not have prevented the incident because the install
came from `main` rather than from the tag.

### 9. A deterministic row failure was a permanent dead end

Any failed row returns the branch to READY and never calls
`_attest_branch_merged`, so `merge_applied_at` stays null. That also disqualifies
`resume_post_merge_bookkeeping`, which requires that evidence. The only exit is a
retry with zero failures — and when the failure is deterministic, that retry
never arrives.

Observed live: **5 failed rows out of 24,748** held an otherwise healthy instance
in a permanent partial state. Drift *Not measured*, ownership *Incomplete*, no
diff-based syncs. Every symptom on that Health page traced to those 5 rows.

`accept_reported_failures` completes the merge over recorded failures, reachable
from an **Accept failures & merge** button on the ingestion page and from
`forward_accept_merge_failures` for support. The safety properties are the point:

- Never automatic — it defaults False at every hop from view through
  `enqueue_merge_job`, the merge job, `sync_merge`, `sync_merge_ingestion`, to
  `merge_branch`, and a test asserts the defaults.
- Failures stay recorded; accepting stops them blocking, it does not erase them.
- The acceptance is written to durable evidence *before* attesting — who, when,
  how many, which issue ids — so an accepted-over baseline can never be mistaken
  for a clean one. Without that this becomes the 2.6.4 defect in a new costume.
- Offered only when genuinely stalled: branch staged, baseline not promoted,
  failures recorded. It is a separate control with its own confirmation, so it
  cannot be reached by clicking Merge twice.

It was first built as a command only. That was corrected: a remedy needing
container shell access is not reachable by the operator whose instance is stuck.

### 10. Misleading drift remediation

The drift check stated flatly that *"folder and repository path changes do not
require rebinding"*, which reads as a guarantee and sent a live investigation
down the wrong path. It now says why a move is tolerated and what genuinely does
require rebinding.

## Constraints

- Do not weaken the tag-only publish trigger or Trusted Publishing scoping.
- Keep `netbox_branching` in the ingestion path.
- Persisted diagnostics must not carry customer data; schema identifiers only.
- Audit NQE call volume on every sync-path change.

## Approach

Evidence before code. Four root-cause hypotheses were tested and discarded
during this work — a dropped `query_id`, stale published source, a folder move,
and a coalesce/constraint mismatch — each killed by a measurement rather than an
argument. Two of this tranche's own changes were then corrected after evidence
contradicted them.

Every behavioural fix lands with a guard verified by reintroducing the defect
and confirming the guard fails.

## Validation

Full `invoke ci` on the final tree. Each item additionally carries targeted
tests. Items 1, 4 and 7 include guards proven by reverting the fix.

## Rollback

Each item is a separate commit and reverts independently. No migration is added.

The one change with reach beyond its own feature is item 1: it alters
`coalesce_update_or_create`, the shared upsert path for every model. It is
deliberately narrow — the ValidationError path proceeds only when every error
code is `unique`/`unique_together`, and policy resolution changes behaviour only
for the models named in `MODEL_CONFLICT_POLICIES` — but a revert of that commit
restores the previous behaviour wholesale if needed.

Two limits are recorded deliberately rather than resolved. The DLM catalogue
root cause is strongly supported by the customer's own counts - 44 pending CVE
rows already present in `main` and 5 duplicated within the branch - but was not
reproduced against that instance. And the single `dcim.device` `ValidationError`

it diagnosable, and makes it non-terminal via the accept-failures control, which
is what restores baseline promotion whether or not the underlying row is ever
corrected.
