# 2.6.6 Tranche

## Goal

Close the customer-visible regression reported against 2.6.5, and remove
two structural defects in the release flow that this release cycle exposed.

## Scope

### 1. Ingestion delete is missing from the UI (regression since 2.6.3)

Reported by a customer on 2026-07-29 against 2.6.5: *"as of 2.6.4 the ingestion logs
can no longer be deleted."* Correct, and it predates 2.6.4 - it went in 2.6.3.

`ForwardIngestionTable.actions = columns.ActionsColumn(actions=())` in
`tables.py`. The 2.6.3 fix for the `NoReverseMatch` crash on the Ingestions list
removed the delete *action* rather than registering the view that was actually
missing. `ForwardIngestion` registers no `delete` or `bulk_delete`
`register_model_view`; `ForwardDeviceAnalysis`, the comparable read-only
overlay, registers both and correctly offers `actions=("delete",)`.

**Not a one-liner.** Four relations point at `ForwardIngestion`:

| Relation | `on_delete` |
| --- | --- |
| `ForwardMergeAttempt.ingestion` | CASCADE |
| `ForwardWorkloadState.ingestion` | CASCADE |
| `ForwardIngestionIssue.ingestion` | CASCADE |
| `ForwardContributorBaseline.ingestion` | **PROTECT** |

An ingestion carrying a contributor baseline is refused at the database. The
restored view must report that as an explicit, actionable message rather than a
500 - `describe_protecting_references` in `bulk_merge.py`, added in 2.6.5, does
exactly this job and should be reused rather than duplicated.

### 2. Release authorization forces a redundant rebind PR

Authorization binds the tagged commit to its parent. The release plan records
the evidence base commit while still on the release branch, so it records the
*branch-side* parent. A squash merge gives the release a different parent on
`main`, so the recorded value can never match once merged, and the release
cannot be tagged until a second PR corrects it.

That cost 2.6.5 an extra PR (#103) and a full ~40-minute CI cycle for a
one-line change, and it is not a one-off: it happens on every release that
squash-merges, which is all of them.

Fix: record `origin/main`'s current HEAD, which is the commit the squash will
land on, instead of the branch-side parent.

### 3. `main` carries an unpublished release

`main` holds the release from the moment the release PR merges - by
construction, before the tag exists and before anything reaches PyPI. For 2.6.5
that window was 12:08 to 13:46 UTC, and a customer installed from `main` inside
it, reporting an upgrade to a version PyPI did not yet have.

**Explicitly rejected:** moving the tag push to after artifact upload.
`release.yml` triggers on `push: tags: v*` and states the intent directly -
*"Only a version tag can publish; there is no manual gate-bypass route."*
Trusted Publishing is scoped to that workflow and the `pypi` environment.
Reordering requires `workflow_dispatch`, which creates precisely the manual
bypass route the control exists to prevent. It would also not have prevented
what happened, because the install came from `main`, not from the tag.

Fix instead: carry a `.dev` suffix on `main` until the tag lands, so an install
from `main` is self-describing as not-the-release. Owner decision 2026-07-29.

## Constraints

- Do not weaken the tag-only publish trigger or the Trusted Publishing scoping.
- Keep `netbox_branching` in the ingestion path.
- The `.dev` marker must not break the four version surfaces
  `scripts/check_release_preflight.py` enforces.
- Deleting an ingestion must never leave merge bookkeeping inconsistent.

## Touched Surfaces

- `forward_netbox/tables.py` - restore the ingestion delete action.
- `forward_netbox/views.py` - register `delete` and `bulk_delete` for
  `ForwardIngestion`, with the protected-reference path reported.
- `scripts/release.py` - evidence base commit binding; `.dev` handling.
- `scripts/check_release_preflight.py` - tolerate the `.dev` marker.
- Tests for each of the three.

## Approach

Smallest-first, each landing with its own guard and each verified by removing
the fix and confirming the guard fails.

Items 2 and 3 are release-flow changes, so they cannot be fully proven until the
next release actually runs. Each therefore lands with a unit-level guard over
the pure logic (which parent is recorded; how a `.dev` version is parsed and
compared) rather than a claim that the end-to-end flow is proven.

## Validation

Full `invoke ci` on the final tree. Each item additionally carries targeted
tests. The ingestion-delete work must include the PROTECT case against a real
`ForwardContributorBaseline` row, not a mock.

## Rollback

Each item is a separate commit and reverts independently. None adds a
migration. Reverting item 1 returns the delete action to absent; reverting 2 or
3 returns the release flow to its current behaviour, including the redundant
rebind PR.

## Decision Log

- 2026-07-29: owner directed the ingestion-delete regression plus both
  release-flow fixes into 2.6.6.
- 2026-07-29: tag-after-artifact reordering rejected - it requires a
  `workflow_dispatch` bypass of the tag-only publish control, and the 2.6.5
  install came from `main` rather than from the tag, so it would not have
  prevented the reported incident.
