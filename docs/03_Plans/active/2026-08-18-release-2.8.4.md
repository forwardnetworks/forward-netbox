# Release 2.8.4

## Goal

Ship the fix that makes the drift report usable on a converged estate, plus
three corrections to the release machinery that this release's own predecessor
exposed.

## Why

`2.8.3` shipped hours earlier and did not fix what a deployment actually
reported. Its drift-report work made the report *self-describing* - it said how
many models it compared and named the ones it could not - and that honesty is
what made the real cause findable. The cause itself was fixed after the tag, so
it needs a release to reach anyone.

## Constraints

- A patch. Nothing changes shape, nothing gains an operator control, and the
  one behavioural change makes a report accurate rather than altering what a
  sync does.
- `max_version` stays `4.6.99`. See the 4.7 section: the block is now measured.
- The four version surfaces move together with the fast-baseline runtime pin,
  through `scripts/release.py`.

## Touched Surfaces

Landed across five pull requests:

- `#238` drift is measured against the fetch rather than the plan
- `#239` the preflight reports skipped and unverified honestly; the
  post-release stage returns the operator to their own branch
- `#240` the post-release stage opens the documentation bridge instead of a
  `.dev0`
- `#241` NetBox 4.7 compatibility, part two

This commit adds the version surfaces, the compatibility tables, and this plan.

## Approach

### What a deployment saw, and why 2.8.3 did not fix it

Its drift report read `Models compared 2 / 32`, and every unmeasured model
showed change candidates exactly equal to its Forward row count -
357224/357224 interfaces, 121978/121978 MAC addresses. That equality is the
signature of the upper-bound fallback, which is what the report prints when it
has no comparison at all.

The preview built its comparison from the PLAN, and the plan legitimately omits
any model with nothing to stage: `apply_durable_workload_deltas` keeps a
workload only `if candidate.estimated_changes`. A model unchanged since the
last run has no upsert and no delete rows, so it was dropped - and the
comparison, reading the same list, lost the model entirely.

The effect was an exact inversion. **The models in perfect sync were displayed
as the most uncertain**, and the better a deployment's convergence the worse
its report looked. A first run, with everything to do, measured correctly,
which is why the feature's own testing never saw it.

It also explains the two models that did report measured. `dcim.device` kept a
non-empty delta and genuinely compared to zero. `netbox_dlm.softwareversion`
had a delete-only delta - non-zero `estimated_changes`, empty `upsert_rows` -
and reached an empty-row shortcut that returned a confident zero for a model
the comparison cannot handle at all, so it showed a green `In sync: Yes`
against 45 Forward rows. That shortcut was removed in `2.8.3`; this release
removes the other half.

The measurement now reads the rows the fetch produced, captured before the
delta narrows them, behind a keyword-only opt-in so only the preview pays for
holding them.

### Three machinery corrections, all from shipping 2.8.3

The preflight printed every result under `passed:`, including checks that
declined to run, so `evidence base commit skipped (v2.8.3 is already tagged)`
was reported as a pass. The sensitive-pattern parity gap - the one that has now
refused two tags - was likewise printed as passed while saying UNVERIFIED. Each
check now reports `passed`, `skipped` or `unverified`.

The post-release stage committed a `.dev0` bump that its own harness refused,
for a reason it could have satisfied: high-risk version surfaces with no plan
file. On failure it left the operator on a branch it had created, holding a
commit they did not make, with a clean working tree. The next branch cut
inherited it, which is how the `v2.8.3` post-release bridge came to carry four
version surfaces and disqualify itself permanently. The stage now generates the
documentation bridge - the commit a release actually needs next - and returns
the operator to their starting branch either way.

### NetBox 4.7 is blocked upstream, and now measurably so

The remaining compatibility items are done: eight API serializers no longer
declare themselves nested groups, and the `querystring` tag is used nowhere.

The cap stays because the suite was run against `v4.7.0-beta1` with it
temporarily lifted, and the runtime never reached plugin code:

    RuntimeError: Model class netbox_branching.models.changes.ObjectChange
    doesn't declare an explicit app_label and isn't in an application in
    INSTALLED_APPS

`netboxlabs-netbox-branching` `1.1.2` is the newest release published and does
not import on `4.7.0-beta1`. Branching is not optional for this plugin, so 4.7
support waits on an upstream release regardless of anything done here. What is
NOT known is whether the plugin itself works on 4.7; the run never got far
enough to say, and this release does not claim otherwise.

## Validation

Recorded in the Release Authorization section below, bound to the evidence base
commit: the full isolated gate and the exact-runtime artifact test, both on the
final tree, both on NetBox 4.6.8.

## Rollback

No migration, so a downgrade is an install of the prior wheel. The drift change
reverts with `#238` and affects only what the preview reports.

## Decision Log

- **Release rather than hold the fix for a larger tranche.** The deployment
  that reported this is on 2.8.3, where the report is honest about measuring
  nothing. Honest and useless is still useless.
- **Do not raise `max_version` on the strength of the compatibility work.**
  Two of the three 4.7 items are done and the third is upstream. Shipping a
  cap change would claim a runtime nothing has successfully started.
- **Patch, not minor.** The only behavioural change makes a report accurate.

## Open

- Cost at scale of comparing a converged estate. It is the same classification
  a sync performs, but the wall-clock effect on a large deployment's preview
  has not been observed.
- Whether the plugin works on NetBox 4.7 at all. Unmeasurable until branching
  publishes a 4.7-compatible release.
- Whether `main` should carry a `.dev0` once the first change after a release
  lands. Narrowed in `#240`, not decided.
