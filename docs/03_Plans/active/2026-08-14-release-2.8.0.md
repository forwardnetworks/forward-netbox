# Release 2.8.0

## Goal

Ship the absence quarantine - so a device merely disabled in Forward is no
longer deleted permanently on the next sync - together with the fix that makes
the quarantine capable of ever releasing, netbox-dlm 0.9.1 support, a template
rendering fix, and a packaged agent skill.

## Constraints

- The four version surfaces moved together, and with them the fast-baseline
  runtime pin. `scripts/release.py` owns all five, which is why the bump went
  through the tool rather than by hand: a stale pin there reverts the ~6 minute
  first baseline to ~15 hours with no error an operator can see.
- The lineage from the recorded bridge to the release commit must hold at least
  four commits; `scripts/check_release_lineage.py` proves it before tagging.
- The prior-release anchor stays at `v2.7.13` until the post-release anchor
  change; the bridge commit after the tag must be documentation-only.
- `FORWARD_SENSITIVE_PATTERNS` is not on this host, so preflight records the
  parity gap rather than scanning against the superset feed. The release
  workflow still applies it and can refuse the tag.
- Migration `0052` is additive and its only foreign keys are CASCADE, so it
  neither blocks a delete nor requires an operator step.

## Approach

### The quarantine

A device disabled in Forward vanishes from `network.devices` and from the REST
inventory alike, so from every interface the plugin has, disabled is
indistinguishable from decommissioned. With orphan pruning on, the next sync
deleted it permanently; 76 devices went that way in one run at a deployment.
The deletion is permanent and the disabling usually is not.

An orphan now waits out both a consecutive-run count and a wall-clock age
before the prune will touch it, defaulting to 3 runs and 72 hours. Both are
required because either alone is defeated by a plausible sync schedule: three
runs is three hours on an hourly sync, and 72 hours is one confirmation on a
weekly one. The manual button carries an override, because a person reading a
named list is not the unattended path that caused the harm; the scheduled job
has none.

### Why the quarantine did not work, and now does

Found by the gate on this tranche, not in review. `out_of_scope` is derived
from devices holding a live scope claim, and the claim reconciliation releases
every claim whose device is missing from the current Forward result - on the
first run that observes the absence. By run 2 the claim table no longer
remembered the device, so it stopped being an orphan, the streak reset, and
with a threshold of 3 nothing could ever become eligible. The panel's held
count also fell to 0, so the failure was invisible: a prune that deletes
nothing and reports nothing held.

An open absence row now counts as previously managed alongside the live claims.
It is created only from a device that held a claim and cleared the moment the
device returns, so it widens what counts as managed without inventing a claim
the sync never made. It also removes a pre-existing order dependency between
the prune job and the tag-reconciliation job.

### netbox-dlm 0.9.1

Its `models.py` delta against 0.8.0 is entirely direct model imports becoming
lazy string references, which Django resolves identically and which generates
no migration, so the surface this plugin binds to is untouched. 0.9.0 is
excluded and a test pins the exclusion: it cannot render its own views.

## Validation

`invoke ci` and `invoke artifact-test` on the exact tree tagged here apart from
the authorization record appended below.

Recorded in the authorization section, which is the evidence rather than this
summary. The quarantine's negative space is pinned in both directions - what
must not be deleted and what must still be - and the two guards are pinned in
composition, because each was tested in a file that switched the other off.

## Rollback

The tag cannot be withdrawn. A defect found after publication needs 2.8.1; the
prior release stays installable from PyPI. Reverting the quarantine returns
absent devices to being prune-eligible immediately, as in 2.7.13.

## Decision Log

- **A minor bump, not 2.7.14.** The quarantine changes when a destructive
  operation fires and adds an operator-visible control with new source
  parameters. That is a behaviour change, not a patch.
- **Quarantine, not report-only.** Making the prune report-only would remove a
  capability operators deliberately enabled. Delay is enough.
- **Ship the release fix with the feature, not after it.** Shipping the
  quarantine alone would have delivered a permanent no-op that looked like it
  was working.
- **Skip netbox-dlm 0.9.0.** It cannot render any of its own views; admitting
  it to keep the validated set contiguous would record a fiction.

## Open

- The 3-run / 72-hour defaults are a guess at how this deployment schedules
  syncs. They are source parameters, so they are tunable without a release.
- netbox-dlm now declares `max_version = "4.6.99"`, identical to ours. No
  conflict today, but whichever side raises its NetBox ceiling first blocks the
  other, and it is worth raising upstream before either of us moves to 4.7.
