# Release 2.9.6: ACI at full speed, the links netbox-routing models, and audits an operator can open

Status: in progress on `maint/2.9.x`. The release cut waits for the
customer's report on 2.9.5; the work does not.

## Goal

After 2.9.6, on the 4.6 maintenance lane:

1. Enabling the Cisco ACI maps no longer switches the fast baseline off for
   the whole sync.
2. Static port bindings (`fvRsPathAtt`) and subject-to-filter attachments
   (`vzRsSubjFiltAtt`) are imported, so a contract subject is not an empty
   shell and an endpoint group says where it is bound.
3. Route-map entries link to the prefix lists and community lists they
   match, the way netbox-routing renders them, instead of carrying the names
   as JSON text only.
4. The nine audits that exist only as management commands are read-only
   report views on the sync page (phase 2 of the no-operator-CLI plan).

## Constraints

- No upstream changes: `netbox-cisco-aci` stays at the exact pin `0.4.0`,
  `netbox-routing` at `0.4.3`. Anything they cannot model is skipped with a
  recorded reason.
- Minimum custom-command set: exactly one more `moquery` class is asked of a
  customer (`vzRsSubjFiltAtt`). `fvRsPathAtt` is already in the reference
  collection.
- No new per-run NQE query. Audit views must not run a Forward query on a
  GET; Forward-backed audits are button jobs. Acceptance is a bounded number
  of executions recorded in `forward_api_usage`.
- Branching stays; the fast baseline is optimised inside the branch.
- Every delete path names an allowlist. The two new ACI models join the ACI
  delete brake (`aci_allow_deletes`), never a broader one.
- No live network or snapshot identifiers, customer names, or scan-matching
  hostnames in committed content, commit messages, or PR bodies. Invented
  examples use the `FAB1` prefix.
- Each production PR passes `invoke ci` under the release-gate environment.

## Approach

**1. Fast baseline with ACI on.** The decision computes `unsupported =
selected models - allowlist` over every *enabled* map's model, so one enabled
ACI map disabled the fast path for everything. All thirteen (fifteen after
this release) `netbox_cisco_aci` models join the allowlist at spec version 1
and the adapter-contract set, at the depth the three routing policy entries
already have: required fields only. Parent resolution stays the adapter's
recorded skip, so restricted and converged runs keep the fast path. A
registry-driven test pins that every registered map model is either
allowlisted or named in `FAST_BASELINE_EXCLUDED_MODELS` with a reason
(`dcim.virtualchassis`, `netbox_dlm.inventoryitemsoftware`,
`netbox_peering_manager.peeringsession`), so the next map cannot reintroduce
the fallback silently. The runtime pin the fast baseline compares to the
plugin version moves in the release-cut commit.

**2. Static port bindings and subject filters.** Two maps over the APIC
`moquery` text, fabric resolved through the APIC as every 2.9.5 map does.
`fvRsPathAtt` rows carry tenant, application profile, EPG, node id and
interface from the distinguished name and `encap`, `primaryEncap`, `mode` and
`instrImedcy` from the attributes, plus a `path_kind` (`path`, `protpath`,
`extpath`). The adapter writes `path` rows only: EPG resolved, never created;
node to device through the existing case-insensitive node lookup; interface
by canonical name. vPC and FEX paths name a policy group, not an interface,
and are recorded and skipped under one rollup reason. `vzRsSubjFiltAtt` rows
carry direction from the `intmnl` / `outtmnl` terminal segment (or `both`),
`action` and `priorityOverride`; the filter resolves in the subject's tenant,
then `common`. Both register at every engine site the five 2.9.5 maps did,
under the ACI delete brake and the readiness diagnostic. The fabrics map is
re-derived from the APICs' locations so a location holding only leaves is no
longer a fabric of its own.

**3. Route-map links.** `coalesce_update_or_create` gains `m2m_values`; after
`save()` it compares the stored pk set with the requested one and calls
`.set()` only on a difference, counting a link change as a change. The
staging branch records it as an ordinary change and the merge already replays
`m2m_data`. Resolution follows the catalogue: the list queries emit
`holder_devices` per variant, the route-map query emits the entry's
`representative_device`, and the adapter resolves each referenced name
through a same-run index by that device; on a miss it falls back to the
bare-name (most-shared) object and counts the fallback; unresolved names
are counted separately. The JSON `match` clause keeps the verbatim name.
Preview and drift compare the link sets as part of the row.

**4. Audit views.** Database-only audits (primary-IP resolution, stale global
IPAM, ambiguous device names, dangling routing rows, interface untagged
VLANs) render on GET, capped at 500 rows with the true count. Forward-backed
audits (stale DLM notices, apply-identity churn, APIC CIMC readiness,
fast-baseline eligibility) are button jobs whose latest payload the view
renders, so the button is the only thing that spends NQE. Health checks whose
remedy was a command name the view. The docs and `SKILL.md` rewrite stay
phase 3.

Sequencing: four production PRs (fast baseline + the carried test fix; ACI
bindings; routing links; audit views), then the customer-feedback PR if one is
needed, then the release cut after that feedback.

## Validation

- `invoke ci` and `invoke artifact-test` under the release-gate environment
  per PR; the sensitive-content scan before every push.
- One bounded acceptance sync on the validation org with every ACI and
  routing map enabled: the fast-baseline preflight reports eligible; static
  port binding `path` rows written and the vPC/FEX skip count visible; subject
  filters populated once the new command is collected; route-map links
  reported as exact / fallback / unresolved with a spot check against config
  text; fabrics agree with the APIC-side node map; a second sync returns no
  Forward changes or an explained delta. `forward_api_usage` census per sync
  unchanged.
- All nine audit views opened on the acceptance stack; each Forward-backed
  one records exactly one job.

## Rollback

Every map is seeded disabled; disabling the two new ACI maps removes their
rows only under `aci_allow_deletes`. The M2M primitive is opt-in per caller
(`m2m_values=None` is the previous behaviour). Views are additive. A wrong
allowlist entry surfaces as `unsupported_row_contract` and the normal engine
runs.

## Decision Log

- Allowlist pinned by registry, not by hand, so a new map cannot switch the
  fast baseline off unnoticed.
- ACI contract depth is required fields only, matching the policy entries.
- vPC and FEX bindings are skipped with a count rather than guessed.
- M2M is an engine primitive with a diff-before-write, not a `.set()` in the
  adapter, so preview, drift and the no-op-on-converged guarantee see it.
- Link resolution follows the representative device and counts every
  fallback; silent wrong links for divergent definitions are the failure to
  avoid.
- Audits that spend NQE are buttons; audits that read the database are pages.
- The interface-VLAN audit persists nothing; the view renders live rows.
