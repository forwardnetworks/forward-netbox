# Release 2.7.8

## Goal

Unblock the customer. Their ownership reconciliation still fails on 2.7.6, and
the fix is on `main`. This is the second attempt to ship it: 2.7.7 was tagged
and refused at the gate, for a reason unrelated to the fix itself.

## Contract

- The four version surfaces move in ONE commit.
- The release commit carries its own release-authorization section, whose
  evidence base commit equals the parent of the commit that gets tagged. Never
  write that heading's text earlier in the plan: the checker splits on its
  first occurrence.
- The table marks 2.7.8 a RELEASE CANDIDATE. The anchor and the "Current
  release" marker move together after the tag.
- The tag is created locally, provenance verified, and only then pushed.
- The first first-parent commit after the tag is documentation-only.

## Constraints

- Gates run locally; there is no CI. Run the FULL plugin suite.
- Verify `invoke lint` IMMEDIATELY before each commit and again after.
- PyPI egress on this host stalls on large HTTP/1.1 responses, so the upgrade
  gate needs `FORWARD_NETBOX_UPGRADE_FROM_VERSION=2.7.6`. Only the DISCOVERY is
  offline; the upgrade itself runs in full.
- Local `verify_release_provenance.py` cannot complete here for the same
  reason. The publish workflow runs the identical verifier on GitHub's runners
  and is fail-closed.
- The gates must be re-run for 2.7.8. The tree is NOT the tree 2.7.7 measured:
  the fixture rename and the version bump both changed it, and evidence is
  bound to a tree.

## Touched Surfaces

- `pyproject.toml`, `forward_netbox/__init__.py`,
  `forward_netbox/utilities/fast_baseline.py`,
  `forward_netbox/tests/test_runtime_dependency_check.py`
- `README.md`, `docs/README.md`, `docs/01_User_Guide/README.md`, `CHANGELOG.md`

## Approach

One fix, already on `main` and already through the full suite (#172). This
change is the version bump and the release notes. The shipped behaviour is
identical to what 2.7.7 would have shipped; only a test fixture name differs.

## Validation

`invoke ci` and `invoke artifact-test` on the pinned environment, then the tag,
then provenance.

## Rollback

Before the tag is pushed, revert the branch. After it is pushed the tag is
immutable and a defect costs a version number - which is what 2.7.3 and 2.7.7
each cost.

## Decision Log

- **2.7.7 was burned by the sensitive-content gate, and the gate was right.**
  The test added for this fix used a real employee name from the customer's
  estate as its tag fixture. The publish workflow's validate job matched it
  against the release-only pattern feed and refused; nothing was built and
  nothing was published. The tag is immutable, so the version was spent.
- **The local gates could not have caught it.** The match was against the
  release-only `FORWARD_SENSITIVE_PATTERNS` feed, which is a strict superset of
  the local `.sensitive-patterns.local.txt`. Now that the gates are local-only,
  that asymmetry is a real hole: the local feed has been extended, but the
  general fix is to make the two feeds agree. Tracked separately.
- **History was rewritten rather than baselined past.** The alternative was to
  advance `.sensitive-history-baseline`, which would have unblocked releases
  while leaving the name in a public repository forever. See
  `2026-08-10-sensitive-history-rewrite.md`.
- **Cut immediately, unlike 2.7.6.** That tranche was correctness and
  diagnosability with the customer already unblocked, so it could wait. This one
  is the thing they are actually stuck behind, and every day on 2.7.6 is another
  day of ownership never completing.
- **The diagnostic shipped in 2.7.6 is what made this findable.** Their job
  named `tag-mutation-identity-unresolved` rather than
  `unrecognized-ownership-conflict`; the previous hypothesis was wrong and would
  have stayed wrong.

## Open

- If the customer also has AMBIGUOUS device names - the same name in two sites -
  this will not fully unblock them. The refusal now reports how many of each,
  so the next run says so without a support round-trip.
- Their eleven absent devices remain absent. Whether Forward should tag devices
  this NetBox has never had is a question for their side; the count makes it
  visible.
- The local and release-time sensitive-pattern feeds still differ. Until they
  agree, a name known only to the release feed can reach a tag again.
