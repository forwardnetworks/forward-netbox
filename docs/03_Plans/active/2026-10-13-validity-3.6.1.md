# Accept netbox-validity 3.6.1

## Goal

Accept and test against netbox-validity 3.6.1, released 2026-10-09. Its only change is pinning scrapli to 2026.2.20, because newer scrapli releases have breaking changes (the plugin already caps scrapli below 2026.10 for the same reason).

## Constraints

- 3.6.0 stays accepted: an operator on it must not see an unsupported-version refusal.
- The tested runtime moves to 3.6.1 only if the image really installs it and the Validity tests pass against it.
- No customer identifiers in the repo, plans, tests or docs.

## Touched Surfaces

- `pyproject.toml`, `constraints.txt`, `development/constraints-upgrade-from.txt` (kept in lockstep), `poetry.lock` (moved with `poetry update --lock`; a plain `poetry lock` keeps the old version).
- `forward_netbox/utilities/validated_runtime.py`, `plugin_integrations/registry.py` (`required_package_version` and `supported_package_versions`).
- `test_optional_plugin_versions.py`, `test_plugin_integrations.py`; comments in `development/Dockerfile` and `development/configuration/plugins.py`.

## Approach

1. Accept 3.6.0 and 3.6.1 in the validated set and the integration's supported versions; require 3.6.1.
2. Move the constraint pins and the lockfile to 3.6.1.
3. Rebuild the test image so it installs 3.6.1 and run the version, integration and config-backup tests in it.

## Validation

- `poetry update --lock netbox-validity` moved the lock from 3.6.0 to 3.6.1; Validity now declares `scrapli = "2026.2.20"`, inside the plugin's own cap.
- The targeted tests run in an image built with 3.6.1 (result recorded in the PR).
- Not verified: Validity's own behavior beyond what these tests exercise; the release note lists no functional change.

## Rollback

Revert the pins; 3.6.0 remains accepted throughout.

## Decision Log

- 3.6.0 stays in the supported set, as netbox-dlm 0.10.0, 0.10.1 and 0.10.2 do.
