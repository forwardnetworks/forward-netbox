# Release 2.8.2

## Goal

Ship the two halves of a 2.8.1 deployment report - the delete path that had no
gate, and the skip record that could not say which row it was about - plus the
two release checks that misreported during 2.8.1 and a toolchain security pin.

## Constraints

- The four version surfaces move together with the fast-baseline runtime pin,
  through `scripts/release.py` rather than by hand. A stale pin there reverts
  the first baseline from about six minutes to about fifteen hours, silently.
- The lineage from the recorded bridge to the release commit must hold at least
  four commits, with the production and release commits last.
  `scripts/check_release_lineage.py` proves it before tagging.
- The prior-release anchor stays at `v2.8.1` until the post-release change; the
  bridge commit after the tag must be documentation-only.
- `FORWARD_SENSITIVE_PATTERNS` is not on this host. The release-time feed is a
  SUPERSET of anything checkable locally and it runs after the tag exists, so
  the gap is recorded explicitly rather than assumed away - see Approach.
- A patch, not a minor. `#217` changes what a sync deletes unattended, which is
  a behaviour change, but it only ever removes capability from a destructive
  path; nothing gains a new operator control and nothing changes shape.

## Touched Surfaces

Landed across four pull requests:

- `#216` the NetBox row identity on a protected-delete skip
- `#217` the removal allowlist on the Forward-diff delete path
- `#215` the two release checks that measured the wrong subject
- `#218` `cryptography` 50.0.0 in the hash-pinned release toolchain

This commit adds the version surfaces, the compatibility tables, and this plan.
It also replaces an invented-but-plausible site slug in two test fixtures with
an obviously synthetic one; see Approach.

## Approach

### The delete path that had no gate

`compute_full_removals` has enforced `BASELINE_REMOVAL_MODELS` since 2.7.13,
refusing sites, device types, platforms, manufacturers, device roles, prefixes,
VLANs, VRFs, devices and the software-version catalogue by name, with the
reasoning written out beside the set. `_split_diff_rows` enforced nothing:
every `DELETED` row became a delete for any model, with only the ACI
suppression check downstream. The exact models one producer protected, the
other deleted unattended.

A deployment on 2.8.1 reached `delete()` on an `ipam.vrf`, a `dcim.devicetype`
and three `dcim.site` rows in one sync. Nothing was lost because PROTECT
refused all five - a database constraint standing in for a gate. A site or
device type with no children has nothing holding it.

Both producers now read one allowlist, stated in one file so they can be read
against each other. A parity test requires every model with a delete handler to
appear in exactly one of the permitted or refused sets, so a model added later
cannot land in neither and inherit "deletable" by omission.

The rule governs `DELETED` rows only. A `MODIFIED` row whose identity key
changed is a rename - Forward reporting the same object under a new identity,
with the replacement written in the same batch - so refusing that delete
preserves nothing and strands a duplicate forever. The blanket version of the
rule was caught by the full suite, not by the targeted tests: an end-to-end
test renames a site and asserts the old row is gone.

### The skip that could not name its row

Five skips reading `dcim.site row processing skipped (...; still referenced by
dcim.device)` were each correct and none actionable, two of them byte-identical
to each other. Everything that would identify the row is a name or a slug, and
`diagnostic_shape` reduces it to key names before it persists. A pk is an
internal identifier, so it survives redaction - the same fix 2.8.1 gave the
merge recorder, applied to the sync recorder.

### The sensitive-pattern gap

The release-only feed is not on this host, so the preflight cannot prove parity
and the publish workflow's superset scan is the first thing that would see a
violation - after the tag, which is immutable. That is what refused v2.7.7.

Mitigated rather than waved through. Everything added since `v2.8.1` was
enumerated and reviewed: all of it is schema identifiers, synthetic fixtures or
prose about "a deployment". Two invented values in the redaction tests were
shaped to look like a real site slug on purpose, which is the one category that
could collide with a private pattern by accident; they are now
`example-site-slug` and `Example Site`, which assert exactly as well. The local
scan passes over all tracked files.

## Validation

Recorded in the Release Authorization section below, bound to the evidence base
commit: the full isolated gate and the exact-runtime artifact test, both on the
final tree.

The upgrade leg seeds from 2.8.1 on the default NetBox version and needs no
`UPGRADE_FROM_NETBOX_OVERRIDES` entry, unlike 2.8.1's - the migration defect
that forced 2.8.0 to seed on v4.6.6 is fixed in the FROM release now.

## Rollback

Nothing here is a migration, so a downgrade is an install of the prior wheel.
The behaviour change in `#217` restores by reverting that commit, which returns
the diff path to deleting any model.

## Decision Log

- **Patch, not minor.** The delete change removes capability from a destructive
  path and adds no control. An operator who never hit the old behaviour sees
  nothing; one who did sees a held-back warning naming the model.
- **Release-note the behaviour change first.** "No longer incorrectly deletes X"
  reads as pure upside and hides that unattended removal genuinely stops for
  those models. The note says a device or site Forward stops reporting now
  stays until someone prunes it.
- **Fold the fixture rename into the release commit** rather than a fifth PR.
  It is two string literals in tests, and 2.8.1's release commit carried a
  migration and a new test module on the same reasoning.
- **Record the pattern-feed gap, do not assume it.** 2.8.1 set the precedent of
  proceeding with `FORWARD_NETBOX_PATTERN_PARITY_UNVERIFIED=1`; this release
  additionally enumerates and reviews every added literal, because "the local
  scan passed" is exactly the sentence that preceded v2.7.7.

## Open

- Nothing blocking. NetBox `4.6.7` and `4.6.8` shipped during this release and
  are patch releases with no plugin-facing changes; the declared range already
  covers them and the "tested on" claim moves in its own change, because the
  version is exact-pinned in the authorization checker, the installed-artifact
  validator and the SBOM validator, and those must move together.
- NetBox `4.7.0-beta1` landed the same day. `max_version = "4.6.99"` means the
  plugin refuses to load there rather than half-working, so it is not a release
  concern; the compatibility work is scheduled after this.
