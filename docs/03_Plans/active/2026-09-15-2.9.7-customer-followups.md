# 2.9.7: the customer's first day on 2.9.6

## Goal

Four things a customer reported within hours of upgrading to 2.9.6, fixed
on `maint/2.9.x` without cutting a release until they batch up: a progress
bar that runs backwards, SNMP endpoints whose vendor is known to Forward
but read as Unknown, and a blocking failure whose message named the
models but not the reason - twice, once on the job log and once on the
issue row.

## Constraints

- No release from this tranche on its own; it waits for the next real
  reason to cut 2.9.7.
- Every change here also belongs in the 3.0.1 forward-port.
- No customer names, identifiers, or scan-matching hostnames in committed
  content, commit messages, or pull-request bodies. The live probe that
  confirmed the SNMP findings read a validation org; none of what it
  returned is recorded anywhere.
- The redaction pipeline's safety boundary is not loosened: every value
  this change surfaces was already an allowlisted slug or a sentence
  composed entirely from this plugin's own vocabulary.

## Touched Surfaces

- `forward_netbox/utilities/branch_lifecycle.py` - new
  `initialize_plan_statistics`; the per-item statistics blocks in
  `run_item_in_branch` and `run_item_direct_to_main`.
- `forward_netbox/utilities/single_branch_executor.py`,
  `forward_netbox/utilities/fast_baseline.py` - call it after
  `build_branch_plan`.
- `forward_netbox/queries/forward_devices.nqe` - the endpoint branch's
  vendor identity.
- `forward_netbox/utilities/diagnostics.py` - `safe_exception_summary`,
  `describe_failure`.
- Tests: `test_plan_statistics_monotonic.py` (new),
  `test_diagnostics_readback.py`, `test_merge_rule_rejection.py`.

## Approach

**Progress bar runs backwards (80% → 50% → 90%).** `build_branch_plan`
splits one model's workload into several plan items when it exceeds the
staging-item budget, which a 70k-row table routinely does. Each item added
only its own `estimated_changes` to the model's running total right before
it applied, so the total grew in installments interleaved with `current`
climbing toward the prior, smaller total: a later item's total landing
while `current` was already most of the way there dropped the ratio, and
it climbed back as that item's rows applied. The whole plan is known
before any item runs, so `initialize_plan_statistics` now sums every
item's `estimated_changes` per model up front and sets the total once;
`current` then climbs to it monotonically. The per-item functions skip
re-adding to a model whose total was precomputed, tracked in a set kept
separate from the one that only gates the reset-to-zero - conflating them
on the first pass silently broke the fallback for any caller that runs a
single item in isolation.

**SNMP endpoints read Unknown vendor.** The endpoint branch derived the
manufacturer from `sysDescr`, or from `sysObjectID`'s enterprise prefix
for the Avocent/Opengear overlay, and never from `endpoint.profileName`.
A live probe found endpoints whose SNMP walk returned neither
`sysDescr` nor `sysObjectID` at all, while Forward's own profile
assignment already named the vendor. The overlay now also matches the
profile name, and two non-console-server vendors Forward names in a
profile get a manufacturer from it before the fallback to Unknown. A
residual set with a fully generic profile and no SNMP identity data still
correctly reads Unknown; that is a collection gap, not a plugin one.

**A blocking failure that did not say why.** An operator enabled three
brand-new models on a sync without enabling their query maps. The plugin
already composes the exact sentence for that - which map to enable, or
disable the model - but two layers threw it away. `safe_exception_summary`
reduced every exception whose message matched a reason slug to the bare
slug; for the two reasons only `_missing_query_specs_message` ever raises,
composed entirely from model strings and NQE Map names this plugin
registers itself, the full sentence is now kept on the job log. And
`describe_failure`, the one renderer behind the blocking issue row for
every recorder, listed the failed models but never the
`failed_model_reasons` the same callers already attach as safe slugs -
it appends them now, generically, for any reason on any failure.

## Validation

- `invoke ci` on the 4.6 stack.
- `test_plan_statistics_monotonic.py`: a split model's total is the sum
  across every item, `current / total` never regresses once initialized,
  every model is marked precomputed.
- `test_diagnostics_readback.py`: the two verbatim-safe reasons keep their
  sentence; an unrelated reason still reduces to the bare slug.
- `test_merge_rule_rejection.py`: failed models carry their reasons; a
  failure with no reason renders exactly as before.
- The NQE linter reports no new diagnostic on `forward_devices.nqe` (the
  three pre-existing argument-type warnings predate this change).

## Rollback

Each change is independent and additive; none touches a migration or a
persisted shape. Reverting any one restores the previous behaviour with no
data repair.

## Decision Log

- **Set the total once, do not clamp the display.** Clamping
  `current / total` to be non-decreasing would have hidden the symptom
  while the accounting stayed wrong; the plan is fully known before any
  item runs, so the honest fix is to use it.
- **Two tracking sets, not one.** "Do not reset this model's total again"
  and "this model's total is already complete" are different facts, and a
  caller that runs a single item in isolation needs the first without the
  second.
- **Profile name as a vendor signal, for the overlay and two generic
  vendors only.** Matching every profile substring to a manufacturer
  would invent vendors from customer-chosen profile names; the overlay
  vendors and the two Forward names in its own bundled profiles are the
  ones this plugin can vouch for.
- **Generic reason on the issue row; verbatim sentence only for two
  reasons on the log.** The generic path surfaces nothing that was not
  already an allowlisted slug and helps every failure. The verbatim path
  is scoped to exactly the two reasons whose sentence is provably built
  from this plugin's own vocabulary, so the redaction boundary is not
  loosened for anything else.
