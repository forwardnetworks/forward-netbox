# 2.9.7: the customer's first day on 2.9.6

## Goal

Five things a customer reported within hours of upgrading to 2.9.6, fixed
on `maint/2.9.x` without cutting a release until they batch up: a progress
bar that runs backwards, SNMP endpoints whose vendor is known to Forward
but read as Unknown, a blocking failure whose message named the models
but not the reason - twice, once on the job log and once on the issue
row - a sync form that let the operator save the very combination that
run could only fail on, and a manual device/interface delete refused by
another plugin's routing rows with no way to clear them but by hand.

## Constraints

- No release from this tranche on its own; it waits for the next real
  reason to cut 2.9.7.
- Every change here also belongs in the 3.0.1 forward-port.
- No customer names, identifiers, or scan-matching hostnames in committed
  content, commit messages, or pull-request bodies. The live probe that
  confirmed the SNMP findings read a validation org; none of what it
  returned is recorded anywhere.
- The redaction pipeline's safety boundary is not loosened: every value
  this change surfaces was already an allowlisted slug or a sentence
  composed entirely from this plugin's own vocabulary.

## Approach

**Progress bar runs backwards (80% → 50% → 90%).** `build_branch_plan`
splits one model's workload into several plan items when it exceeds the
staging-item budget, which a 70k-row table routinely does. Each item added
only its own `estimated_changes` to the model's running total right before
it applied, so the total grew in installments interleaved with `current`
climbing toward the prior, smaller total: a later item's total landing
while `current` was already most of the way there dropped the ratio, and
it climbed back as that item's rows applied. The whole plan is known
before any item runs, so `initialize_plan_statistics` now sums every
item's `estimated_changes` per model up front and sets the total once;
`current` then climbs to it monotonically. The per-item functions skip
re-adding to a model whose total was precomputed, tracked in a set kept
separate from the one that only gates the reset-to-zero - conflating them
on the first pass silently broke the fallback for any caller that runs a
single item in isolation.

**SNMP endpoints read Unknown vendor.** The endpoint branch derived the
manufacturer from `sysDescr`, or from `sysObjectID`'s enterprise prefix
for the Avocent/Opengear overlay, and never from `endpoint.profileName`.
A live probe found endpoints whose SNMP walk returned neither
`sysDescr` nor `sysObjectID` at all, while Forward's own profile
assignment already named the vendor. The overlay now also matches the
profile name, and two non-console-server vendors Forward names in a
profile get a manufacturer from it before the fallback to Unknown. A
residual set with a fully generic profile and no SNMP identity data still
correctly reads Unknown; that is a collection gap, not a plugin one.

**A blocking failure that did not say why.** An operator enabled three
brand-new models on a sync without enabling their query maps. The plugin
already composes the exact sentence for that - which map to enable, or
disable the model - but two layers threw it away. `safe_exception_summary`
reduced every exception whose message matched a reason slug to the bare
slug; for the two reasons only `_missing_query_specs_message` ever raises,
composed entirely from model strings and NQE Map names this plugin
registers itself, the full sentence is now kept on the job log. And
`describe_failure`, the one renderer behind the blocking issue row for
every recorder, listed the failed models but never the
`failed_model_reasons` the same callers already attach as safe slugs -
it appends them now, generically, for any reason on any failure.

**The form let it happen.** The operator asked whether the model checkbox
on the sync could enable the map too. It cannot honestly: an NQE Map is
one global row shared by every sync, several maps can feed one model, and
enabling one from a sync's edit page would silently change every other
sync's next run. What the form can do is refuse the combination it knows
will fail. `ForwardSyncForm.clean` now resolves query specs for every
enabled model against the enabled maps exactly as the run would, and puts
the run's own sentence on the offending checkbox. The sentence moved out
of the query fetcher into the registry so the two callers cannot drift.

**A manual delete refused by another plugin's routing rows.** The device
ownership panel already names every foreign PROTECT relation blocking a
delete (`describe_delete_blockers`, shipped in 2.9.6 after ten
`netbox_routing` BGP rows refused a customer's delete with no explanation).
Naming was not releasing: an operator still had to find and delete each
`OSPFInstance`/`OSPFInterface`/etc. row by hand, in the routing plugin's own
UI, before NetBox would let the device go. `release_foreign_delete_blockers`
does the release itself, but only for rows in an explicit, narrow app-label
allowlist (`netbox_routing`, since this plugin's own routing-policy sync
re-creates them from Forward on the next run) - never a blanket release of
everything `describe_delete_blockers` can name, since a `netbox_dlm` or
`netbox_cisco_aci` record might be an operator's own hand-authored data. It
re-runs the same `Collector.collect` walk the panel already reads, deletes
exactly the rows it finds, resolves any blocker one level deeper the same
way, and rolls back the whole attempt the moment it meets a row outside the
allowlist - a refused release never leaves a device half-cleared. The panel
offers a release button only when EVERY foreign blocker on the device is
allowlisted; a mix still falls back to the existing manual instructions
naming everything, allowlisted or not, since a partial release would just
trade one confusing refusal for another. The button re-checks the exact
`{label: count}` it showed against a fresh `describe_delete_blockers` before
releasing anything, so a race with a sync run or another operator's action
refuses instead of releasing a different set of rows than the one confirmed.

## Validation

- `invoke ci` on the 4.6 stack.
- `test_plan_statistics_monotonic.py`: a split model's total is the sum
  across every item, `current / total` never regresses once initialized,
  every model is marked precomputed.
- `test_diagnostics_readback.py`: the two verbatim-safe reasons keep their
  sentence; an unrelated reason still reduces to the bare slug.
- `test_merge_rule_rejection.py`: failed models carry their reasons; a
  failure with no reason renders exactly as before.
- `test_forms.py`: a model whose only map is seeded disabled is refused on
  its own checkbox with the run's sentence, accepted once the map is
  enabled, and the form and the fetcher produce the identical sentence.
- The NQE linter reports no new diagnostic on `forward_devices.nqe` (the
  three pre-existing argument-type warnings predate this change) or on
  `forward_devices_with_netbox_aliases.nqe`, which the endpoint branch
  stays byte-identical to (`test_endpoint_branches_stay_byte_identical`).
- `test_release_foreign_delete_blockers.py`: an allowlisted blocker is
  released; a blocker one level deeper resolves before the outer retry; a
  non-allowlisted blocker (including one reached only after an allowlisted
  one) rolls back with nothing deleted; a non-converging release stops at
  its iteration cap instead of looping; the offer helper refuses a mixed
  set and requires an owning sync.
- `test_button_jobs.py`: the new kind is fully specified, its runner's
  `Meta.name` matches the spec suffix, its work function is named and
  invoked, and its REST action enforces its own `device`/`expected_blockers`
  body (the one kind in the registry with no whole-set, bodiless meaning).

## Rollback

Each change is independent and additive; none touches a migration or a
persisted shape. Reverting any one restores the previous behaviour with no
data repair.

## Decision Log

- **Set the total once, do not clamp the display.** Clamping
  `current / total` to be non-decreasing would have hidden the symptom
  while the accounting stayed wrong; the plan is fully known before any
  item runs, so the honest fix is to use it.
- **Two tracking sets, not one.** "Do not reset this model's total again"
  and "this model's total is already complete" are different facts, and a
  caller that runs a single item in isolation needs the first without the
  second.
- **Profile name as a vendor signal, for the overlay and two generic
  vendors only.** Matching every profile substring to a manufacturer
  would invent vendors from customer-chosen profile names; the overlay
  vendors and the two Forward names in its own bundled profiles are the
  ones this plugin can vouch for.
- **Generic reason on the issue row; verbatim sentence only for two
  reasons on the log.** The generic path surfaces nothing that was not
  already an allowlisted slug and helps every failure. The verbatim path
  is scoped to exactly the two reasons whose sentence is provably built
  from this plugin's own vocabulary, so the redaction boundary is not
  loosened for anything else.
- **Refuse the save, do not enable the map.** Maps are global and
  many-to-one with models; a checkbox on one sync must not mutate what
  every other sync runs. A save-time refusal costs the operator one click
  to the NQE Maps page and saves a failed run.
- **A narrow, named allowlist - not a blanket release of everything
  `describe_delete_blockers` can name.** `netbox_routing` rows this
  plugin's own sync creates cost nothing to release; a customer's own
  `netbox_dlm` or `netbox_cisco_aci` record deserves the same scrutiny a
  device does, so releasing it stays a manual, deliberate act elsewhere.
- **All-or-nothing per device, not partial.** A release that clears some
  blockers and leaves others just trades one confusing refusal for
  another; the panel only offers the button when every blocker on that
  device is in the allowlist.
- **This action is not a `BUTTON_JOB_SPECS` kind like the others.** Every
  existing kind has a sensible bodiless call (a whole-set default); this
  one has no device to act on without one being named, so its REST action
  validates its own body rather than reusing the shared bodiless-call
  helper, and the generic REST-parity test was extended with a per-kind
  POST body rather than pretending a bodiless call means something here.
