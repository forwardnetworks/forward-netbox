# Release 3.0.1

## Goal

Cut `3.0.1` on `main`, the NetBox 4.7 line. `3.0.0` shipped without any of the
fixes the 4.6 line released as `2.9.7` through `2.9.11`, so a deployment
moving to 4.7 lost them. This release carries all of them, plus the
forward-sdk migration finished on `main` and a fix for committed-query
lookups by path, which read attributes the SDK's result type does not have.

## Constraints

- Version surfaces (`pyproject.toml`, `forward_netbox/__init__.py`,
  `forward_netbox/utilities/fast_baseline.py`,
  `forward_netbox/tests/test_runtime_dependency_check.py`, the README
  compatibility tables) must all read `3.0.1` together, or `check_harness.py`
  refuses the release.
- The tested runtime moves to NetBox `4.7.1` with netbox-branching `1.2.0`.
- `forward-sdk` is `0.1.20`, pinned exactly.
- No code change in this commit: every functional change already landed as
  its own reviewed, `invoke ci`-green PR.
- Two bundled queries (`forward_interfaces`, `forward_ip_addresses_ipv4`)
  changed their `@query` parameter lists since `v3.0.0`, and the three
  routing-policy queries gained an output column. A published org copy is not
  rewritten by `pip install`, so the release note tells operators to run
  Publish Bundled Queries. The preflight refuses a release whose row omits it.
- Migrations `0053` to `0057` and `0060` adopt the 2.9.x schema history so a
  deployment upgrading from either line reaches one graph.
- No customer names, identifiers, or scan-matching hostnames in this plan,
  the changelog entry, or the release commit message.

## Approach

`scripts/release.py 3.0.1 --write --summary "..."` bumps every version
surface and the fast-baseline pin in the same commit and regenerates
`CHANGELOG.md` from the README compatibility table. What it covers, on
`main` since `v3.0.0`:

1. The one-merge port of everything `maint/2.9.x` shipped after `2.9.6`
   (#487), against `v2.9.6` rather than a commit replay, so `2.9.9`'s
   site-slug regression never lands on this line.
2. The lineage and runtime change that made the gate passable again: the
   2.9.x migrations adopted, NetBox 4.7.1, netbox-routing 0.5.0 (#486).
3. Reading the SDK's `RepositoryQuery` by its real attributes and moving to
   `forward-sdk` 0.1.20 (#488).
4. The release lane declared on `main` (#361).
5. The 2.9.11 tranche ported as one change against `v2.9.10` (#495): the Auto
   merge review hold, row-count and recent-ingestion evidence in Health and the
   support bundle, the configurable config backup folder and the config backup
   result counts.
6. The upgrade gate's from side for `3.0.0` seeded on NetBox 4.7.0, its
   declared minimum (#489); without it the gate could not load the previous
   release.
7. The forward-sdk migration steps completed on `main` since `3.0.0`.

- #488's path-filtered repository lookup was run live against a real Forward

- `scripts/release.py 3.0.1 --write` verify step: version-surface

- The sensitive-pattern parity check runs UNVERIFIED in this checkout
  (`FORWARD_SENSITIVE_PATTERNS` is a CI-only secret); the release gate applies
  the superset feed and can still refuse the tag.

## Rollback

This commit is a version bump and changelog entry only. Reverting it restores
the previous version surfaces; the functional PRs need their own reverts.
Migrations `0053` to `0057` and `0060` are already on `main` and are not
reversed by this commit.

## Decision Log

- **Ported as one merge.** Replaying four releases of commits would have
  landed a known regression before removing it.
- **The SDK fix rides in this release, not after it.** Committed-query
  lookups by path fail against a real Forward without it, so shipping `3.0.1`
  without it would ship the same class of bug the release exists to close.
- **Not held for the follow-up.** A larger-than-normal-run warning and a
  merge guard for Auto merge are planned for the 4.6 line first and ported to
  the next release here.
