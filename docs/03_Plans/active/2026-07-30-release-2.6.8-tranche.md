# Release 2.6.8 Tranche

## Goal

Ship the 2.6.7 tranche, which was tagged but never published, together with the
two field defects its own diagnosability work exposed.

## Contract

- `2.6.8` carries everything `2.6.7` contained. No `2.6.7` artifact exists on
  PyPI, so the compatibility table omits it entirely, as it omits `2.6.2`.
- A module whose type would recreate a component another module already owns is
  reported and skipped, not failed.
- An address that is already another device's primary IP is not reassigned.
- The release build job checks out with tags, and a harness check fails closed if
  that ever regresses.
- Upgrade and re-run the sync. No migration, no operator step.

## Constraints

- Keep persisted and logged diagnostics free of customer data — counts and
  schema identifiers only.
- Do not weaken any fail-closed gate.
- Do not claim `2.6.7` shipped.

## Touched Surfaces

- `.github/workflows/release.yml`, `scripts/check_harness.py`
- `forward_netbox/utilities/sync_inventory_module.py`
- `forward_netbox/utilities/primary_ip.py`
- `forward_netbox/utilities/{sync,sync_reporting}.py` — the new rollup reason
- `forward_netbox/tests/test_field_reported_integrity_failures.py` (new)
- Version surfaces and the three compatibility tables.
- This plan.

## Approach

**Why 2.6.7 never published.** `artifact-upgrade-test`, added in 2.6.7, resolves
the version to upgrade *from* by reading released tags. The release workflow's
`build` job checks out without `fetch-depth: 0`, so that checkout has no tags and
the task failed closed with "no released tag below 2.6.7" — *after* the tag had
been pushed. The tag ruleset forbids deletion and non-fast-forward with no bypass
actors, so `v2.6.7` cannot be moved or reused, exactly as `v2.6.2` could not.

Nothing in the repository could have caught it: the task passes locally, where
every tag exists, and the gap appears only in a CI checkout. So beyond the
one-line fix there is now a harness check asserting that any job invoking a
tag-dependent task checks out with tags.

**Both field defects were found from the issue list**, because 2.6.7 records the
violated constraint on sync-phase failures. Before that they read "row processing
failed (IntegrityError)" and were indistinguishable.

*`dcim.module` → `dcim_consoleport_unique_device_name`.* NetBox builds its
component-adoption candidates as
`device.<components>.filter(module__isnull=True)`, so a component already claimed
by a *different* module is invisible to adoption. The module type's template then
instantiates a second component with the same name and `UNIQUE(device_id, name)`
rejects it. `_adopt_components=True` is already set and `dcim.module` is on the
adapter path, so adoption runs — it simply cannot cover this case. The collision
is now detected before the write.

*`dcim.device` → `dcim_device_primary_ip4_id_key`.* `UNIQUE(primary_ip4_id)`:
an address is the primary of exactly one device. The `Mgmt_`-tag path assigned
`device.primary_ip4` with no ownership check, so two devices resolving the same
management address ended the whole ingestion at `device.save()`, after every
workload had already been staged. Existing owners are now read from the branch —
an address may already belong to another device from an earlier sync or an
operator edit, and that owner need not appear in this run's assignment set.

Both are reported and skipped rather than failed, for the reason established in
this line of work: a failed row blocks baseline promotion, so a condition the
sync cannot resolve must not be allowed to wedge convergence.

## Validation

- `test_field_reported_integrity_failures` — 5 tests covering both defects,
  including that an *unclaimed* component is still left to adoption, so the guard
  does not skip modules that install correctly.
- `test_primary_ip`, `test_module_readiness`, `test_module_readiness_rollup`,
  `test_sync`, `test_models`: 440 tests, OK.
- `scripts/tests`: 247 OK. `pre-commit run --all-files` converged.
- **Negative control on the harness check:** with `fetch-depth: 0` removed the
  check fails, and it is silent on the fixed workflow.
- The module test reproduced the customer's exact error while being written —
  `dcim_consoleport_unique_device_name`, `Key (device_id, name)=(…, Console)` —
  because creating a module instantiates its console-port template and assigns
  the port to that module. Independent confirmation of the mechanism rather than
  inference from the constraint name.

## Rollback

Revert the commits. All three changes are additive: two pre-write guards, one
workflow input, one harness assertion. No migration or persisted state.

## Decision Log

- 2026-07-30: `2.6.7` is omitted from the compatibility tables rather than shown
  as superseded, matching how `2.6.2` was handled. The tables list releases that
  exist on PyPI; showing a version that was never published would misstate what
  an operator can install. The `2.6.8` summary explains the gap.
- 2026-07-30: Module collisions are a rolled-up skip, not per-row warnings. The
  reporting customer has 1,381 modules, and a per-row wall is what the
  module-bay rollup already exists to avoid.
- 2026-07-30: Primary-IP conflicts are logged as counts per field. Device names
  and addresses are customer data and stay out of the log.

## Evidence

- Constraint definitions read from the running database:
  `dcim_consoleport_unique_device_name` is `UNIQUE (device_id, name)`;
  `dcim_device_primary_ip4_id_key` is `UNIQUE (primary_ip4_id)`.
- NetBox's adoption candidate set was read from `dcim.models.Module.save` on the
  4.6.6 runtime, not assumed.
- The reporting deployment ran plugin `2.6.7` on NetBox `4.6.6` — so the version
  tolerance shipped in that tranche is working; the plugin loads where it
  previously refused.
