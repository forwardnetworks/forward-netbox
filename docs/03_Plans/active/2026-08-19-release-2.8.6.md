# Release 2.8.6

## Goal

Ship the two changes that make an unhandled failure diagnosable from the NetBox
UI, so the deployment blocked on one stops paying for opaque runs.

## Why

A deployment has now lost three syncs to the same unhandled `KeyError` -
`ipam.ipaddress`, plan item 51 of 90, about thirteen seconds in, roughly half an
hour of staging discarded each time. Two of those runs happened after releases
intended to make the failure legible.

2.8.5 made the exception's KEY nameable, keyed off `MODEL_SYNC_CONTRACTS`. The
key is not a name this repository chose, so it was correctly withheld and the
third run was exactly as opaque as the first two. That release was aimed at the
wrong artifact: a frame exists for every exception, a nameable key does not.

While this release was being gated, the defect was identified and fixed, and
the fix is included: a change batch carrying two models corrupted ChangeDiffs
(see `2026-08-19-mixed-model-change-diffs.md`). The diagnostic changes remain
what they were - the means by which the next such defect names itself.

## Constraints

- A patch. No migration, and nothing changes what a sync writes to NetBox.
- No shell. The release owner's requirement, and the direct reason for the
  second change: an operator must not be asked to read RQ's failed-job registry
  out of Redis, which is what finding this failure required and which returned
  nothing newer than two months old when it was tried.
- Nothing exported gains a value. Frames are code identifiers; the traceback
  lives only where it does not travel.
- `max_version` stays `4.6.99`, unchanged and for the same measured reason.

## Touched Surfaces

Landed across two pull requests:

- `#256` a failure records where it happened
- `#257` the traceback is readable without a shell

This commit adds the version surfaces, the compatibility tables, and this plan.

## Approach

`structured_failure_diagnosis` records `raise_site`, the innermost in-package
frames as `path:line:function`. Both failure recorders append the innermost one,
and the log sanitizer recovers it - that sanitizer REBUILDS a failure line from
what it can recover and discards the rest, so a detail it cannot read back is
written and then thrown away, which is how an earlier attempt at richer messages
was undone.

The full traceback goes to `job.data["traceback"]`, which NetBox renders on the
job page and which `sanitize_job_diagnostics` already replaces wholesale on
export. `exc_info=True` reaches the Python logger at the top-level sync failure
only, which is the deployment's own server log.

Three tiers, no shell in any of them: the issue row names the line, the job page
carries the traceback and never leaves the deployment, and the support bundle
carries frames but not values.

## Validation

Recorded in the Release Authorization section below, bound to the evidence base
commit: the full isolated gate and the exact-runtime artifact test, both on the
final tree, both on NetBox 4.6.8.

## Rollback

No migration, so a downgrade is an install of the prior wheel. Both entries are
observational; reverting restores the previous reporting and changes nothing
about what a sync does.

## Decision Log

- **Ship diagnosability before the defect it will diagnose.** The alternative is
  another blind run at that deployment, and three have been spent already.
- **Frames, not the key.** The previous release named the key and could not name
  this one.
- **The traceback in `job.data`, not in the issue's `raw_data`.** `raw_data` is
  exported verbatim; a traceback there would leave the deployment.
- **Patch, not minor.** Nothing gains an operator control.

## Open

- The defect: FOUND and fixed while this release was being gated. The
  narrowing recorded here earlier was correct as far as it went - the raise was
  not in `bulk_orm_apply_ipaddress` nor its direct callees, but in Branching's
  `_update_conflicts`, handed a corrupted diff our `_sync_branch_change_diffs`
  had created from a mixed-model batch.
- That deployment's RQ failed-job registry has recorded no plugin failure since
  2026-06-29 despite three errored syncs since. `expected_failure` covers only
  `ForwardSyncError`, `SyncError` and `JobTimeoutException`, so a `KeyError`
  should re-raise and register. Unexplained, and a second reason the server log
  matters more than the registry.
