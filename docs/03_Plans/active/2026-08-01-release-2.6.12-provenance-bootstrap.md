# Release 2.6.12: Provenance Bootstrap

## Goal

Make the release provenance gate satisfiable. Two of its requirements have not
been jointly satisfiable since the 2.6 series began, and between them they burned
`v2.6.10` and `v2.6.11`.

## Contract

- A release can be tagged and published without either requirement failing.
- The trusted sensitive-content scanner is still verified at the release commit,
  by a check that is strictly stronger than the one it replaces.
- No gate is weakened, disabled, or made advisory.

## Constraints

- `.github/workflows/release.yml` stays tag-triggered and Trusted Publishing
  stays scoped as it is.
- The main ruleset is not touched.
- The bootstrap files themselves are not modified by this change.

## Touched Surfaces

- `scripts/verify_release_provenance.py` - `_require_security_bootstrap`,
  `BOOTSTRAP_FILE_DIGESTS`, `_git_capture_bytes`, result key rename
- `scripts/check_harness.py`, `scripts/tests/test_check_harness.py` - pin the
  new constant
- `scripts/tests/test_verify_release_provenance.py` - cover the new check
- `README.md`, `docs/README.md`, `docs/01_User_Guide/README.md`,
  `CHANGELOG.md` - correct the `2.6.11` root cause and fold it in as unpublished
- `docs/03_Plans/active/2026-07-31-release-2.6.11-tranche.md` - correct the
  root cause recorded there
- Version surfaces for `2.6.12`.
- This plan.

## Approach

**The conflict.** `verify_release_commit_provenance` walks the first-parent
commits from `PRIOR_RELEASE_TAG` and requires two things of that range:

1. `_require_merged_main_pr` requires every commit to still have a successful
   main-push run for `ci.yml` and `codeql.yml`. GitHub expires workflow runs, so
   this bounds how long the range may be.
2. `_require_security_bootstrap` diffed `PRIOR_POST_RELEASE_DOC_COMMIT` against
   the first reviewed commit and required all three bootstrap files to appear in
   that diff. Only one commit has ever touched `scripts/sensitive_content.py` -
   `3b6fe4d`, "security: bootstrap 2.6 release controls". The check therefore
   only passed while the anchor sat immediately before `3b6fe4d`, which pins the
   anchor in the past.

A fixed anchor makes the range grow until a run expires. Moving the anchor makes
the bootstrap diff empty. `v2.6.10` failed the first way; `v2.6.11`, after the
anchor was moved to fix it, failed the second. There is no anchor value that
satisfies both.

**The fix.** `_require_security_bootstrap` now verifies the bootstrap files at
the release commit against pinned SHA-256 digests, rather than requiring them to
appear in a diff from an anchor.

This is strictly stronger than what it replaces. The diff test accepted *any*
change that touched all three paths - including one that emptied them; it never
looked at content. The digest test accepts only the exact reviewed bytes.
Changing the scanner now means updating `BOOTSTRAP_FILE_DIGESTS` in the same
pull request, which the trusted scanner and CodeQL both gate.

It is also anchor-independent, so the anchor is free to advance each release and
the reviewed range stays short enough that retention is not a factor.

`security_bootstrap_commit` is renamed to `first_reviewed_commit` in the result:
that commit is no longer required to be a bootstrap commit, and leaving the old
name would have described the value wrongly.

**Correcting the record.** The `2.6.11` tranche plan, PR #112 and the `2.6.11`
release notes all state that the anchors went stale because four releases were
tagged by hand rather than through `release.py --auto-finish`. That was wrong.
The anchors were pinned deliberately, to straddle `3b6fe4d`. The hand-tagging
did happen and did skip the bridge step, but it is not why provenance failed.
Every surface carrying that claim is corrected here.

**Version surfaces.** All four bump together to `2.6.12`, including the
fast-baseline runtime pin - bumping that separately silently reverts the fast
baseline from roughly six minutes to roughly fifteen hours with nothing an
operator can see. `2.6.10` and `2.6.11` are removed from the compatibility
tables rather than promoted: both were tagged and neither published, so PyPI
goes straight from `2.6.9` to `2.6.12`. Both tranches are folded into the
`2.6.12` row and named as unpublished, matching `2.6.2`, `2.6.7` and `2.6.8`.

## Validation

- `verify_release_provenance.py --tag v2.6.11` passes against the real tag and
  the live GitHub API with this change applied, which is the end-to-end proof
  that the bootstrap check now holds on a moved anchor.
- A test asserts a modified bootstrap file is rejected, and another asserts an
  absent one is.
- Full local gate and exact-runtime artifact test, recorded below.

## Rollback

Revert the commit. `_require_security_bootstrap` returns to the diff test, which
means releases fail again at the tag - so a rollback should be paired with a
decision about which of the two failure modes to accept.

## Decision Log

- 2026-08-01: Pinned content rather than relaxing the retention walk. Excluding
  expired runs would have removed a real control to work around a design
  conflict; pinning the scanner's bytes removes the conflict and tightens what
  is checked.
- 2026-08-01: Kept `PRIOR_RELEASE_TAG` at `v2.6.10` rather than reverting to
  `v2.5.11`. With the bootstrap check no longer anchor-dependent, the short
  range is the safer of the two, because it is the one whose runs still exist.
- 2026-08-01: `v2.6.11` is not recoverable. Its tagged tree contains the old
  verifier, so re-running its release workflow fails identically. The version
  number is spent.

## Evidence

- `v2.6.11` failed at `Verify protected main-branch release provenance` with
  `security bootstrap is missing required files` naming all three paths; build,
  publish and github-release were skipped, so no artifact exists and PyPI stayed
  on `2.6.9`.
- With this change, `Release provenance verification passed.` for that same tag.
