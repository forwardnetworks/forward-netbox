# Release 3.0.12

## Goal

Ship the tranche that follows 3.0.11 (PR 611): a blocked run says when Forward failed to collect devices in scope, the support bundle answers the follow-up questions a customer report raises, Scope Reconciliation opens with one checklist that says what to do about each cleanup count, devices nobody manages that Forward no longer has can be deleted through a guarded, reviewed action, and firewall contexts can each have a primary IP.

## Constraints

- No customer names, network ids, snapshot ids, hostnames or addresses in the repo, plans, tests or docs. Tests use synthetic names.
- No shipped NQE query change, so nothing to republish. No migration.
- The one runtime dependency change is forward-sdk 0.1.29 to 0.1.31. The upgrade gate's from-side pin in `development/constraints-upgrade-from.txt` moves to 0.1.29 because the previous release (3.0.11) ships that pin.
- The new delete (`prune_unmanaged`) has no unattended path and the narrowest allowlist in the plugin; the firewall-context copies are opt-in and off by default.
- The support bundle stays name-free.

## Touched Surfaces

- Blocked runs and the bundle: `snapshot_collection_health.py`, `validation.py`, `validation_guidance.py`, `health_summary_blocks.py`, `health_evidence.py`, `bundle_diagnostics.py`, `bulk_merge.py`, `merge.py`, `scope_reconciliation.py`.
- Cleanup: `cleanup_checklist.py`, `views.py`, `urls.py`, `jobs.py`, `sync_facade.py`, `api/views.py`, the Scope Reconciliation and prune templates, `bundle_label_index.py`.
- Firewall contexts: `context_ip_copies.py`, `primary_ip.py`, `primary_ip_reasons.py`, `sync_primitives.py`, `sync_ipam.py`, `apply_engine_bulk.py`, `forms.py`, `model_validation.py`.
- `constraints.txt`, `pyproject.toml`, `poetry.lock`, `scripts/validate_sbom.py` (forward-sdk 0.1.31) and the release surfaces written by `scripts/release.py`.

## Approach

1. PR 611 merged to `main` after code-reviewer audits (three on the delete, one on the context copies), every finding fixed and tested, and the full Django suite passed (4303 tests, 33 skipped) before the last small commit.
2. Run `scripts/release.py 3.0.12` through the usual lineage: cut, authorize, evidence, tag, post-release bridge, anchor.
3. After the tag nothing needs republishing. A customer upgrades, re-syncs and sends a bundle.

## Validation

- `invoke ci` on the release tree via `scripts/release.py`, including the artifact and upgrade legs.
- The full Django suite and `pre-commit run --all-files`; `invoke harness-check`.
- Forward-side claims were checked read-only against a real network.
- Not verified: the NetBox-side bundle evidence (delete accounting, include-tag timeline, prefix-delete cause, context copies, checklist counts) on a real install, the new pages in a browser, and the copies with a netbox-branching branch merged in production.

## Rollback

Revert the release. Nothing is migrated. The new parameter defaults off and the new bundle fields are additive. Per-context address copies, if created, stay until deleted (filter IP addresses by the `forward-context-copy` tag).

## Decision Log

- The release-only sensitive-pattern feed is a GitHub secret and cannot be read locally, so the cut runs with the parity bypass; the release workflow runs the real feed at tag time.
- The user chose to cut with the NetBox-side bundle evidence still unproven on real data.
- The pre-push upgrade gate needs the from-side pin to stay at the previous release until the version bumps, so it moves in this release commit.
