# Release 2.6.10 Tranche

## Goal

Make a merge failure explain itself without anyone reading a log, stop a
permanently unsatisfiable row from holding a baseline hostage, and stop the one
protected delete from reading as a defect.

## Contract

- Every non-field validation failure names its rule in the UI - catalogued ones
  by slug, uncatalogued ones by wording with all values masked.
- A row NetBox refuses on its own validation rule is recorded and skipped, not
  failed. Integrity and other errors still fail and still block.
- The ingestion log download contains the issues behind the run.
- The baseline delete refusal reads as expected behaviour, not an error.
- Upgrade and re-run the sync. No migration, no operator step.

## Constraints

- Persisted diagnostics stay free of customer data - schema identifiers, rule
  slugs, and wording with every value-bearing token masked.
- Do not weaken any fail-closed gate.

## Touched Surfaces

- `forward_netbox/utilities/diagnostics.py` - rule catalogue, message shaping,
  `describe_failure`
- `forward_netbox/utilities/{merge,sync_orchestration,sync_reporting}.py`
- `forward_netbox/views.py` - issues in the log export and support bundle, the
  delete refusal
- `forward_netbox/tests/test_merge_rule_rejection.py` (new)
- Version surfaces and the compatibility tables.
- This plan.

## Approach

**`__all__` is a field name meaning "no field".** A customer's `ipam.ipaddress`
merge failure reported exactly that and nothing else, because the diagnosis
recorded field names only. The message that identifies the rule cannot be
persisted as-is: NetBox interpolates before raising
(`_("{ip} is a network ID...").format(ip=...)`), so by the time the exception
exists the address is inside the string.

An allowlist resolves known rules to slugs this module defines. Anything
unrecognised is reduced to wording - a token survives only if it is purely
alphabetic, so addresses, prefixes, interface and device names are all masked
while ordinary English is not. That second path matters more than the first: it
means the *next* unknown rule is legible on sight instead of after a release.

**Asking the customer for logs was never going to work.** The merge recorder
logs the model and the exception class; the message is discarded. The grep we
sent could not have matched anything on any deployment. The log download now
carries the issue rows themselves, with an explicit `truncated` flag past 200 so
a partial export cannot read as complete.

**A rule rejection is not a retryable failure.** Any failed row blocks baseline
promotion, so a handful of permanently unsatisfiable addresses could stop
thousands of correct changes from ever being attested. Re-running cannot change
a `ValidationError` - the rule is a property of the destination, not of the
incoming data - so those rows are recorded and skipped. Integrity errors stay
failures: those are usually ordering or contention, where a retry is right and
skipping would hide a real defect.

**The protected delete was reported as a bug twice.** One ingestion in a
sequence refused to delete while the rest went fine, and the UI said so in red.
It is the baseline - the record of what has already converged - and NetBox
protects it deliberately. The refusal now says that, and is raised as a warning
rather than an error.

## Validation

- `test_merge_rule_rejection` (new): the retryable/unsatisfiable split, all five
  catalogued rules, precedence across the shared helper, and that an
  uncatalogued rule reaches the message while a device name, an address and a
  VLAN name do not.
- `test_issue_diagnosis`: 15 OK. `test_ingestion_merge`: 28 OK.
  `test_log_export`: 14 OK. `test_merge_rule_rejection`: 14 OK.
- **The new tests found a real defect before the release, not a test artifact.**
  `getattr(exc, "message_dict", None)` returns `None` for a bare
  `ValidationError`, because the property raises `AttributeError` and `getattr`
  swallows it into the default. The diagnosis block was gated on that value, so
  a `ValidationError` raised directly - rather than through `full_clean()`,
  which builds the dict form - recorded nothing but its exception class. That is
  precisely the failure this release exists to remove, reintroduced one layer
  down. Both call sites now branch on `error_dict` and fall back to `messages`.
- Rule slugs verified against message text read from the live 4.6.6 runtime, not
  written from memory.

## Rollback

Revert the commits. All changes are additive - a catalogue, a helper, extra
export keys, one message level. No migration or persisted state.

## Decision Log

- 2026-07-31: An allowlist rather than redacting the raw message. Masking alone
  would be general, but persisted diagnostics are held to schema identifiers
  only, and an allowlist cannot leak a value the catalogue does not contain.
- 2026-07-31: Uncatalogued rules still emit masked wording. An allowlist alone
  would leave a first-time rule as silent as `__all__`, which is the exact
  failure this work exists to remove.
- 2026-07-31: `ValidationError` alone is treated as unsatisfiable. Broadening it
  to any repeated failure would have swept up ordering bugs that a retry fixes.
- 2026-07-31: A baseline can now be attested with a few rows unapplied. They
  stay recorded as issues and reappear in drift every run, which is visible;
  a baseline that can never promote is not. Reversible if the stricter
  behaviour is preferred.
- 2026-07-31: Uploading diagnostics to Forward was considered and rejected. The
  only endpoint taking an arbitrary zip is snapshot ingest, which would create
  junk snapshots in the customer's network and worsen an API-volume complaint
  Forward has already raised; `/collector/logs` is protobuf and collector
  scoped. Transport was never the gap - bundle contents were.

## Evidence

- The customer's ingestion 2708 reached merge and failed with
  `on invalid field(s) __all__`, which is 2.6.9's diagnosis working and also the
  proof that field names alone are not enough.
- A `journalctl` search of the worker over the failing minute returned nothing,
  consistent with the message never being logged.
- `IPAddress.clean()` on 4.6.6 has seven raise sites; four are field-scoped and
  five are non-field, and the five are catalogued here.
