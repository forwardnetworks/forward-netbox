# Advance the release provenance anchor to 2.8.0

## Goal

Move `PRIOR_RELEASE_TAG` and `PRIOR_POST_RELEASE_DOC_COMMIT` onto `v2.8.0` and
its bridge, and promote 2.8.0 to current in the compatibility tables.

## Why

The verifier walks the first-parent lineage from the anchor bridge to the tag
being published. Left on `v2.7.13`, that range grows with every commit, and a
range large enough for GitHub to expire the run burns a release at the tag -
which is what happened to `v2.6.10`. The anchor is advanced immediately after a
release for that reason, not as bookkeeping.

The table promotion belongs in the same change: `check_harness.py` fails while
the anchor disagrees with whichever release the table calls current, so
advancing one without the other trades a stale anchor for a red harness.

## Constraints

- The bridge must already be on `main` and must be the first first-parent
  commit after the tag. `5826e34` is, via #203.
- `v2.8.0` published successfully, so it is NOT recorded in
  `UNPUBLISHED_RELEASE_TAGS`; that list is only for tags that were cut and never
  shipped.
- Five sites carry the anchor and must move together, two of them outside
  `verify_release_provenance.py`.

## Touched Surfaces

- `scripts/verify_release_provenance.py` - both anchor constants
- `scripts/check_harness.py` - the expected `release.yml` fetch line
- `.github/workflows/release.yml` - the tag it force-fetches
- `scripts/tests/test_tasks.py` - the assertion pinning that line
- `README.md`, `docs/README.md`, `docs/01_User_Guide/README.md`, `CHANGELOG.md`

## Approach

Mechanical. The bridge SHA is read from
`git rev-list --first-parent v2.8.0..origin/main | tail -1` rather than copied,
and the table promotion goes through `promote_release_candidate_text` and
`gen_changelog.py` rather than by hand, so the three tables and the changelog
cannot drift apart.

## Validation

`scripts/check_harness.py` (which enforces both the anchor/table agreement and
the `release.yml` shape) and `scripts/tests`.

## Rollback

Revert. The anchor returns to `v2.7.13`, which is stale but not broken until the
reviewed range grows large enough to expire a run.

## Decision Log

- **Promote the table in the same commit as the anchor.** The harness couples
  them, so splitting them guarantees one red commit.
- **Do not add `v2.8.0` to `UNPUBLISHED_RELEASE_TAGS`.** It published: PyPI has
  the wheel and sdist, and the GitHub release carries both plus the SBOM. That
  list exists for tags that never shipped, and recording a shipped tag there
  would make the next anchor check accept a false statement.

## Open

- The first 2.8.0 tag attempt was refused at publish and its commits survive in
  `refs/pull/199/head` and `refs/pull/200/head`, which only GitHub Support can
  purge. Not an anchor concern - those refs are not on the first-parent lineage
  - but it is the one piece of this release that is not closed out.
