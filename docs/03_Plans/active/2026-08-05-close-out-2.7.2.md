# Close out 2.7.2

## Goal

Finish the post-release steps for the shipped `v2.7.2`: promote the release
table, regenerate the changelog, and advance the provenance anchor onto the
bridge commit. Deliberately WITHOUT opening a `.dev0` version on `main`.

## Contract

- The release table and the provenance anchor move in the SAME change. The
  harness requires the anchor to track the release the README calls current, so
  splitting them leaves `main` red.
- The four version surfaces are not touched at all, so the fast-baseline pin
  stays consistent with the declared version by not moving either.
- This change is NOT the post-release bridge. The bridge slot is already held
  by the archive-only commit `d6c886c`, which is documentation only.

## Constraints

- The anchor is hardcoded in SIX coupled places: `PRIOR_RELEASE_TAG` and
  `PRIOR_POST_RELEASE_DOC_COMMIT` in the verifier, the tag fetch in
  `release.yml`, two literal assertions in `check_harness.py`, a workflow
  fixture in `scripts/tests/test_check_harness.py`, and an assertion in
  `scripts/tests/test_tasks.py`. All six must move together or the next release
  fails at the tag, when the version is already spent.
- `check_harness.py` reads the real workflow, so it passes locally while the
  two fixture-based tests still fail. Only `python3 -m unittest discover -s
  scripts/tests` catches that pair.
- No customer identifiers.

## Touched Surfaces

- `README.md`, `docs/README.md`, `docs/01_User_Guide/README.md`, `CHANGELOG.md`
- `scripts/verify_release_provenance.py` (anchor)
- `scripts/check_harness.py` (tag assertions)
- `.github/workflows/release.yml` (prior-tag fetch)
- `scripts/tests/test_check_harness.py`, `scripts/tests/test_tasks.py`

## Approach

Promotion is driven by the existing `release.py` helpers rather than applied by
hand. The anchor moves to `v2.7.2` and to bridge commit `d6c886c`, whose diff
against the tag contains only `docs/**.md` paths.

`release.py 2.7.3 --open-next` was run and then reverted. The four version
surfaces stay at `2.7.2`.

## Validation

`pre-commit run --all-files` (twice), `python3 -m unittest discover -s
scripts/tests`, `scripts/check_harness.py`, and `scripts/check_harness.py
--base origin/main`. Recorded with real outcomes rather than asserted.

## Rollback

Revert. `v2.7.2` is tagged and on PyPI independently of this commit, so
reverting only returns the documentation and the anchor to their pre-close-out
state.

## Decision Log

- **No `.dev0` opened on `main`.** Operator instruction, after a customer
  upgrading from source landed on `2.7.2.dev0` and reported it as a shipped
  build. Nothing in the release tooling requires a dev version on `main`: the
  anchor check ties `PRIOR_RELEASE_TAG` to the README table, not to
  `pyproject.toml`, and no preflight, authorization, or provenance check reads
  the declared version at all.
- Promotion was kept OUT of the bridge commit, for the same reason as `2.7.1`:
  the harness couples promotion to the anchor, and the anchor lives in
  `scripts/`, so promoting in the bridge would drag executable content into a
  commit that must carry none.

## Open

- With `main` declaring `2.7.2` while carrying post-`2.7.2` commits, a source
  install reports a version it is not. The previous shape made that visible in
  the version string; this one does not, so the next release must bump the four
  surfaces as its FIRST post-tag act rather than relying on a dev marker to
  signal "not the release".
- Task #37 (refuse a prerelease build against production) was designed around
  detecting a `.dev` marker. With no dev marker on `main`, that guard cannot
  fire for source installs and needs a different signal — the release tag the
  commit descends from, not the declared version.
