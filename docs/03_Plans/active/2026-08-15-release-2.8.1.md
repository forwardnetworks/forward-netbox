# Release 2.8.1

## Goal

Ship the drift measurement - the report has never once produced a number - and
the merge-rejection row identity, which together close both halves of the
deployment report that opened #206.

## Constraints

- The four version surfaces moved together with the fast-baseline runtime pin,
  through `scripts/release.py` rather than by hand. A stale pin there reverts
  the first baseline from about six minutes to about fifteen hours, silently.
- The lineage from the recorded bridge to the release commit must hold at least
  four commits, with the production and release commits last.
  `scripts/check_release_lineage.py` proves it before tagging.
- The prior-release anchor stays at `v2.8.0` until the post-release change; the
  bridge commit after the tag must be documentation-only.
- `FORWARD_SENSITIVE_PATTERNS` is not on this host. The first 2.8.0 attempt was
  refused at publish for exactly that gap, so this release also runs the scan
  locally against the identifier that caused it before the tag exists.
- A patch, not a minor. Nothing here changes when a destructive operation fires
  and nothing adds an operator control; the drift work fixes a report that never
  worked, and the preview parameter it adds is unreachable by any existing
  caller.

## Touched Surfaces

Landed across five pull requests:

- `#205` the agent skill's NQE call-volume wording

## Approach

### Drift

`EXACT_COMPARISON` was defined in `drift_report.py` and produced nowhere. The
dependency preview counted every fetched row as a change, so `In sync`,
`Drifted models` and `Total drift` read "Not measured" on every run for every
deployment, permanently - and no amount of re-running cleared it. A deployment
read 694,477 "estimated apply work" against roughly 4,000 devices, which is the
row count rather than a divergence.

The preview now compares against NetBox for ten models by running the apply
path in a read-only mode, rather than reimplementing the comparison. A second
normaliser would drift from the first, and the symptom would be a drift figure
wrong in whichever direction is least noticeable - worse than no figure, because
an operator would act on it.

Coverage is partial on purpose. `comparison_available` stopped being
`all(models)`, because there is always at least one uncompared model and that
gate is what made the report silent. The uncompared models are named. `In sync`
stays unanswered until every model is compared, since zero drift over part of an
estate is not a statement about the estate.

### Merge rejection identity

A skipped `ipam.ipaddress` row named the rule it violated but not the row. The
record now carries the NetBox primary key, which resolves to the object page
where the edit has to happen. It names the pk rather than the address
deliberately: the address, device and interface are customer values and
ingestion issues reach support bundles, while a primary key is a surrogate that
discloses nothing.

### A defect in 2.8.0, found by this release's gate

Migration `0052_device_absence_quarantine` shipped in 2.8.0 depending on
`dcim.0241_nullify_empty_cable_end`, a NetBox **4.6.6** migration, while the
plugin declares `min_version = "4.6.5"`. On 4.6.5 the migration graph cannot be
built at all:

    NodeNotFoundError: Migration forward_netbox.0052_device_absence_quarantine
    dependencies reference nonexistent parent node
    ('dcim', '0241_nullify_empty_cable_end')

So **2.8.0 is not installable on NetBox 4.6.5**, and its supported-version claim
is false. Anyone on 4.6.5 is held at 2.7.13 until this release.

2.8.0's own gate could not have caught it. Its upgrade leg seeded 2.7.13 - which
has no `0052` - on 4.6.5 and only ever applied `0052` on 4.6.6. This release is
the first whose from side installs a plugin carrying that migration onto the
older supported NetBox.

The fix: `0052` only needs `dcim.Device` to exist, so it depends on
`dcim.0001_initial` like every other migration here. Changing a dependency does
not re-run an applied migration, so 4.6.6 installs that already applied it are
unaffected.

`makemigrations` writes whichever core migration is newest on the author's
machine, so this recurs by default rather than by mistake.
`test_migration_dependencies` now fails at author time on any version-specific
`dcim` dependency. It found a second one immediately - `0034` ->
`dcim.0166_virtualdevicecontext` - which is legitimate, because that migration
creates foreign keys to the model `0166` adds. It is allowlisted with that
reason, and the allowlist states the distinction between a real dependency and
an accidental one.

### Why the upgrade gate seeds the from side on 4.6.6

The published 2.8.0 wheel is what the from side installs, and it cannot be
changed - so the 2.8.0 -> 2.8.1 upgrade on 4.6.5 is impossible by construction
rather than merely failing. A from release is seeded on a runtime it can
actually run on, and for 2.8.0 that is 4.6.6 only.

`invoke ci` calls `artifact-upgrade-test` as a pre-task with no arguments, so
the existing `--from-netbox-ver` flag could not reach it.

The first attempt at this was an environment door, matching the one the
from-side plugin version has. It worked and it was wrong: being global to the
run, it also moved the scenario suite's upgrade fixtures from `4.6.5 -> 4.6.6`
to `4.6.6 -> 4.6.6`, silently dropping the NetBox upgrade path they exist to
exercise - for every from-release, when one needed it.

Which runtime a release can run on is a property of that release, so it is a
per-release entry in `UPGRADE_FROM_NETBOX_OVERRIDES` instead.
`UPGRADE_FROM_NETBOX_VER` stays `v4.6.5` and every other from-release still
seeds there. `invoke ci` needs no special environment for it, which matters
given how much of this release's difficulty came down to whether an environment
variable was set. Two tests hold it: one carrying the reason 2.8.0 is
exceptional, one asserting only 2.8.0 is listed, so each future entry has to be
justified where it is written.

## Validation

`invoke ci` and `invoke artifact-test` on the exact tree tagged here apart from
the authorization record, recorded below.

Also run before tagging, because its absence is what refused the first 2.8.0
attempt: `check_sensitive_content.py --git-files --protected-history
--require-env-patterns` against the identifier the release feed carries and the
local feed does not.

## Rollback

The tag cannot be withdrawn. A defect found after publication needs 2.8.2.

Rolling back is not neutral here, which is unusual for a patch. 2.8.0 stays
installable from PyPI, but only on NetBox 4.6.6 - it cannot be installed on
4.6.5 at all, and this release is the fix for that. A deployment on 4.6.5 has no
2.8.x to roll back to and would have to return to 2.7.13.

## Decision Log

- **Patch, not minor.** No destructive behaviour changes and no operator control
  is added. The `preview` parameter threaded through the apply engine defaults
  to `False` and no existing caller reaches it, which the unchanged suite is the
  evidence for.
- **Ship partial drift coverage.** Withholding every figure until all models can
  be compared is what produced "Not measured" in the first place, and the
  adapter-only models cannot be compared by this machinery at all.
- **`In sync` stays `None` under partial coverage.** Reporting "Yes" from a
  measured subset is the same class of error as reporting zero drift for a model
  nothing looked at.
- **`virtualchassis` declines to answer.** It is tractable, but an unsaved
  chassis makes a device with no chassis compare equal and count as unchanged -
  an under-count that looks correct. Low volume, and measuring it unlocks
  nothing while the adapter models remain uncompared.

## Open

- The adapter-only models have no comparison and are reported as unmeasured.
  #206 stays open for them.
- The quarantine defaults shipped in 2.8.0 (3 runs / 72 hours) are still a guess
  at one deployment's sync cadence. They are source parameters.
