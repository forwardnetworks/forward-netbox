# Release 2.7.9

## Goal

Unblock the customer. Their ownership reconciliation still fails on 2.7.6, and
the fix has been sitting on `main` through two burned tags.

## Contract

- The four version surfaces move in ONE commit.
- The release commit carries its own release-authorization section, whose
  evidence base commit equals the parent of the commit that gets tagged. Never
  write that heading's text earlier in the plan: the checker splits on its
  first occurrence.
- The table marks 2.7.9 a RELEASE CANDIDATE. The anchor and the "Current
  release" marker move together after the tag.
- The first first-parent commit after the tag is documentation-only.

## Constraints

- Gates run locally; there is no CI. Run the FULL plugin suite.
- Verify `invoke lint` IMMEDIATELY before each commit and again after.
- PyPI egress on this host stalls on large HTTP/1.1 responses, so the upgrade
  gate needs `FORWARD_NETBOX_UPGRADE_FROM_VERSION=2.7.6`. Only the DISCOVERY is
  offline; the upgrade itself runs in full.
- `FORWARD_SENSITIVE_PATTERNS` is a repository secret and is not present on this
  host, so the preflight's parity scan cannot run and
  `FORWARD_NETBOX_PATTERN_PARITY_UNVERIFIED=1` is required. The publish gate
  still applies the superset feed and can still refuse the tag.
- The lineage must be `bridge -> control -> production -> release`. The bridge
  is `0f4a4a7`, the control commit is the anchor advance (#176), and the
  production commit is the pattern-parity fix (#177).

## Touched Surfaces

- `pyproject.toml`, `forward_netbox/__init__.py`,
  `forward_netbox/utilities/fast_baseline.py`,
  `forward_netbox/tests/test_runtime_dependency_check.py`
- `README.md`, `docs/README.md`, `docs/01_User_Guide/README.md`, `CHANGELOG.md`

## Approach

The shipped behaviour is unchanged from what 2.7.7 and 2.7.8 would each have
shipped: one fix, already on `main` and already through the full suite (#172).
This change is the version bump and the release notes.

## Validation

`invoke ci` and `invoke artifact-test` on the pinned environment, then the tag.

## Rollback

Before the tag is pushed, revert the branch. After it is pushed the tag is
immutable and a defect costs a version number - which is what 2.7.3, 2.7.7 and
2.7.8 each cost.

## Decision Log

- **Two tags were burned before this one, for unrelated reasons.** 2.7.7 used a
  real customer name as a test fixture and the release-only pattern feed caught
  it. 2.7.8 was refused because the history rewrite that removed that name
  rebuilt two commits, and pull request association is by SHA, so the verifier
  could no longer prove they were reviewed.
- **The anchor now sits at 2.7.8**, which puts both unverifiable commits behind
  it. `v2.7.8` is recorded in `UNPUBLISHED_RELEASE_TAGS` so the harness accepts
  an anchor that the compatibility table does not call current.
- **The root cause is fixed in the production commit for this release.** The
  release-time scan now runs at preflight, so the next fixture carrying customer
  data costs a second rather than a version number.

## Open

- If the customer also has AMBIGUOUS device names - the same name in two sites -
  this will not fully unblock them. The refusal now reports how many of each.
- Their eleven absent devices remain absent.
- On this host the parity scan is acknowledged rather than run, so the publish
  gate is still the first place the superset feed is applied.

Two environment overrides are set deliberately and recorded here rather than
hidden.

`FORWARD_NETBOX_UPGRADE_FROM_VERSION`: PyPI egress from this host stalls on
large HTTP/1.1 responses, so the gate could not ASK the index which release an
operator would be upgrading from. `2.7.6` is not a guess: it is the current
published release, confirmed on the index, and neither 2.7.7 nor 2.7.8
published anything. Only the discovery is offline; the upgrade itself ran in
full, seeding real rows under 2.7.6 and reading them back under the built 2.7.9
wheel.

`FORWARD_NETBOX_PATTERN_PARITY_UNVERIFIED`: `FORWARD_SENSITIVE_PATTERNS` is a
repository secret and is not present on this host, so the preflight could not
run the superset scan that this release introduces. The gap is narrowed rather
than closed here: the publish workflow still applies the superset feed and can
still refuse this tag, which is exactly what it did to 2.7.7.
